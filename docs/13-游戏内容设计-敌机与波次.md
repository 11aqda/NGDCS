## 2. 敌机类型表

> 速度单位是 **px/s**（不是 px/tick）—— 理由见 §5.1。
> 屏幕 720×960，20 Hz。`hp` 是击杀所需的玩家子弹命中次数。

| `type` | 名称 | `hp` | 速度 | 轨迹 | 射击间隔 | 弹型 / 角度 | 分数 |
|---|---|---|---|---|---|---|---|
| `0x01` | 直线俯冲 | **1** | 90 px/s 向下 | 直线下落，出屏即消失 | 1.2 s | `0x11`，`angle=128`（正下） | 10 |
| `0x02` | 横向移动 | **2** | 下落 60 + 横移 120 px/s | 下落到 `y ∈ [140, 300]` 后**固守该高度**左右来回（撞边反向） | 1.5 s | `0x12` 扇形 3 发，`angle = 112 / 128 / 144` | 20 |
| `0x03` | 追踪玩家 | **2** | 70 px/s 向下 + 40 px/s 横移 | 缓慢向**最近的玩家**横向靠拢（只调 x，不加速） | 2.0 s | `0x13`，`angle` 指向最近玩家（量化到 8 方向） | 30 |

### 2.1 为什么这样设计

| 选择 | 理由 |
|---|---|
| 三种敌人**速度都不高**（60~120 px/s） | 玩家只有左右移动，太快会变成"必死"，不是"可练" |
| `0x02` 固守高度来回 | 让玩家必须**改变位置**，而不是站着打 |
| `0x03` 只横移不加速 | 全速追踪会贴脸必杀；慢速靠拢给玩家反应时间 |
| 分数 10/20/30 | 与风险成正比，简单可讲 |
| `0x02`/`0x03` 各 2 血 | 有"需要打两下"的层次感，但不会太肉 |

> ⚠️ `0x03` 的"最近玩家"每 tick 重算会抖，实现时**每 10 tick（0.5 s）重算一次目标**，
> 中间保持方向 —— 既省算力，视觉上也更稳。

| `wave` | 敌机组合 | 数量 | 生成间隔 | 预计时长 |
|---|---|---|---|---|
| **1** | `0x01` × 18 | 18 | 0.90 s | ≈ 26 s |
| — | 波间停顿 | — | — | 3 s |
| **2** | `0x01` × 10 + `0x02` × 8 | 18 | 0.70 s | ≈ 23 s |
| — | 波间停顿 | — | — | 3 s |
| **3** | `0x01` × 8 + `0x02` × 8 + `0x03` × 6 | 22 | 0.60 s | ≈ 24 s |
| — | 波间停顿 | — | — | 3 s |

**刷新位置**：`x` 在 `[40, 680]` 随机（沿用 `SPAWN_MARGIN=40`），但**同一波内要求相邻两个敌机
的 x 至少相差 60 px** —— 否则会重现"一排飞下来"的问题（见 §6）。

**波次推进条件**：本波已生成的敌机**全部离场或被击落** → 停顿 3 s → 下一波。

预计流程总时长：

```
波次 1-3（含停顿）  ≈ 85 s
BOSS（下一个 commit）≈ 60 s
阵亡重试 1~2 次      ≈ 40 s
────────────────────────────
单局                 ≈ 3 分钟，落在 3~5 分钟目标区间
```

> 这些是**起始值**，实现后按实测调。目标：**不阵亡时一局 3~5 分钟**。

## 4. 只走 `GamePolicy`，默认路径不动

### 4.1 触发方式

```powershell
python -X utf8 -m server.main 9527 --game-mode
```

`--game-mode` 等价于：

```python
World(policy=GamePolicy(tick_hz=..., seed=...), enable_kills=True, fixed_entities=False)
```

- **`--game-mode` 隐含 `--enable-kills`**（不击杀就没法推进波次）
- `--game-mode` 与 `--fixed-entities` **互斥**（实验要恒定数量，游戏要波次），同时传就报错
- `--enable-kills` 单独传仍然可用（保持向后兼容，步骤 10 的用法不变）

### 4.2 唯一的改动点：给 `World.step` 加一个分派

```python
def step(self, players):
    self._move()
    if self.policy.manages_spawning:      # 新增：只有一行判断
        self.policy.tick_spawn(self, players)
    else:
        self._respawn(players)            # 默认路径：原样
```

`PlaceholderPolicy.manages_spawning = False` → **默认路径的行为一字未改**，
只是多读一个类属性。字节层面完全一致，黄金基线 SHA 会证明。

## 5. 三个必须先讲清的技术点

### 5.1 速度改成 **px/s**，不再用 `*_PER_TICK`

E5 已经量出：`PLAYER_SPEED_PER_TICK = 15` 这种写法让**游戏速度随 tick 率变化** ——
30 Hz 下玩家实际是 450 px/s，10 Hz 下只有 150 px/s（图 6-12 那个"反直觉结论"的根因）。

**默认路径不动**（E5 的数据还依赖它）。但 `GamePolicy` 内部按 **px/s** 定义速度，
再按 `tick_hz` 换算成每 tick 位移：

```python
class GamePolicy:
    def __init__(self, tick_hz: int = 20):
        self.per_tick = tick_hz / 1.0     # px/s → px/tick 的缩放在下面
    def enemy_move(self, enemy):
        px_per_tick = speed_px_s / self.tick_hz
```

**好处**：`--tick-hz 10` 和 `--tick-hz 30` 下游戏**手感一致**，而且顺手把 E5 指出的
设计缺陷在游戏路径里修掉了。

### 5.2 运行时状态挂在哪：`Enemy` 加**不参与快照**的字段

横向移动需要"阶段"、射击需要"冷却计时"、追踪需要"目标玩家"。
但 `Enemy` 现在只有 5 个字段，而**快照只发 `id/x/y/type/hp`**。

方案：给 `Enemy` 加带默认值的运行时字段

```python
@dataclass(slots=True)
class Enemy:
    enemy_id: int
    x: int
    y: int
    type: int = ENEMY_DIVE
    hp: int = 1
    # ↓ 新增，**不进快照编码**，PlaceholderPolicy 完全不碰
    phase: int = 0        # 0x02 的"下落/横移"阶段
    fire_cd: int = 0      # 射击冷却（tick 数）
    home_y: int = 0       # 0x02 固守的高度
    target_x: int = 0     # 0x03 当前追踪目标
```

**安全性**：`snapshot_enemies()` 只取前 5 个字段，**字节不变**；
PlaceholderPolicy 从不读写这些字段 → 默认行为不变。

> 备选方案是 `GamePolicy` 内部维护 `dict[enemy_id, State]`，但敌机被移除时要清理，
> 漏清理就是内存泄漏。挂在实体上随实体一起消失，更省心。

### 5.3 子弹来源要分支：**占位是"补满"，游戏是"发射"**

现在 `_respawn` 不管谁打的，直接把子弹补到 `bullet_target` —— 这是实验需要的
（子弹数恒定，E9 的自变量）。游戏模式必须反过来：**敌机按冷却主动发射**。

```python
# PlaceholderPolicy：保持"补到恒定数量"（E9 要的自变量）
# GamePolicy：     不自动补弹，子弹全部来自 enemy 的 fire_cd 与玩家的开火
```

实现上由 `manages_spawning` 一并接管（§4.2），默认路径不受影响。

**玩家开火**：现在玩家的子弹也是"补满"的。game-mode 下改为
**按住空格自动连发**（间隔 0.15 s），子弹从玩家当前位置向上 —— 这是游戏性的必要改动，
也只在 game-mode 生效。

> 需要 `client/main.py` 增加"空格开火"的发键。这是一个**新的输入语义**，
> 要确认是否接受（见 §8 待确认第 2 条）。

## 6. 顺带修掉"一排飞下来"

之前实测发现：所有敌机共用出生点 `y=0` + 同一速度 → **y 极差恒为 0**，永远是刚性横排。

`GamePolicy` 的三条修正：
1. **出生 y 加随机偏移**：`y = -rng.randrange(0, 120)`（从屏幕上方不同高度进入）
2. **速度加 ±12% 抖动**：每个敌机出生时定一个自己的速度倍率
3. **同波相邻 x 至少差 60 px**（§3）

## 7. 客户端如何按 `type` 渲染

**颜色语义不变**：冷色=我方、暖色=敌方（D-* 里定的规矩）。

| 对象 | 形状 | 颜色 | 备注 |
|---|---|---|---|
| 玩家 | 三角（现有） | 冷色/本机白边 | 不动 |
| `0x01` 俯冲 | 小三角（现有） | 正红 `#FF5858` | 尺寸 14 px |
| `0x02` 横向 | **菱形** | 橙红 `#FF7A3C` | 尺寸 18 px，比 0x01 大一圈 |
| `0x03` 追踪 | **倒三角 + 内核点** | 洋红 `#E040C0` | 尺寸 16 px，"有个眼睛盯着你" |
| 敌方子弹 `0x11` | 圆点（现有） | 橙红 | 半径 4 px |
| 敌方子弹 `0x12` | 圆点 | 亮黄 `#FFC040` | 半径 5 px（扇形弹更大更醒目） |
| 敌方子弹 `0x13` | 圆点 + 短尾迹 | 紫 `#C060FF` | 半径 4 px，"会追的"一眼能认出 |

**血量表现**：`hp ≥ 2` 的敌机在描边外侧加**一圈细白边**，被击中一次后消失。
（客户端只知道"当前 hp"，看不到"最大 hp"，所以用 `hp >= 2` 判断"还没被打"就够了。）

**客户端兼容性**：`test_client_ui.py` 有渲染相关测试，新增分支不能改动现有默认绘制路径 ——
`type` 命中未知值时**回落到现在的 `draw_enemy_ship`**。
