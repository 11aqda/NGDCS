## 1. 这步到底在解决什么问题？

### 用一个快递的比喻

想象你在寄快递：

```
你寄出去：  [箱子A]  [箱子B]  [箱子C]

对方收到：  一堆连在一起的箱子 —— 看不出哪个是哪个的边界
```

**TCP 就是这样一条「传送带」：它只保证东西按顺序送到，但不管你寄了几件。**

所以你要在每个箱子外面贴一张标签：

```
[标签:100] [箱子A · 100 字节] [标签:50] [箱子B · 50 字节] ...
```

**这个"标签"就是「长度前缀」。** 对面收到后：

```
1. 先读 4 个字节 → 这是个数字，代表"下一个箱子有多重"
2. 按这个数字切出那么多字节 → 这就是一个完整的箱子
3. 剩下的继续重复
```

**这一步做的，就是这件事。**

### 为什么不用「\n 分隔」？

| 方案 | 问题 |
|---|---|
| 用 `\n` 分隔 | 如果**消息内容本身包含 `\n`**（二进制数据里很常见），就切错了 |
| **用长度前缀** ✅ | 对任意字节都安全，不管内容是什么 |

> **答辩标准答案**：TCP 是字节流，没有消息边界。用长度前缀而不是分隔符，
> 是因为二进制载荷中可能出现任意字节，用分隔符必须转义，既增加体积又容易出错。

## 2. 核心只有两个函数

### ① `pack_frame` —— 贴标签（打包）

```python
def pack_frame(payload: bytes) -> bytes:
    return HEADER.pack(len(payload)) + payload
```

**翻译成人话**：

```
取载荷的长度（比如 3）→ 变成 4 个字节（00 00 00 03）
→ 拼在载荷前面 → 返回
```

**就这一行。** 例如 `pack_frame(b"abc")` 得到：

```
00 00 00 03  61 62 63
└─ 长度=3 ─┘ └─ abc ─┘
```

> `HEADER = struct.Struct("!I")` 里的 `!I` 意思是：
> **`!` = 大端序（网络字节序，全世界的机器都约定的顺序）**
> **`I` = 4 字节无符号整数**
>
> **这一条必须记住** —— 答辩问「长度怎么编码的」，答案就是「4 字节大端 uint32」。

---

### ② `recv_exact` —— 按标签取货（精确读满 N 字节）

```python
def recv_exact(sock, n):
    if n == 0:
        return b""

    chunks = []
    remaining = n
    while remaining > 0:
        chunk = sock.recv(remaining)      # ① 最多读 remaining 字节
        if not chunk:                    # ② 对方关闭了
            if remaining == n:
                return None              #   一个字节都没读到 = 正常断开
            raise ProtocolError(...)     #   读到一半才断开 = 帧被截断
        chunks.append(chunk)
        remaining -= len(chunk)          # ③ 记下还差多少
    return b"".join(chunks)
```

**为什么要写成循环？这是整个 TCP 编程里唯一的坑：**

```
你：recv(10)    意思是"给我最多 10 字节"
TCP：给你 3 字节  ← 不保证给满！！！

你只能：再 recv(7)
TCP：给你 7 字节  ✓ 凑满 10 字节了
```

**这就是「半包」的来源。** 不是 bug，是 TCP 的正常行为。

> **答辩标准答案**：`recv(n)` 只保证「最多返回 n 字节」，
> 网络分段、内核缓冲区都会导致提前返回。所以要循环累加，直到凑够需要的字节数。

## 3. 完整流程（一张图看懂）

```
发送方：
    payload = b"hello"
    pack_frame → [00 00 00 05][h e l l o]
    sendall    → 塞进内核缓冲区

网络（可能拆成任意碎片）

接收方：
    recv_frame(sock):
        ├─ recv_exact(4)      → 读满 4 字节 → 得到 length = 5
        ├─ 检查 5 是否超过上限  → 防止对方报个 4GB 把内存吃光
        └─ recv_exact(5)      → 读满 5 字节 → 得到 b"hello"
```

**`recv_frame` 就是这三步。** 没有别的。

## 4. 代码分三层 —— 你只需要懂第一层

| 层 | 内容 | 行数占比 | 你要懂的程度 |

| 🟢 **核心逻辑** | `pack_frame` / `recv_frame` / `while` 循环 | 约 30% | **必须能自己讲出来** |
| 🟡 **防御性代码** | 长度超限检查、截断检测、`ProtocolError` | 约 50% | 知道「为什么要有」即可 |
| ⚪ **语法糖** | 类型注解、`from __future__` | 约 20% | **完全可以跳过** |

### 🟡 防御性代码清单（知道用意就行，不用背）

| 代码 | 防的是什么 |
|---|---|
| `if len(payload) > MAX_PAYLOAD: raise` | 自己发的包太大 |
| `if length > MAX_PAYLOAD: raise` | **对方说自己有 4GB** → 不检查就会按这个数字分配内存，**内存爆掉** |
| `if not chunk` + `remaining == n` | 区分「正常断开」和「读到一半断开」 |
| `if payload is None: raise` | 帧头读到了，载荷却没读完 |

> **这类代码在答辩时是加分项** —— 可以主动说：
> 「协议必须防御恶意输入。如果我不检查长度就按对方说的分配内存，
> 一个 `length=4GB` 的报文就能让服务器崩掉。」

## 5. 这些语法你可以**完全跳过**

看到就跳过，不影响你理解任何逻辑：

| 语法 | 是什么 | 为什么可以跳过 |
|---|---|---|
| `from __future__ import annotations` | 让类型注解延迟求值 | 纯粹是版本兼容技巧 |
| `payload: bytes` / `-> bytes` | 类型注解 | **只是给人看的提示**，运行时不起作用 |
| `bytes \| None` | 表示「可能是 bytes，也可能是 None」 | 同上 |
| `list[bytes]` | 同上 | 同上 |
| `class ProtocolError(Exception)` | 自定义异常类型 | 知道"它是个错误"就够了 |

> **重点**：类型注解对程序**没有任何行为影响**，删掉也能跑。
> 它只是给编辑器和你自己看的说明。

## 6. 测试文件在干什么（152 行，但只做一件事）

`tests/test_framing.py` 里有一个 `FakeSocket`，它**假装自己是 socket**，但由你控制"每次返回多少字节"。

```python
sock = FakeSocket([frame[:split], frame[split:]])
#                   ↑ 前半段      ↑ 后半段
# 这就是人为制造「半包」
```

**为什么要假 socket**：真实网络的字节到达方式是内核决定的，**没法稳定复现半包**。
用假的就能精确构造。

| 测试名 | 验证什么 |
|---|---|
| `test_empty_payload` | 长度 0 的帧合法 |
| `test_sticky_two_frames` | 两条粘在一起，能一条条读出来 |
| `test_split_at_every_byte` | **在每个字节位置切开都能还原**（最狠的一个） |
| `test_one_byte_at_a_time` | 每次只给 1 字节也能拼回来 |
| `test_oversized_length_rejected` | 报超大长度时，**读完帧头就报错，不分配内存** |
| `test_clean_eof_returns_none` | 正常断开返回 `None`，不抛异常 |

> **答辩可以说**：「我用假 socket 精确构造半包和粘包，
> 覆盖了 15 个边界用例，包括逐字节切分和超大长度攻击。」

## 8. 自测：能不能用自己的话说出来？

**合上笔记，试着回答这 5 题。答得出 4 题，这一步就过关了。**

<details>
<summary>① 为什么要在消息前面加长度？</summary>

因为 TCP 是字节流，没有消息边界。一次 `recv` 可能拿到半条、一条或好几条消息，
必须靠长度才能切出完整的消息。

</details>

<details>
<summary>② `recv(10)` 一定返回 10 字节吗？</summary>

不一定。它只保证「最多 10 字节」。网络分段会导致提前返回，
所以要循环累加直到凑够。

</details>

<details>
<summary>③ 为什么不用 `\n` 分隔？</summary>

二进制载荷里可能出现 `\n`，会切错。用分隔符就必须转义，增加体积和复杂度。
长度前缀对任意字节都安全。

</details>

<details>
<summary>④ 为什么读到长度后要先检查 MAX_PAYLOAD？</summary>

防止对方报一个超大长度（比如 4GB），服务端按这个数字分配内存会被打爆。
**这是防攻击，不是防 bug。**

</details>

<details>
<summary>⑤ 对端正常关闭时，`recv_frame` 返回什么？</summary>

返回 `None`（表示干净的断开），而不是抛异常。
如果读到一半才断开，说明帧被截断，才抛 `ProtocolError`。

</details>

```
贴着标签的传送带：
  每个包裹标好重量（长度前缀）
```
