## 0. 一句话

E1 不是比“谁写代码更快”，而是回答一个协议问题：

> **同一份快照，二进制发和 JSON 发，体积、编码时间差多少？在目标规模下还发不发得出去？**

---

## 1. 这步解决什么问题

把快照想成同一车货：

- 二进制是**按固定格子装箱**：每个字段占几字节是提前定死的，箱子外面不用写“这是什么”。
- JSON 是**每件货都贴一张标签**：`{"i":1,"x":100,...}`，字段名要重复写，收货人还得先读标签。

E1 要量的是：**换一种装箱方式，到底多占多少地方、多花多少时间**。

但只拿“我们写的二进制”去比“随手写的 JSON”是不公平的，所以实验里多了一个 `binary_fast`：

- `binary`：逐条目 `struct.pack` 再拼接，是协议标准写法。
- `binary_fast`：**同一个协议、产物逐字节相同**，只是整帧只调一次 `struct.pack`，用缓存好的格式串。
- `json`：短键名、去空格、`ensure_ascii=False`，是“认真写的 JSON”。

这样就能把两件事分开：

- `binary` vs `json` → **协议形式**的差异；
- `binary` vs `binary_fast` → **实现方式**的差异。

没有 `binary_fast`，别人可以说“JSON 慢是因为你二进制写得好、JSON 写得烂”，结论就站不住。

---

## 2. 实验怎么设计的

| 项 | 设置 |
|---|---|
| 自变量 1 | 编码：`binary` / `binary_fast` / `json` |
| 自变量 2 | 同屏实体：30/200、100/800、150/1200、250/2000 |
| 控制变量 | 4 玩家、20 Hz、无网络损伤、固定 seed、ramp 4/s、每档 2 轮 |
| 因变量 | 快照字节数、`encode_ms`、`ser_ms`、`tick_ms`、单核占用、下行带宽 |
| 热身 | 每轮开头 10 秒丢掉（进程刚起、客户端没连满） |
| 无效行 | `client_count == 0` 的行不统计（服务端空转） |

一共 **4 档 × 3 编码 × 2 轮 = 24 轮**，总耗时约 74 分钟。

**公平性靠代码锁，不靠嘴说：**

- 三种编码吃的是同一份 `Snapshot`；
- JSON 的计时包含“建 dict + dumps + encode”全过程；
- 二进制包含“读属性 + pack”全过程；
- 往返测试断言 JSON 解出来的实体和二进制完全相等；
- JSON 不加二进制才有的值域校验，也不拿全字段名去比。

## 3. 结果：三条就够

### 3.1 JSON 在最大规模下不是“慢”，是**发不出去**

`E1-e250-b2000-json` 两轮都失败，报错完全一样：

```text
ProtocolError: 载荷超限：89538 B > 65536 B
```

- 协议帧层上限 `MAX_PAYLOAD = 64 KiB`；
- JSON 在 250/2000 下是 **89 538 B**，超限 36.6 %；
- 同规模二进制只有 **18 307 B**，只到上限的 28 %。

所以 E1 的达标数是 **22/24**。那 2 轮失败不是“没跑完”，而是**最重要的结论**：目标规模下 JSON 路径不可用。

### 3.2 体积稳定差 4.7 倍

| 档位 | 二进制 | JSON | 倍数 |
|---|---|---|---|
| 30/200 | 1 927 B | 9 076 B | 4.71× |
| 100/800 | 7 357 B | 34 788 B | 4.73× |
| 150/1200 | 11 007 B | 52 097 B | 4.73× |
| 250/2000 | 18 307 B | ❌ 超限 | — |

三档都稳定在 4.7 倍，说明这是**结构性开销**，不是某次没写好。

### 3.3 编码快 4~5 倍，但总 tick 只差 5~18 %

| 档位 | 二进制编码 ms | JSON 编码 ms | 倍数 |
|---|---|---|---|
| 30/200 | 0.0639 | 0.2493 | 3.90× |
| 100/800 | 0.1608 | 0.6396 | 3.98× |
| 150/1200 | 0.2164 | 1.0569 | 4.89× |

但编码只占 tick 的 1.2 %~6.4 %（二进制），JSON 也只占 8.5 %~21.2 %。  
**因为 E9 已经证明碰撞判定才是大头。**

所以结论要这样写：

> **打包方式不是瓶颈；二进制的优势是结构性的**——体积小 4.7 倍、编码快 4~5 倍，而且大规格下仍能发出去。

## 4. 踩过的坑（答辩可讲）

### 4.1 CSV 表头 22 列，数据行 23 列

E1 第一次跑完，`snapshot_bytes` 只有 48 B、`encode_ms` 是空的——**整列错位**。

根因：`_open_for_append()` 只在文件不存在时写表头。文件里已有 E9 的旧 22 列表头，新加的 `encode_ms` 没写进表头，`DictWriter` 按 `fieldnames` 顺序写，于是：

- 数据行多一个值；
- 表头少一个名字；
- **不报错、不崩溃，但数据全错。**

修法：

1. 写 `tools/migrate_metrics.py`，按列名迁移旧行，缺列补空；
2. 表头不匹配直接抛 `MetricsSchemaError`，宁可在开跑前失败；
3. 测试锁住“表头字段 = 写入字段”。

**教训：append-only CSV + 加列，一定要在开跑前验表头。**

### 4.2 其余局限

- 本机 loopback，RTT≈0：E1 只看服务端编码开销和体积，不受 RTT 影响。
- 带宽是服务端自计的应用层字节，不是抓包值；抓包验证是 E7。
- 不含道具，和早期纸面估算口径不同，所以不能和 5.6 倍旧数直接比。

## 6. 自测题（先自己说，再看答案）

1. **为什么要有 `binary_fast`？**  
   答：把“协议形式”和“实现方式”分开。否则 JSON 慢可以被解释成“你二进制写得好、JSON 写得烂”。

2. **JSON 在 250/2000 为什么失败？**  
   答：载荷 89 538 B，超过帧层 64 KiB 上限，`ProtocolError`，tick 循环崩溃；两轮都复现。

3. **二进制只比 JSON 小 4.7 倍，为什么说 JSON“不可用”？**  
   答：因为在目标最大规模下它**超过协议上限**，不是单纯慢；同规模二进制只到上限 28 %。

4. **编码快 4~5 倍，为什么总 tick 只差 5~18 %？**  
   答：编码只占 tick 的一小部分，碰撞判定占大头；优化编码对总耗时影响有限。

5. **22/24 算失败还是成功？**  
   答：算成功，而且那 2 轮失败是结论的一部分：JSON 路径在最大规模下被协议上限否决。

---

## 7. 答辩话术

> E1 比较二进制和 JSON 两种快照编码。为了排除“实现水平”的干扰，我加了一个 `binary_fast` 变体：协议和产物与标准二进制逐字节相同，只是减少 `struct.pack` 调用。结果是：二进制体积约为 JSON 的 1/4.7，编码快 4~5 倍；在 250 敌机、2000 子弹时，JSON 载荷 89 538 字节，超过 64 KiB 帧上限，两轮都发不出去，而二进制只有 18 307 字节。另一方面，编码只占 tick 的很小一部分，所以总 tick 只差 5~18 %——这说明**瓶颈不在打包，而在游戏逻辑侧**，二进制的优势主要是结构性的体积和可发送性。
