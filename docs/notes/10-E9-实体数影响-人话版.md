## 0. 一句话

E9 回答的是本课题最核心的问题：

> **同屏实体越来越多时，到底是通信先扛不住，还是游戏逻辑先扛不住？**

答案是：**通信占比一路下降，瓶颈在碰撞判定的 O(子弹×敌机)。**

---

## 1. 这步解决什么问题

直觉上，实体越多，要发的字节越多，通信应该越来越贵。  
但“通信贵不贵”不能只看总字节数，要看它**占一帧时间的比例**。

如果实体涨 35 倍，通信只涨 33 倍，而碰撞涨几百倍，那通信的**占比**反而会下降。  
E9 就是把这个“占比”量出来，找到：

- 50 % 单核舒适线在哪里；
- 设计目标 30 敌机/200 子弹处还有多少余量；
- 继续加实体时，应该先优化哪一层。

---

## 2. 实验怎么设计的

| 项 | 设置 |
|---|---|
| 自变量 | 9 档实体：敌机 10/20/30/50/80/100/150/200/250，子弹 50/100/200/400/600/800/1200/1600/2000 |
| 控制变量 | 4 玩家、20 Hz、二进制编码、无网络损伤、固定 seed、ramp 4/s |
| 因变量 | `tick_ms`（拆成四段）、单核占用、快照字节、下行带宽、命中数 |
| 每档轮数 | 2 轮，每轮 180 秒 |
| 热身 | 每轮开头 10 秒丢掉 |
| 无效行 | `client_count == 0` 的行不统计 |
| 总数据 | 18 轮，3313 行 |

前 6 档是原计划；后 3 档是**追加的**，因为预实验发现 100/800 时单核才约 11 %，碰不到 50 % 舒适线，必须加档才能出拐点。

### 四段计时

一帧被拆成：

```text
sim_ms + collision_ms + ser_ms + net_ms ≡ tick_ms
```

- sim：移动、剔除、补足；
- collision：朴素 O(子弹×敌机)；
- ser：序列化；
- net：逐客户端广播。

这样图 6-20 才能画成 100 % 堆叠柱，答辩时能回答“有没有漏计”。

## 3. 结果：三句话

### 3.1 通信占比从 73.0 % 降到 6.7 %

| 档位 | tick ms | 碰撞 ms | 通信合计 ms | 通信占比 |
|---|---|---|---|---|
| 10/50 | 0.366 | 0.047 | 0.267 | **73.0 %** |
| 30/200 | 1.016 | 0.446 | 0.433 | 42.7 % |
| 100/800 | 5.738 | 4.493 | 0.842 | 14.7 % |
| 250/2000 | 30.797 | 27.825 | 2.057 | **6.7 %** |

实体越多，通信的**绝对耗时**也在涨，但涨得比碰撞慢得多，所以占比被稀释。

**结论：通信层是可扩展的，瓶颈在游戏逻辑侧的算法复杂度。**

### 3.2 广播耗时几乎不随报文变大

快照从 547 B 涨到 18 307 B（33.5 倍），广播耗时只从 0.150 ms 涨到 0.182 ms。

原因：内核发送缓冲区没饱和时 `await drain()` 立即返回，广播成本主要是“每个客户端一次 write”的固定开销，近似 **O(客户端数)**，与报文大小关系不大。

> 如果缓冲区饱和，就会退化——那正是 E4/E5 要测的弱网情形。

### 3.3 50 % 舒适线在 200/1600 ~ 250/2000 之间

| 档位 | 单核占用 |
|---|---|
| 30/200（设计目标） | **2.0 %** |
| 100/800 | 10.5 % |
| 200/1600 | 39.2 % |
| 250/2000 | **61.0 %** |

设计目标 30/200 只有 2.0 %，距 50 ms 预算有 49 倍余量。  
D-011 的“敌机 ≤ 30、子弹 ≤ 300”因此有了实测支持。

## 4. 数据可信吗

- **18/18 轮全部达标**：4/4 连接、机器人 `errors=0`、无崩溃标记、每轮 184 行指标。
- 每轮快照数 14 397~14 400，理论值 4×20×180=14 400，吻合。
- `tick_ms × 20` 和 psutil 单核占用交叉验证：高负载 98 %~99 % 吻合。
- 快照公式 `57 + 9E + 8B` 九档逐字节吻合，偏差 0 B。

### 必须如实说的一处干扰

第 1 轮 `E9-e10-b50-r1` 最后约 20 秒，在同一台机器上跑了 218 个单元测试（约 3.5 秒满载一个核）。

- 影响窗口约 11 %，且已剔除前 10 秒热身；
- 该轮与 r2 的 tick 偏差 0.9 %，CPU 均值仅 0.0 %，未造成可观测偏差；
- 数据保留，但教训是：**跑批时不要在同一台机器上跑测试。**

### 局限

- 本机 loopback，RTT≈0，测不到真实网络延迟；E4/E5 要上 VMnet1+netem。
- 低负载档 CPU 读数被调度粒度量化，以 `tick_ms` 为准。
- 碰撞是占位实现（只判定不生效），敌机无 AI；第 11 步换真实逻辑后绝对耗时会变，但通信部分不受影响。

## 6. 自测题（先自己说，再看答案）

1. **为什么实体越多，通信占比反而下降？**  
   答：通信近似线性涨，碰撞是 O(子弹×敌机) 超线性涨，分母涨得更快，占比被稀释。

2. **广播耗时为什么几乎不随报文变大？**  
   答：内核发送缓冲区未饱和，`drain()` 立即返回，成本主要是每客户端一次 write 的固定开销。

3. **30/200 下单核 2.0 % 说明什么？**  
   答：设计目标规模离 50 ms 预算和 50 % 舒适线都很远，余量约 49 倍。

4. **50 % 舒适线的拐点在哪？**  
   答：200/1600 的 39.2 % 和 250/2000 的 61.0 % 之间，插值约 215/1720。

5. **E9 最重要的结论是什么？**  
   答：通信层不是瓶颈，瓶颈在碰撞判定；继续扩容应优化游戏逻辑复杂度，而不是协议本身。

---

## 7. 答辩话术

> E9 测了 9 档同屏实体，每档 2 轮、每轮 180 秒，共 3313 行数据。一帧被拆成模拟、碰撞、序列化、广播四段，四段之和严格等于 tick 总耗时。结果有三个：第一，通信占比从 10/50 的 73.0 % 降到 250/2000 的 6.7 %，说明通信层可扩展，瓶颈在碰撞的 O(子弹×敌机)；第二，快照从 547 B 涨到 18 307 B，广播耗时几乎不变，因为发送缓冲区未饱和；第三，50 % 单核舒适线在 200/1600 到 250/2000 之间，而设计目标 30/200 只有 2.0 %，余量充足。这为“敌机 ≤ 30、子弹 ≤ 300”的约束提供了实测依据。
