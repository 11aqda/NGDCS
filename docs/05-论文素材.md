# 1. 可直接引用的设计论点（「为什么这么设计 / 没选什么」）

> 这一节是答辩的核心弹药。每条都写清了**替代方案为什么被否**——
> 只讲"我选了什么"没有说服力，讲清"我否了什么、为什么否"才是设计。

## 1.1 协议层

| # | 论点 | 替代方案（已否决） | 来源 |
|---|---|---|---|
| 1 | **长度前缀划消息边界**：二进制安全，对任意字节成立 | 分隔符（`\n`/`\0`）→ 载荷里出现分隔符要转义，体积与复杂度都上升；定长包 → 可变载荷浪费带宽 | D-017 |
| 2 | **4 字节长度**：上限 4 GB，扩展余量大 | 2 字节 → 上限 65535 B，余量小；且加 type/seq 后帧头本身就超 4 字节 | D-017 |
| 3 | **12 字节帧头**（magic/version/type/seq/length）：一条连接跑多种消息 | 只有长度 → 无法区分消息、无法关联响应；8 字节（magic+length）→ 丢掉 version/type/seq | D-019 |
| 4 | **magic + version 在帧层快速失败**：连错端口 / 版本不匹配时立刻拒绝，不把垃圾当消息解析 | 只在业务层校验 → 错误报文要先解析到一半才发现 | D-019 |
| 5 | **`seq` 一举三得**：请求-响应关联（算 RTT）、丢包检测、防重放 | 无 seq → 心跳无法算 RTT、响应无法配对 | D-019 |
| 6 | **禁用浮点**：定点整数保证跨平台一致 + 更省字节（双精度 8 B） | 浮点 → 平台/版本间舍入差异，破坏可复现性 | 02 §4.3 |
| 7 | **角度 0° = 正上方、顺时针**：竖版射击游戏"向上"是主方向，最常见的两个方向恰好落在 0 和 128 | 数学习惯的 0° = 正右 → 玩家子弹要写 192，反直觉易错 | 02 §4.5、D-024 |
| 8 | **二进制 vs JSON**：体积差约 5.6 倍 | JSON → 体积大、解析慢；作为 E1 的对照组保留而非丢弃 | D-019、01 §4.1 |
| 9 | **32 位时间戳 + 无符号差值**：`(now - sent) & 0xFFFFFFFF` 天然免疫回绕 | 无符号直接相减 → 回绕后算出负数 | D-023 |

> **⭐ 可以单独成段的点**：`02 §5.3` 的**「状态同步 vs 事件同步」**——
> 快照里已经有 `wave` 字段能表达"现在是第 3 波"，但客户端还需要知道
> "**刚刚进入**第 3 波"这个**瞬间**才能播动画。"值是多少"和"刚刚变成这个值"是两件事。
> 本协议两者都用：状态用 `S_SNAPSHOT`，事件用 `S_WAVE_START` / `S_BOSS_SPAWN` / `S_PLAYER_DOWN`。
> **文档明确标注"这是一个可以在论文里展开讨论的设计点"。**

# 2. 已实测的量化结论

## 2.1 TCP 基础性质（第 1~2 步）✅

| 结论 | 数据 | 来源 |
|---|---|---|
| **TCP 是字节流，没有消息边界** | 发送 1100 B 时，客户端一次 `recv(1024)` 只拿到 **1024 B** | PROGRESS §2.6 |
| 回环 RTT | **0.03 ~ 0.14 ms** | PROGRESS §2.6 |
| **粘包**：两条帧一次 `sendall` | 正确拆成 `b'one'` / `b'two'` | PROGRESS §2.7 |
| **半包**：先发帧头、隔 0.3 s 再发载荷 | 正确还原 `b'hello-half'` | PROGRESS §2.7 |
| **超大包防护**：声明 1,000,000 B > 64 KiB | 服务端抛 `ProtocolError` 并断开，客户端收到 EOF | PROGRESS §2.7 |
| 帧头开销 | 空载荷时帧头 12 B；**输入包载荷仅 1 B，帧头是它的 12 倍** | 02 §4.1 |

## 2.2 快照体积（✅ 逐字节核对通过）

| 构成 | 字节 |
|---|---|
| 帧头 | 12 B |
| 快照头 | 13 B |
| 玩家条目 | 11 B × N |
| 敌机条目 | 9 B × N |
| 子弹条目 | 8 B × N |
| 道具条目 | 7 B × N |

**实测核对（4 人）**：

| 场景 | 公式 | 实测 |
|---|---|---|
| 30 敌机 + 200 子弹 | `13 + 4×11 + 30×9 + 200×8 = `**1927 B** | ✅ **1927 B** |
| 100 敌机 + 800 子弹 | `13 + 4×11 + 100×9 + 800×8 = `**7357 B** | ✅ **7357 B** |

- 含 12 B 帧头：1939 B / 7369 B
- @20 Hz 下行：**38.8 KB/s** 与 **147.4 KB/s**（每客户端）
- `01 §7.4` 的设计目标 **1974 B** 比我们的 1939 B 多 35 B —— 那是**5 个道具**的体积，别混淆

**带宽线性度** ✅：实体数 **3.86 倍** → 下行带宽 **3.84 倍**（图 6-18 要验证的就是这个）

> ⭐ **一个协议设计的代价（可作为讨论点）**：子弹条目**没有唯一 ID**（只有 `owner_id`），
> 所以客户端**无法按实体逐帧匹配子弹，也就不能对子弹做插值**。
> 省下 2 B/颗 × 200 颗 = **400 B/帧**，约占快照 **20%**。
> 玩家与敌机都有 id，不受影响。这是"省带宽"与"可插值"之间的真实取舍。

| 场景 | 连接 | 快照 | 间隔 p50 | 间隔 p95 | 错误 |

## 2.5 CPU 测量本身的校验 ✅

指标定义：**单核占用 = ΔCPU 秒数 ÷ Δ墙钟秒数 × 100**（100 % = 一个核跑满），
与 `D-011` 的「8.9 % 单核」「87.3 % 单核极限」同量纲。

| 人为负载 | 读出的值 |
|---|---|
| 忙等 0.5 s / 秒 | **49.95 %** |
| 忙等 0.1 s / 秒 | **9.37 %** |
| 全程睡觉 | **0.0 %** |

> 量纲正确、精度优于 0.1 %。**这条可以写进"实验方法的可靠性验证"**。

> ⚠️ **2026-10-25 补充：低负载下的单秒读数不可信**
>
> 进程 CPU 时间是按**调度时钟**更新的（Windows 上约 15.6 ms 一跳）。
> 当服务端每秒只花约 20 ms CPU 时（30 敌机 + 200 子弹），
> 单行会读成 **0 % 或 1.56 %** —— 同一档位两轮的逐秒均值实测差 **66 %**（2.6 % vs 0.5 %）。
> 而同期 `tick_ms` 两轮只差 **1.5 %**（进程内 `perf_counter`，高精度）。
>
> **解法**：CSV 同时存**累计 CPU 秒数**，出图时用
> 「**首尾累计差 ÷ 首尾墙钟差**」算**整轮** CPU% —— 只有两个端点各带一次量化误差，
> 除以几分钟的时长后基本消失。修正后 100/800 两轮偏差 **7.3 %**，tick 偏差 0.5 %。
>
> **这一段本身就该写进论文的"实验方法"**：它说明为什么**不能直接对逐秒读数求平均**，
> 以及怎么用累计量消除量化误差。答辩被问"你的 CPU 数据准吗"，这是完整答案。

## 2.6 环境与网络（✅ 两轮实测，方法论价值高）

**第一轮：本机自连局域网 IP —— 测不到真实网络指标**

| 测试 | 结果 |
|---|---|
| `ping 127.0.0.1` / `ping 10.140.71.127` | 均 **< 1 ms** |
| 回声 RTT | **0.03 ~ 0.14 ms** |
| 向 `10.140.71.127` 传 16 MB | **1145.8 MB/s**，WLAN 网卡收发增量仅 **0.001 / 0.012 MB** |

→ **Windows 把发往本机地址的流量短路到回环**，根本没经过网卡。

**第二轮：VMware 桥接 WiFi（用户实测）**

| 测试 | 结果 |
|---|---|
| 桥接 + 校园网 | 虚拟机**拿不到 IPv4**（校园网拒绝虚拟机 MAC） |
| 桥接 + 手机热点：host → VM | **RTT = 0.00 ms，20/20 全成功** |
| host → 网关 `10.152.181.188` | **4.67 ms（1~6 ms）**；8000 B 包 **9.60 ms** |
| 加静态路由强制走网关 | 仍为 **0 ms** |

**关键推理（这段推理本身就是论文素材）**：
网关 RTT 4.67 ms、大包 9.60 ms → **说明 ping 本身有精度**，
所以 VM 的 0.00 ms 是**真 0**，不是"测不出来"；
改 L3 路由表仍然 0 ms → **VMware 桥接在 L2（链路层）直接截获，绕不过去**。

→ 最终方案：**VMware VMnet1 仅主机模式 + `tc netem` 内核态注入**（D-016）。

> **这段的方法论价值 > 结果本身**：它演示了"**如何证明一个测量结果是假的**"——
> 不是看到 0.00 ms 就说"网络很快"，而是先验证测量工具本身有精度（用网关做对照），
> 再逐层排除（改 L3 路由 → 仍为 0 → 确定在 L2 截获）。
> **答辩如果被问"你怎么知道你的数据是真的"，这就是答案。**

# 3. ⭐ 反直觉 / 有亮点的发现（答辩加分项）

按"容易被追问"的程度排序。

### 3.1 广播耗时与包大小几乎无关

**现象**（9 档实测）：快照从 **547 B 涨到 18 307 B（33.5 倍）**，
广播耗时只从 **0.150 → 0.182 ms**；中间 8 档在 0.137 ~ 0.182 ms 之间几乎水平。

**原因**：内核发送缓冲区**未饱和**时 `await writer.drain()` 立即返回。
所以广播成本主要是「每个客户端一次 write 调用」的固定开销，
**≈ O(客户端数)，与报文大小无关**。

**前提要说清**：缓冲区一旦饱和就会退化 —— 那正是 E4/E5 网络损伤实验要测的。

### 3.2 通信占比随实体数**下降**：73.0 % → 6.7 %

直觉上"实体越多、要传的字节越多、通信越贵"，
但实测**占比**从 **73.0 % 单调降到 6.7 %** —— 因为游戏逻辑是 O(子弹×敌机) 的
超线性增长（碰撞 0.047 → 27.825 ms，**592 倍**），而通信是近似线性的，
占比自然被逻辑侧稀释。

**这个结论直接支撑本课题的题目**：《数据通信系统》要证明的不是"网络很快"，
而是"**通信层不是瓶颈，且可扩展**"。它同时是**图 6-20** 存在的全部意义。

> 附带的量化边界：单核占用跨过 50 % 舒适线的拐点约在 **215 敌机 / 1720 子弹**，
> 可作为第 11 步关卡编排的上限参考。

### 3.3 「只判定不生效」是一种**测量夹具**设计

为了让实验的自变量（同屏实体数）恒定，碰撞检测**只计算命中、不产生任何效果**。

**为什么值得写**：这是"**为了测量而刻意退化功能**"的工程决策。
如果命中就删实体，数量就会波动；"删了立刻补足"又等于把命中效果当场抹平。
**测量夹具的设计本身就是实验方法的一部分**，而且仍然统计命中数来证明循环真在计算。

### 3.4 心跳回显式设计：**不需要两端时钟同步**

服务端把 `client_time` **原样抄回**，RTT 完全由客户端本地计算：

```
RTT = (本地现在读数 - 我发出去时的读数) & 0xFFFFFFFF
```

**为什么值得写**：如果改成"服务端发自己的时间、客户端拿本地时间相减"，
两端的**钟差**（可能几秒）会直接算进 RTT。**这是一个很典型的分布式测量陷阱。**

### 3.5 帧率会**量化**定频上报

客户端用 `next_input_at = now + 0.05` 时，服务端实测只收到 **17 次/秒**；
改成 `next_input_at += 0.05`（deadline 累加）后稳定 **20 次/秒**。

**原因**：60 fps 下每帧 16.7 ms，而 50 ms 不是 16.7 ms 的整数倍，
"下一帧才发"导致平均间隔被拉长到约 55 ms。

**为什么值得写**：这是"**定时器不能靠'当前时间 + 间隔'推进**"的具体反例，
而且有前后对照数据。服务端 `tick_loop` 用的是同一个正确模式（deadline 累加）。

### 3.6 静默死掉的协程：**asyncio 不会替你报错**

**现象**：一个漏掉的 import 让 `tick_loop` 在第一个 tick 抛 `NameError` 后静静死掉。
服务端**照常监听、照常打印 "player joined"**，但客户端再也收不到一帧快照：

```
机器人：clients_connected: 4、snapshots: 0、errors: 0
```

**原因**：asyncio 的未取回异常**只在任务对象被垃圾回收时**才打印，
而 `main()` 一直持有 `tick_task` 引用 —— 进程活着时什么都不显示。

**为什么值得写**：这是异步编程里很典型、但文档很少强调的坑。
对**无人值守跑 3 分钟**的性能实验，后果是"跑完了但全是 0 的数据"。

### 3.7 协议文档的一个真实漏洞：角度基准没定义

`02 §4.3` 写了"角度 uint8，0~255 映射到 0~360°"，但**没定义 0° 指向哪个方向**。
子弹必须有方向 —— 这是**设计文档在实现阶段才暴露的不完备**，
补充为"0° = 正上、顺时针"并说明了为什么不沿用数学习惯。

**为什么值得写**：说明"协议设计需要经过实现验证才能闭合"，
也体现了"值域定义 ≠ 语义定义"（`D-012` 的坐标值域问题是同一类）。
