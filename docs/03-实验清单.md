## 3. 指标定义

**所有指标必须有精确定义，否则数据不可比。**

| 指标 | 符号 | 定义 | 采集端 |
|---|---|---|---|
| 往返延迟 | RTT | 心跳包发出到收到 ACK 的时间差 | 客户端 |
| 下行带宽 | BW↓ | 每客户端每秒接收字节数 | 客户端 |
| 上行带宽 | BW↑ | 每客户端每秒发送字节数 | 服务端 |
| 包率 | PPS | 每秒报文数 | 两端 |
| 平均包大小 | — | 总字节数 ÷ 报文数 | 两端 |
| 逻辑帧耗时 | tick_ms | 服务端一次世界更新的耗时 | 服务端 |
| CPU 占用 | CPU% | 进程 CPU 百分比 | 两端 |
| 内存占用 | RSS | 进程常驻内存 | 两端 |
| 序列化耗时 | ser_ms | 编码 + 解码总耗时 | 两端 |
| **插值误差** | err_px | 客户端渲染位置与最近权威位置的欧氏距离 | 客户端 |
| 丢包率 | loss% | 序号不连续的比例 | 客户端 |
| 断线检测延迟 | detect_s | 客户端断开到服务端标记断线的时间 | 服务端 |

> **插值误差**是本项目最有说服力的指标 —— 它直接量化「网络变差时玩家看到的东西有多不准」。

## 4. 数据采集方案

### 4.1 服务端埋点

**每 `interval` 秒（默认 5 s）聚合一次，追加写入 CSV：**

```
server_metrics.csv
timestamp,client_count,tick_ms_avg,tick_ms_max,cpu_percent,mem_mb,
packets_out,bytes_out,packets_in,bytes_in,ser_ms_avg,room_count
```

**场景标记**：每次实验开始时写一行场景信息，便于后续切分数据。

```
server_scenario.csv
timestamp,scenario_id,encoder,tick_rate,client_count,inject_loss,inject_delay
```

### 4.2 客户端埋点

```
client_metrics.csv
timestamp,rtt_ms,packets_in,bytes_in,frame_ms,interp_err_px,pos_desync_px
```

### 4.3 设计原则

| 原则 | 原因 |
|---|---|
| **追加写，不覆盖** | 一次实验可能分段跑，不能丢历史 |
| **每行带 `scenario_id`** | 便于按实验条件切分数据 |
| **采集本身的开销要可忽略** | 聚合后写，不是每包都写磁盘 |
| **时间戳用单调时钟** | 避免系统时间被调整导致数据错乱 |

## 5. 实验详细设计

### E1 · 协议编码对比（二进制 vs JSON）

- **目的**：量化自定义二进制协议在体积与 CPU 上的优势
- **自变量**：`encoder = binary | json`
- **控制变量**：**4 人 + 30 敌机 + 200 子弹**、tick 率 20 Hz、无网络损伤
- **因变量**：平均包大小、BW↓、序列化耗时、CPU%
- **步骤**：
  1. 配置 `encoder=binary`，跑 5 分钟，采集
  2. 配置 `encoder=json`，同条件跑 5 分钟
  3. 对比
- **预期结果**（依据 `01-系统架构.md §7.4` 的推算）：

  | 编码 | 快照大小 | 带宽 @20Hz |
  |---|---|---|
  | 二进制 | ≈ **1974 B** | ≈ **39.5 KB/s** |
  | JSON | ≈ **11000 B** | ≈ **220 KB/s** |
  | **比值** | **约 5.6 倍** | **约 5.6 倍** |

  CPU 差异同样明显 —— JSON 需要在服务端把 200+ 实体逐个拼字符串。
- **产出图表**：
  - 图 6-1：两种编码的**平均包大小对比**（柱状图）
  - 图 6-2：**序列化耗时对比**（柱状图）
  - 图 6-3：**CPU 占用随实体数变化**（折线图）

### E3 · IO 模型对比（事件驱动 vs 每连接一线程）· 可选

- **目的**：验证事件驱动在高并发下的资源效率
- **自变量**：`io_model = asyncio | thread_per_connection`
- **控制变量**：同 E2
- **因变量**：CPU%、内存、最大稳定连接数
- **实现要求**：需要额外实现一个线程版服务端核心（**仅替换网络层，业务层复用**）
- **成本提示**：约 8~10 小时。**若时间紧张可只做理论对比，不做实现**

- **目的**：找带宽与平滑度的平衡点
- **自变量**：tick 率 = 10 / 15 / 20 / 30 Hz
- **控制变量**：8 人、二进制、无损伤
- **因变量**：BW↓、插值误差、客户端帧率
- **产出图表**：
  - 图 6-11：**tick 率 vs 带宽**（折线图）
  - 图 6-12：**tick 率 vs 插值误差**（折线图，双轴叠加）
- **论文价值**：给出「20 Hz 是性价比最优点」的数据支撑

### E6 · 快照策略对比（全量 vs 增量 vs 确定性生成）· 可选

- **目的**：验证不同同步策略的带宽收益与实现代价
- **自变量**：`snapshot_mode = full | delta | deterministic`
- **控制变量**：4 人 + 30 敌机、tick 率 20 Hz、无损伤
- **因变量**：BW↓、CPU%（增量计算与确定性校验都有开销）
- **三种策略说明**：

  | 策略 | 做法 | 理论带宽 |
  |---|---|---|
  | **full**（默认） | 每帧广播全部实体 | ≈ 39.5 KB/s |
  | **delta** | 只广播发生变化的实体 | 视移动比例而定 |
  | **deterministic** | 子弹不广播，只同步「何时何地发射了哪种弹幕」，各客户端本地推算 | 子弹部分几乎归零 |

- **注意**：子弹占快照的 **1600 / 1974 ≈ 81%**，所以 `deterministic` 的**理论上限收益极大**；
  但它要求浮点运算确定性一致，**跨平台会飘** —— 这正是要测/要讨论的结论
- **产出图表**：
  - 图 6-13：**三种策略的带宽对比**（柱状图）
  - 另出一张**实现复杂度 / 风险对比表**（非图表，直接写进正文）

> **本实验是"弹幕游戏"相对"简单移动游戏"的最大加分项** ——
> 只有子弹数量足够多，"确定性生成"这个优化方向才有讨论价值。

### E7 · 抓包验证

- **目的**：证明协议实现正确，且能被第三方工具解析
- **步骤**：
  1. Wireshark 在 Npcap 回环适配器 / VMnet1 接口抓包；或 Ubuntu 内 `tcpdump -w` 导出 pcap
  2. 过滤条件：`tcp.port == 9527`
  3. 用 `Follow TCP Stream` 展示原始字节流
  4. 对照 `02-协议设计.md` 逐字段标注帧头
  5. 验证粘包拆包：人为构造半包/粘包，看能否正确解析
  6. **验证"出屏即剔除"**：观察越界实体确实不再出现在报文中（见 D-012）
- **产出图表**：
  - 图 6-14：**抓包总览**（能看到 20 Hz 的稳定节拍）
  - 图 6-15：**单个快照报文的帧头与实体字段标注**
  - 图 6-16：**粘包 / 半包的解析对比**

### E8 · 断线检测时效

- **目的**：验证心跳超时机制的有效性
- **自变量**：心跳间隔 = 3 / 5 / 10 s
- **因变量**：断线检测延迟
- **步骤**：强制 kill 客户端进程，记录服务端标记断线的时间
- **产出**：表格（含理论值与实测值对比）

### E9 · ⭐ 实体数量对带宽与 CPU 的影响（**本项目核心实验**）

- **目的**：找出服务端单核的处理上限，为「同屏实体上限」提供数据依据（见 D-011）
- **自变量**：同屏实体数
  - 敌机数 = 10 / 20 / 30 / 50 / 80 / 100
  - 子弹数 = 50 / 100 / 200 / 400 / 600 / 800
- **控制变量**：4 人、二进制编码、20 Hz
- **因变量**：`tick_ms`、CPU%、快照字节数、BW↓
- **步骤**：
  1. 用机器人客户端 + 配置项制造指定的实体规模
  2. 每档稳定运行 3 分钟
  3. 记录 `tick_ms` 与 CPU
- **已知预估值**（来自基准测试，见 `01-系统架构.md §7.1`）：

  | 敌机 | 子弹 | ms/tick | CPU@20Hz |
  |---|---|---|---|
  | 30 | 200 | 0.45 | 8.9 % |
  | 50 | 400 | 1.21 | 24.1 % |
  | 80 | 600 | 2.72 | 54.4 % |
  | 100 | 800 | 4.37 | 87.3 % |

- **产出图表**：
  - 图 6-17：**实体数 vs 单帧耗时**（折线图，找拐点）
  - 图 6-18：**实体数 vs 带宽**（折线图，验证线性关系）
  - 图 6-19：**实体数 vs 单核占用**（折线图，标出 50% 舒适线）

- **论文价值**：这张图直接支撑「同屏敌机上限 = 30、子弹上限 = 300」的设计决策，
  是**设计 → 实测 → 反推约束**的完整闭环。

## 7. 实验记录模板

每次实验后填写，存于 `docs\experiments\`：

```markdown
## 实验：E1 协议编码对比
- 日期：2026-XX-XX
- 场景 ID：E1-binary-01
- 配置：encoder=binary, tick=20, players=4, enemies=30, bullets=200, loss=0, delay=0
- 时长：5 分钟
- 原始数据：data/E1-binary-01-server.csv, data/E1-binary-01-client.csv
- 关键结果：
  - 平均快照大小：1974 字节
  - 平均 BW↓：39.5 KB/s
  - 平均 CPU：10.2 %
- 异常/备注：无
- 图表：图 6-1（左柱）
```

**要求**：每个实验至少跑 **2 次**，取一致的结果；差异大要查明原因。

**注意**：记录时必须写明**实体构成**（玩家 / 敌机 / 子弹数），
否则不同实验的数据不可比 —— 这是本项目最容易出错的地方。
