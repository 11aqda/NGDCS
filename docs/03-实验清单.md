## 3. 指标定义

**所有指标必须有精确定义，否则数据不可比。**

| 指标 | 符号 | 定义 | 采集端 |
|---|---|---|---|
| 往返延迟 | RTT | 心跳包发出到收到 ACK 的时间差 | 客户端 |
| 下行带宽 | BW↓ | 每客户端每秒接收字节数 | 客户端 |
| 上行带宽 | BW↑ | 每客户端每秒发送字节数 | 服务端 |
| 包率 | PPS | 每秒报文数 | 两端 |
| 平均包大小 | — | 总字节数 ÷ 报文数 | 两端 |
| 逻辑帧耗时 | tick_ms | 服务端一次世界更新的耗时（**总**） | 服务端 |
| ├ 模拟 | sim_ms | 玩家输入移动 + 实体移动 / 出屏剔除 / 补足数量 | 服务端 |
| ├ 碰撞判定 | collision_ms | 朴素 O(子弹×敌机) 判定（**只判定不生效**） | 服务端 |
| ├ 序列化 | ser_ms | `pack_snapshot` 逐实体编码 | 服务端 |
| └ 广播发送 | net_ms | 逐客户端 `write` + `await drain` | 服务端 |
| 碰撞命中 | hits | 每 tick 判定命中的（子弹,敌机）对数 | 服务端 |
| CPU 占用 | CPU% | 进程 CPU 百分比（**单核**：100% = 一核跑满） | 两端 |
| 内存占用 | RSS | 进程常驻内存 | 两端 |
| 序列化耗时 | ser_ms | 编码 + 解码总耗时 | 两端 |
| **插值误差** | err_px | 客户端渲染位置与最近权威位置的欧氏距离 | 客户端 |
| 丢包率 | loss% | 序号不连续的比例 | 客户端 |
| 断线检测延迟 | detect_s | 客户端断开到服务端标记断线的时间 | 服务端 |

> **插值误差**是本项目最有说服力的指标 —— 它直接量化「网络变差时玩家看到的东西有多不准」。

> **2026-10-25 新增分段（tick 四段）**：只报一个 `tick_ms` 回答不了
> 「**瓶颈在游戏逻辑还是通信层**」，而这正是本课题的核心问题。
> 四段**严格相加等于 `tick_ms`**（计时点首尾相接、一次不多一次不少），
> 所以能画成 100% 堆叠图，不需要"其它"那一类。
> 约定：**逻辑 = sim + collision**，**通信 = ser + net**。

## 4. 数据采集方案

### 4.1 服务端埋点

**每 `interval` 秒（默认 5 s）聚合一次，追加写入 CSV：**

```
server_metrics.csv
timestamp,client_count,tick_ms_avg,tick_ms_max,cpu_percent,mem_mb,
packets_out,bytes_out,packets_in,bytes_in,ser_ms_avg,room_count
```

**场景标记**：每次实验开始时写一行场景信息，便于后续切分数据。

```
server_scenario.csv
timestamp,scenario_id,encoder,tick_rate,client_count,inject_loss,inject_delay
```

### 4.2 客户端埋点

```
client_metrics.csv
timestamp,rtt_ms,packets_in,bytes_in,frame_ms,interp_err_px,pos_desync_px
```

### 4.3 设计原则

| 原则 | 原因 |
|---|---|
| **追加写，不覆盖** | 一次实验可能分段跑，不能丢历史 |
| **每行带 `scenario_id`** | 便于按实验条件切分数据 |
| **采集本身的开销要可忽略** | 聚合后写，不是每包都写磁盘 |
| **时间戳用单调时钟** | 避免系统时间被调整导致数据错乱 |

## 5. 实验详细设计

### E1 · 协议编码对比（二进制 vs JSON）

- **目的**：量化自定义二进制协议在体积与 CPU 上的优势
- **自变量**：`encoder = binary | binary_fast | json`（**三种**，2026-10-26 定）

  | 变体 | 是什么 | 用来回答 |
  |---|---|---|
  | `binary` | 协议标准编码，逐条目 `struct.pack` | 基线 |
  | `binary_fast` | **同一个协议、逐字节相同**，但整帧只调一次 `struct.pack` | **实现方式**能带来多少差异 |
  | `json` | 短键名 JSON，**编解码双向都实现** | **编码形式**能带来多少差异 |

  > 加 `binary_fast` 是为了把「协议优势」和「实现优势」分开。
  > 没有它，JSON 慢多少都可以被质疑成"你的 JSON 写得烂"或"你的二进制写得快"。

- **JSON 是公平实现**（答辩会被问，约定写死在 `protocol/encoders.py` 的模块注释里）：
  1. **字段与实体集合完全一致** —— 同一份 `Snapshot` 进去，三种编码装同一批数据
     （`tests/test_encoders.py` 用**往返测试**锁住：encode→decode 后与原对象相等）
  2. **标准库、不做人为劣化**：
     `json.dumps(payload, separators=(",", ":"), ensure_ascii=False).encode("utf-8")`
  3. **键名刻意取短**（`t`/`p`/`i`/`x`…）—— 拿字段名拼全的 JSON 来比是稻草人
  4. **不做协议值域校验** —— JSON 本来就不需要（没有固定位宽）
  5. **不只是"能发"**：解码也实现了（`unpack_snapshot_json`），是一条完整可用的协议路径
- **控制变量**：**4 人**、tick 率 20 Hz、无网络损伤、服务端实体种子固定、每档 2 轮
- **档位**：4 档 —— 30/200、100/800、150/1200、250/2000
- **因变量**：平均包大小、BW↓、**编码耗时 `encode_ms`**、CPU%
- **⚠️ 关键测量口径：用 `encode_ms` 而不是 `ser_ms`**

  `ser_ms` 量的是整个 `build_snapshot()`，其中包含**实体对象构造**
  （100 敌机 + 800 子弹 = 900 个 dataclass 实例），而那一部分**三种编码共享**。
  实测 100/800 时共享开销约 0.55 ms、真正的编码只有 0.14~0.64 ms ——
  用 `ser_ms` 画图会得到三根**一样高的柱子**，什么也证明不了。

  所以加了一个**嵌套计时** `encode_ms`（嵌在 `ser` 内，**不参与四段相加**），
  只量 `encoder.encode()` 这一步。约束：`encode_ms ≤ ser_ms` 恒成立。
- **跑批命令**：

  ```powershell
  python -X utf8 -m tools.run_e9 --levels 30/200,100/800,150/1200,250/2000 \
      --encoders binary,binary_fast,json --reps 2 --duration 180 --prefix E1
  python -X utf8 -m tools.plot --csv data/server_metrics.csv --out docs/figures --scenario E1-
  ```
- **产出图表**：
  - 图 6-1：三种编码的**平均包大小对比**（柱状图）
  - 图 6-2：**编码耗时对比**（柱状图，用 `encode_ms`）
  - 图 6-3：**CPU 占用随实体数变化**（折线图，每种编码一条）
- **体积口径（2026-10-26 统一，以此为准）**
  - **条件**：4 人 + 30 敌机 + 200 子弹、**无道具**、JSON 用 `list[dict]` +
    `separators=(',',':')` + `ensure_ascii=False`
  - **实测**：binary **1927 B** / JSON **9048 B** = **4.7 倍**
    （二进制侧逐字节吻合 `13 + 4×11 + 30×9 + 200×8`）
  - ⚠️ **原设计估算的 5.6 倍（1974 B / 11000 B）不要再用**：
    它是 `01 §7.4` 的**纸面推算**，且二进制侧**含 5 个道具**（1974 B）。
    两个口径不可混用 —— 含道具的设计值 vs 不含道具的实测值。
  - 20 Hz 下带宽：binary ≈ **37.9 KB/s**、JSON ≈ **178 KB/s**（每客户端）

### E6 · 快照策略对比（全量 vs 增量 vs 确定性生成）· 可选

- **目的**：验证不同同步策略的带宽收益与实现代价
- **自变量**：`snapshot_mode = full | delta | deterministic`
- **控制变量**：4 人 + 30 敌机、tick 率 20 Hz、无损伤
- **因变量**：BW↓、CPU%（增量计算与确定性校验都有开销）
- **三种策略说明**：

  | 策略 | 做法 | 理论带宽 |
  |---|---|---|
  | **full**（默认） | 每帧广播全部实体 | ≈ 39.5 KB/s |
  | **delta** | 只广播发生变化的实体 | 视移动比例而定 |
  | **deterministic** | 子弹不广播，只同步「何时何地发射了哪种弹幕」，各客户端本地推算 | 子弹部分几乎归零 |

- **注意**：子弹占快照的 **1600 / 1974 ≈ 81%**，所以 `deterministic` 的**理论上限收益极大**；
  但它要求浮点运算确定性一致，**跨平台会飘** —— 这正是要测/要讨论的结论
- **产出图表**：
  - 图 6-13：**三种策略的带宽对比**（柱状图）
  - 另出一张**实现复杂度 / 风险对比表**（非图表，直接写进正文）

> **本实验是"弹幕游戏"相对"简单移动游戏"的最大加分项** ——
> 只有子弹数量足够多，"确定性生成"这个优化方向才有讨论价值。

### E9 · ⭐ 实体数量对带宽与 CPU 的影响（**本项目核心实验**）

- **目的**：找出服务端单核的处理上限，为「同屏实体上限」提供数据依据（见 D-011）
- **自变量**：同屏实体数（**9 档**，2026-10-25 定稿）
  - 敌机数 = 10 / 20 / 30 / 50 / 80 / 100 / **150 / 200 / 250**
  - 子弹数 = 50 / 100 / 200 / 400 / 600 / 800 / **1200 / 1600 / 2000**
  - 前 6 档是原计划；**后 3 档是实测追加的** —— 100/800 时单核只占约 11 %，

- **控制变量**：4 人、二进制编码、20 Hz、服务端实体生成种子固定为 1、每档 **2 轮**
- **运行器**：`python -X utf8 -m tools.run_e9`（参数固化成代码，避免手敲导致条件不一致）
- **因变量**：`tick_ms`（及四段拆解）、CPU%、快照字节数、BW↓
- **步骤**：
  1. 用机器人客户端 + 配置项制造指定的实体规模
  2. 每档稳定运行 3 分钟
  3. 记录 `tick_ms` 与 CPU
- **已知预估值**（来自项目早期的**一次性原型**，见 `01-系统架构.md §7.1`；

  **不可与当前 20 Hz 数据直接对比**，已被 E9 取代。原值 / 更正值并列：

  | 敌机 | 子弹 | ms/tick | CPU 原值 | **CPU 更正（20 Hz）** |

  碰撞耗时为 O(子弹×敌机)，所以它在 100/800 处已占 tick 的 **78%**、通信只占 **16%**；
  按这个斜率外推，**要在 50% 舒适线上找到拐点，把最高档提到 200/1600 甚至 250/2000 才够**
  （100/800 时单核占用只有约 13%）。D-011 明确说过实验**有意突破** 30/300 的设计上限。

- **论文价值**：这张图直接支撑「同屏敌机上限 = 30、子弹上限 = 300」的设计决策，
  是**设计 → 实测 → 反推约束**的完整闭环。

## 7. 实验记录模板

每次实验后填写，存于 `docs\experiments\`：

```markdown
## 实验：E1 协议编码对比
- 日期：2026-XX-XX
- 场景 ID：E1-binary-01
- 配置：encoder=binary, tick=20, players=4, enemies=30, bullets=200, loss=0, delay=0
- 时长：5 分钟
- 原始数据：data/E1-binary-01-server.csv, data/E1-binary-01-client.csv
- 关键结果：
  - 平均快照大小：1974 字节
  - 平均 BW↓：39.5 KB/s
  - 平均 CPU：10.2 %
- 异常/备注：无
- 图表：图 6-1（左柱）
```

**要求**：每个实验至少跑 **2 次**，取一致的结果；差异大要查明原因。

**注意**：记录时必须写明**实体构成**（玩家 / 敌机 / 子弹数），
否则不同实验的数据不可比 —— 这是本项目最容易出错的地方。
