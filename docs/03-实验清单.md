### 2.2 拓扑

**本机多进程**（当前方案）：

```
    ┌──────────────── 同一台开发机 ────────────────┐
    │                                              │
    │  服务端进程  ←── TCP ──→  客户端进程 × N      │
    │                          机器人进程 × M       │
    │                                              │
    └──────────────────────────────────────────────┘
```

> ⚠️ **必须连本机局域网 IP**（`192.168.x.x`），**不要连 `127.0.0.1`**
> 原因见 `01-系统架构.md §9.2`：回环不经过网卡，拿不到真实 RTT 与抖动。
> **这一条要在阶段 1 先用 `ping` 验证。**

## 3. 指标定义

**所有指标必须有精确定义，否则数据不可比。**

| 指标 | 符号 | 定义 | 采集端 |
|---|---|---|---|
| 往返延迟 | RTT | 心跳包发出到收到 ACK 的时间差 | 客户端 |
| 下行带宽 | BW↓ | 每客户端每秒接收字节数 | 客户端 |
| 上行带宽 | BW↑ | 每客户端每秒发送字节数 | 服务端 |
| 包率 | PPS | 每秒报文数 | 两端 |
| 平均包大小 | — | 总字节数 ÷ 报文数 | 两端 |
| 逻辑帧耗时 | tick_ms | 服务端一次世界更新的耗时 | 服务端 |
| CPU 占用 | CPU% | 进程 CPU 百分比 | 两端 |
| 内存占用 | RSS | 进程常驻内存 | 两端 |
| 序列化耗时 | ser_ms | 编码 + 解码总耗时 | 两端 |
| **插值误差** | err_px | 客户端渲染位置与最近权威位置的欧氏距离 | 客户端 |
| 丢包率 | loss% | 序号不连续的比例 | 客户端 |
| 断线检测延迟 | detect_s | 客户端断开到服务端标记断线的时间 | 服务端 |

> **插值误差**是本项目最有说服力的指标 —— 它直接量化「网络变差时玩家看到的东西有多不准」。

## 4. 数据采集方案

### 4.1 服务端埋点

**每 `interval` 秒（默认 5 s）聚合一次，追加写入 CSV：**

```
server_metrics.csv
timestamp,client_count,tick_ms_avg,tick_ms_max,cpu_percent,mem_mb,
packets_out,bytes_out,packets_in,bytes_in,ser_ms_avg,room_count
```

**场景标记**：每次实验开始时写一行场景信息，便于后续切分数据。

```
server_scenario.csv
timestamp,scenario_id,encoder,tick_rate,client_count,inject_loss,inject_delay
```

### 4.2 客户端埋点

```
client_metrics.csv
timestamp,rtt_ms,packets_in,bytes_in,frame_ms,interp_err_px,pos_desync_px
```

### 4.3 设计原则

| 原则 | 原因 |
|---|---|
| **追加写，不覆盖** | 一次实验可能分段跑，不能丢历史 |
| **每行带 `scenario_id`** | 便于按实验条件切分数据 |
| **采集本身的开销要可忽略** | 聚合后写，不是每包都写磁盘 |
| **时间戳用单调时钟** | 避免系统时间被调整导致数据错乱 |

## 5. 实验详细设计

### E1 · 协议编码对比（二进制 vs JSON）

- **目的**：量化自定义二进制协议在体积与 CPU 上的优势
- **自变量**：`encoder = binary | json`
- **控制变量**：玩家数 8、tick 率 20 Hz、无网络损伤
- **因变量**：平均包大小、BW↓、序列化耗时、CPU%
- **步骤**：
  1. 配置 `encoder=binary`，跑 5 分钟，采集
  2. 配置 `encoder=json`，同条件跑 5 分钟
  3. 对比
- **预期结果**：二进制包大小约为 JSON 的 **1/5**，CPU 明显更低
- **产出图表**：
  - 图 6-1：两种编码的**平均包大小对比**（柱状图）
  - 图 6-2：**序列化耗时对比**（柱状图）
  - 图 6-3：**CPU 占用随玩家数变化**（折线图，10/20/50 人）

### E2 · 并发能力测试

- **目的**：找服务端的承载上限与性能拐点
- **自变量**：机器人客户端数量 = 10 / 20 / 50 / 100 / 200
- **控制变量**：`encoder=binary`、tick 率 20 Hz
- **因变量**：`tick_ms`、CPU%、内存、RTT 分位数
- **步骤**：用 `loadtest.py` 逐级加压，每级稳定运行 3 分钟后采样
- **产出图表**：
  - 图 6-4：**连接数 vs CPU / 内存**（双轴折线图）
  - 图 6-5：**连接数 vs tick 耗时**（折线图，找拐点）
  - 图 6-6：**RTT 分位数**（P50 / P95 / P99 随连接数变化）

### E3 · IO 模型对比（事件驱动 vs 每连接一线程）· 可选

- **目的**：验证事件驱动在高并发下的资源效率
- **自变量**：`io_model = asyncio | thread_per_connection`
- **控制变量**：同 E2
- **因变量**：CPU%、内存、最大稳定连接数
- **实现要求**：需要额外实现一个线程版服务端核心（**仅替换网络层，业务层复用**）
- **成本提示**：约 8~10 小时。**若时间紧张可只做理论对比，不做实现**
- **产出图表**：
  - 图 6-7：**两种 IO 模型的资源占用对比**

### E4 · 网络损伤对同步质量的影响

- **目的**：量化恶劣网络下游戏体验的退化程度
- **自变量**：
  - 丢包率 = 0 / 5 / 10 / 20 %
  - 延迟 = 0 / 50 / 100 / 200 ms
- **控制变量**：8 人、20 Hz、二进制编码
- **因变量**：**插值误差 (err_px)**、RTT、可见卡顿次数
- **步骤**：用 `tools\netem.py` 注入，每档跑 3 分钟
- **产出图表**：
  - 图 6-8：**丢包率 vs 插值误差**（折线图）
  - 图 6-9：**延迟 vs 插值误差**（折线图）
  - 图 6-10：**丢包×延迟 二维热力图**

### E5 · 同步频率（tick 率）的影响

- **目的**：找带宽与平滑度的平衡点
- **自变量**：tick 率 = 10 / 15 / 20 / 30 Hz
- **控制变量**：8 人、二进制、无损伤
- **因变量**：BW↓、插值误差、客户端帧率
- **产出图表**：
  - 图 6-11：**tick 率 vs 带宽**（折线图）
  - 图 6-12：**tick 率 vs 插值误差**（折线图，双轴叠加）
- **论文价值**：给出「20 Hz 是性价比最优点」的数据支撑

### E6 · 快照策略对比（全量 vs 增量）· 可选

- **目的**：验证增量同步的带宽收益
- **自变量**：`snapshot_mode = full | delta`
- **因变量**：BW↓、CPU%（增量计算有开销）
- **注意**：8 人场景下全量仅约 97 字节，**增量收益可能不明显** —— 这正是要测的结论
- **产出图表**：
  - 图 6-13：**玩家数 vs 两种策略的带宽**

### E7 · 抓包验证

- **目的**：证明协议实现正确，且能被第三方工具解析
- **步骤**：
  1. Wireshark 在 `WLAN` 接口抓包
  2. 过滤条件：`tcp.port == 9527`
  3. 用 `Follow TCP Stream` 展示原始字节流
  4. 对照 `02-协议设计.md` 逐字段标注帧头
  5. 验证粘包拆包：人为构造半包/粘包，看能否正确解析
- **产出图表**：
  - 图 6-14：**抓包总览**
  - 图 6-15：**单个报文的帧头字段标注**
  - 图 6-16：**粘包/半包的解析对比**

### E8 · 断线检测时效

- **目的**：验证心跳超时机制的有效性
- **自变量**：心跳间隔 = 3 / 5 / 10 s
- **因变量**：断线检测延迟
- **步骤**：强制 kill 客户端进程，记录服务端标记断线的时间
- **产出**：表格（含理论值与实测值对比）

## 7. 实验记录模板

每次实验后填写，存于 `docs\experiments\`：

```markdown
## 实验：E1 协议编码对比
- 日期：2026-XX-XX
- 场景 ID：E1-binary-01
- 配置：encoder=binary, tick=20, players=8, loss=0, delay=0
- 时长：5 分钟
- 原始数据：data/E1-binary-01-server.csv, data/E1-binary-01-client.csv
- 关键结果：
  - 平均包大小：89 字节
  - 平均 BW↓：1.7 KB/s
  - 平均 CPU：3.2 %
- 异常/备注：无
- 图表：图 6-1（左柱）
```

**要求**：每个实验至少跑 **2 次**，取一致的结果；差异大要查明原因。
