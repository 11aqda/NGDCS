```
│                              │               └───────┬───────┘   │

│   ┌──────────────────────────────────────────────────▼────────┐  │

│   ├───────────────────────────────────────────────────────────┤  │
│   │  ② 协议层      粘包拆包 / 报文集编解码 / 校验               │  │
│   ├───────────────────────────────────────────────────────────┤  │
│   │  ③ 分发层      按消息类型路由到对应处理器                   │  │
│   ├───────────────────────────────────────────────────────────┤  │
│   │  ④ 业务层      会话管理 / 房间管理 / 游戏逻辑               │  │
│   ├───────────────────────────────────────────────────────────┤  │
│   │  ⑤ 游戏循环    20 Hz tick：应用输入 → 推进世界 → 广播快照   │  │
│   └───────────────────────────────────────────────────────────┘  │
│   ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌──────────┐  │
│   │ 数据采集    │  │ 配置加载    │  │ 日志        │  │ 网络损伤  │  │
│   └────────────┘  └────────────┘  └────────────┘  └──────────┘  │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2 分层职责

| 层 | 职责 | 不该做的事 |
|---|---|---|
| 网络层 | 建立/关闭连接、字节流读写、连接生命周期 | 不懂协议内容 |
| 协议层 | 从字节流切出完整报文、编解码、校验 | 不懂业务语义 |
| 分发层 | 按 `type` 把消息交给对应处理函数 | 不直接改游戏状态 |
| 业务层 | 会话、房间、玩家管理 | 不碰 socket |
| 游戏循环 | 定频推进世界、生成快照 | 不做网络 IO |

**分层的目的**：任一层可独立替换与测试。例如把"二进制编解码"换成"JSON 编解码"时，只动协议层，其余不变——**这正是实验 §6.3 要验证的。**

### 3.3 两个关键架构选择

**① 用 C/S，不用 P2P**

| 理由 | 说明 |
|---|---|
| 题目要求 | 题目明确写「基于 C/S 架构」 |
| 服务端权威 | 状态由服务端裁定，天然避免不一致与作弊 |
| 便于测试 | 一台机器集中采集所有指标 |

**② 服务端用事件驱动，不用「每连接一线程」**

| 方案 | 特点 |
|---|---|
| 每连接一线程 | 编程直观，但连接数上升时线程切换开销大、内存高 |
| **事件驱动（asyncio）** | 单线程事件循环，高并发下资源占用低 |

**这不只是实现选择，更是论文第 4 章和第 6 章的对比实验对象**（见 `03-实验清单.md`）。

## 4. 通信设计

### 4.1 为什么用自定义二进制协议

| 方案 | 体积 | 解析速度 | 可读性 |
|---|---|---|---|
| JSON | 大（约 5~6 倍） | 慢 | 好 |
| **自定义二进制** | **小** | **快** | 差（需要工具） |

实时游戏每秒要发几十次状态，**体积和解析开销直接决定并发上限**。
JSON 版本会保留下来作为**对比实验**，而不是被丢弃。

### 4.2 同步模型：服务端权威

```
客户端  ──[输入: 按键位掩码]──▶  服务端
                                      │
                                 20Hz 推进世界
                                      │
客户端  ◀──[快照: 所有玩家状态]────  服务端
```

**设计要点：**

| 要点 | 说明 |
|---|---|
| 客户端只发**输入**，不发位置 | 位置由服务端计算 → 客户端无法直接篡改坐标 |
| 服务端 20 Hz 广播**全量快照** | 房间人数少（≤8），全量比重增量更简单可靠 |
| 客户端**插值**渲染 | 把 20 Hz 的快照渲染成 60 fps 的平滑动画 |

**为什么局域网下不需要客户端预测？**

局域网 RTT 通常 < 5 ms，而 20 Hz 的一个 tick 是 50 ms。
**往返延迟远小于一帧**，玩家感受不到滞后，因此第一版**不做预测**，保持简单。

客户端预测作为**进阶项**（F12）：实现后可做「有预测 vs 无预测」的对比。

### 4.3 客户端为什么不会卡住

**关键约束：网络 IO 绝不能阻塞渲染主循环。**

| 方案 | 评价 |
|---|---|
| 主线程阻塞 `recv()` | ❌ 网络一卡，游戏直接冻死 |
| **非阻塞 socket + 每帧 poll** | ✅ **选用**：单线程、无锁、无并发 bug |
| 独立接收线程 + 队列 | 可用，但引入线程同步问题 |

**选用「非阻塞 + 每帧轮询」**，主循环每帧最多花极短时间检查一次 socket 可读性。这个取舍会记入 `DECISIONS.md`。

### 4.4 通信分层（**主线** · F11）

| 数据类型 | 传输方式 | 理由 |
|---|---|---|
| 实时游戏数据 | **TCP 长连接 + 自定义二进制协议** | 高频、低延迟、需要自己控制报文 |
| 账号 / 排行榜 / 战绩 | **HTTP 短连接（Django）** | 低频、请求-响应模型、开发快 |
| 排行榜缓存 | **Redis** | 高频读取、内存级响应 |
| 用户与分数持久化 | **MySQL** | 需要事务与长期存储 |

**两层如何衔接**：客户端先通过 HTTP 登录，得到 **token**；再用该 token 在 TCP 连接上认证（`C_AUTH`）。这样两层自然衔接，且**实时连接无需重复处理账号逻辑**。

> **论文论点**：按数据类型选择通信方式，而非一套打天下。
> 这是「数据通信**系统**」比「一个 TCP 服务器」更完整的体现。

> ⚠️ **接口需要有调用方**：客户端必须实现 HTTP 调用，且**不得阻塞游戏主循环**（沿用 D-007 的非阻塞原则）。

## 5. 游戏形态（已定稿）

### 5.1 一句话描述

> 多名玩家操控**几何飞船**在同一竞技场内自由移动，位置与朝向实时同步。

### 5.2 画面示意

```
┌──────────────────────────────────────────────────────┐
│  房间 LC5WTF        延迟 12ms        在线 4/8        │
├──────────────────────────────────────────────────────┤
│                                                      │
│                                                      │
│                        ▲ 小明                        │
│                       ╱ ╲                            │
│                                                      │
│                                                      │
│         ▲ 你 (Anria)                                 │
│        ╱ ╲                                           │
│                                                      │
│                                                      │
│                                    ▲ 眉姨阁诗人     │
│                                   ╱ ╲                │
│                                                      │
│      ▲ 玩家3                                         │
│     ╱ ╲                                              │
│                                                      │
└──────────────────────────────────────────────────────┘
            WASD / 方向键 移动        ESC 退出
```

### 5.3 玩法

| 有 | 没有 |
|---|---|
| 自由移动（WASD / 方向键） | 敌人、AI |
| 机头跟随行进方向 | 子弹、碰撞 |
| 前方半透明**视野扇形**（纯视觉） | 波次、关卡、道具 |
| 玩家名字标签 | 分数、胜负 |
| 角落显示房间号 / 延迟 / 在线人数 | 音效 |

**明确的取舍**：本游戏是通信系统的**负载发生器**，不追求玩法。

### 5.4 视觉规范（几何风格）

| 元素 | 实现方式 |
|---|---|
| 飞船本体 | `pygame.draw.polygon` 画几何多边形，机头指向行进方向 |
| 外发光 | 由外向内 2~3 层递减 alpha 的同形状，`BLEND_RGB_ADD` 叠加 |
| 拖尾 | 缓存最近 N 帧位置，按时间递减 alpha 绘制 |
| 视野扇形 | `draw.polygon` 画扇形 + 低 alpha 填充，跟随朝向 |
| 名字 | 项目自带 TTF 字体 + 描边，**不用系统默认字体** |
| 背景 | 深色底 + 细网格线 |
| 配色 | 8 色调色板，每个玩家分配一个固定色 |

> **为什么坚持几何风格**：素材风格不统一是"廉价感"的头号来源；几何绘制风格天然统一、永不失真、便于染色与加特效。

### 5.5 竞技场

| 项 | 值 |
|---|---|
| 尺寸 | 960 × 640（固定一屏） |
| 相机 | **无**（不做滚动、不做视野裁剪） |
| 边界行为 | 撞墙停住 |
| 障碍物 | **无** |

## 9. 测试环境方案（无第二台设备）

**问题**：题目是「局域网」联机，但只有一台开发机。

### 9.1 选定方案：本机多进程

在**同一台机器**上启动 1 个服务端 + N 个客户端进程，模拟多客户端环境。

| 优点 | 说明 |
|---|---|
| 零成本 | 不需要装任何虚拟机软件 |
| 覆盖逻辑与协议 | 连接管理、房间、同步、并发、粘包拆包**全部可验证** |
| 便于压测 | 配合机器人客户端可轻松跑到 50+ 连接 |
| 抓包可行 | 需要时可在回环/网卡接口抓包 |

### 9.2 ⚠️ 关键要求：不要连 `127.0.0.1`

**必须让客户端连接本机的局域网 IP**（如 `192.168.1.100`），而不是 `127.0.0.1`。

| 连接方式 | 流量路径 | 能否得到真实网络指标 |
|---|---|---|
| `127.0.0.1` | 操作系统内部回环，**不经过网卡** | ❌ RTT ≈ 0.1 ms，无抖动无丢包 |
| **本机局域网 IP** | 经过 WiFi 网卡与协议栈 | ✅ 可能有真实 RTT 与抖动 |

**必须在阶段 1 实测验证**（用 `ping` 对比两者，或用 Wireshark 看 `WLAN` 接口是否有流量）：

- **RTT 在 2~10 ms 量级** → 走了真实网卡，**实验数据可用，不需要虚拟机**
- **RTT 在 0.1 ms 量级** → 被系统当作回环短路，**网络实验无数据 → 必须改用虚拟机方案**

### 9.3 已知局限（论文中要如实说明）

- 物理上仍是同一台机器，测不出真正的跨机 CPU 竞争与时钟差异
- 若本机 LAN IP 被短路为回环，则**没有真实的丢包与抖动**，必须依赖人为注入（`tools\netem.py`）

### 9.4 升级选项（按需启用）

| 方案 | 成本 | 说明 |
|---|---|---|
| 虚拟机 + 桥接网络 | 免费 | 虚拟机获得独立 IP，构成真正的跨主机 C/S |
| 树莓派 Zero 2 W | 约 ¥150 | 真正的独立第二主机，对网络工程毕设是加分项 |
| 临时借用他人电脑 | 免费 | 关键验证时用几天即可 |

### 10.2 决定 4 带来的影响 ⚠️

**问题**：只用本机多进程（`127.0.0.1` 回环）测试，**拿不到真实的 RTT、抖动、丢包数据**，第 6 章的网络性能部分将没有素材。

**强制要求**：客户端连接**本机局域网 IP**（如 `192.168.x.x`）而不是 `127.0.0.1`。

**必须实测验证**：用 `ping` 与 Wireshark 确认流量是否真的经过 WiFi 网卡。

| 实测结果 | 结论 |
|---|---|
| RTT 为 2~10 ms 量级 | ✅ 走了真实网卡，实验数据可用，**不需要虚拟机** |
| RTT 为 0.1 ms 量级 | ❌ 被系统当作回环短路，**网络实验无数据 → 必须改用虚拟机方案** |

**这一步要在阶段 1 就验证**，不能拖到最后才发现没数据。
