## 1. 项目定位

### 1.1 题目

《基于 C/S 架构的网络游戏数据通信系统设计与实现》

### 1.2 核心交付物

**数据通信系统**，由四部分组成：

| 组成 | 说明 |
|---|---|
| 应用层通信协议 | 自定义二进制协议，含粘包/拆包方案 |
| 服务端 | 多客户端并发、会话与房间管理、游戏逻辑 |
| 客户端通信模块 | 非阻塞收发、心跳、断线重连 |
| 测试与压测工具 | 机器人客户端、压测脚本、数据采集 |

### 1.3 游戏的角色

游戏**只是验证通信系统的应用场景**，不追求玩法深度。

> **答辩话术**：我做的是实时数据通信系统，游戏是它的验证平台。

### 1.4 优先级（⭐ 决定了超时时的取舍）

```
① 通信跑通  →  ② 抓包实验  →  ③ 性能测试  →  ④ 游戏内容
```

**这个顺序保证了：任何一周停下来，手上都有完整可交付、可写论文的成果。**

- 做到 ③ → **论文第 3 / 4 / 6 章素材齐全，毕设已经成立**
- ④ 是「锦上添花」，时间不够时**第一个砍它，论文不受影响**

### 3.2 分层职责

| 层 | 职责 | 不该做的事 |
|---|---|---|
| 网络层 | 建立/关闭连接、字节流读写、连接生命周期 | 不懂协议内容 |
| 协议层 | 从字节流切出完整报文、编解码、校验 | 不懂业务语义 |
| 分发层 | 按 `type` 把消息交给对应处理函数 | 不直接改游戏状态 |
| 业务层 | 会话、房间、玩家、游戏世界管理 | 不碰 socket |
| 游戏循环 | 定频推进世界、生成快照 | 不做网络 IO |

**分层的目的**：任一层可独立替换与测试。例如把「二进制编解码」换成「JSON 编解码」时，只动协议层，其余不变 —— **这正是实验 E1 要验证的。**

### 3.3 两个关键架构选择

**① 用 C/S，不用 P2P**

| 理由 | 说明 |
|---|---|
| 题目要求 | 题目明确写「基于 C/S 架构」 |
| 服务端权威 | 状态由服务端裁定，天然避免不一致与作弊 |
| 便于测试 | 一台机器集中采集所有指标 |

**② 服务端用事件驱动，不用「每连接一线程」**

| 方案 | 特点 |
|---|---|
| 每连接一线程 | 编程直观，但连接数上升时线程切换开销大、内存高 |
| **事件驱动（asyncio）** | 单线程事件循环，高并发下资源占用低 |

**这不只是实现选择，更是论文第 4 章与实验 E3 的对比对象。**

### 3.4 ⭐ 三阶段解耦：占位对象 → 完整游戏

**问题**：优先级 ④（游戏内容）排在最后，那前三个阶段「通信跑通」时同步什么？

**方案**：把网络层与游戏层**解耦**，分三阶段演进：

| 阶段 | 同步的对象 | 目的 |
|---|---|---|
| **阶段 1~3**（第 1~13 周） | **极简占位**：几个方块在场地内移动 | 验证通信系统本身，与游戏无关 |
| **阶段 4**（第 14~17 周） | 逐步替换为敌机、子弹、道具 | 增加同步负载与复杂度 |
| 最终 | 完整飞机大战（含 BOSS） | 演示效果 |

**好处**：

1. **通信系统可独立验证** —— 用最简单的对象证明协议、粘包、同步、并发都是对的
2. **占位方块是最好的协议测试工具** —— 排查问题时排除游戏逻辑的干扰
3. **风险前移** —— 最难的部分先做完，游戏内容可随时削减

> **占位阶段不是白做**：它的实体结构、同步机制、渲染管线与最终版本一致，只是实体类型少。
> 替换游戏内容时**通信层不用改**。

## 4. 通信设计

### 4.1 为什么用自定义二进制协议

| 方案 | 体积 | 解析速度 | 可读性 |
|---|---|---|---|
| JSON | 大（约 5~6 倍） | 慢 | 好 |
| **自定义二进制** | **小** | **快** | 差（需工具） |

实时游戏每秒要广播 20 次全场状态，**体积和解析开销直接决定并发上限**。
JSON 版本会保留下来作为**对比实验的对照组**，而不是被丢弃。

### 4.2 同步模型：服务端权威

```
客户端  ──[输入: 按键位掩码]──▶  服务端
                                      │
                                 20Hz 推进世界
                              （移动、弹幕、命中判定、计分）
                                      │
客户端  ◀──[快照: 全场实体状态]────  服务端
```

| 要点 | 说明 |
|---|---|
| 客户端只发**输入**，不发位置 | 位置由服务端计算 → 客户端无法篡改坐标 |
| 服务端 20 Hz 广播**全量快照** | 房间人数少（≤4），全量比重增量更简单可靠 |
| 客户端**插值**渲染 | 把 20 Hz 的快照渲染成 60 fps 平滑动画 |
| **命中判定、伤害、计分全在服务端** | 客户端说「我打中了」不算 |

**为什么局域网下不做客户端预测**：局域网 RTT < 5 ms，远小于一个 50 ms 的 tick，
玩家感受不到滞后。预测列为进阶项 F13。

### 4.3 客户端为什么不会卡住

**关键约束：网络 IO 绝不能阻塞渲染主循环。**

| 方案 | 评价 |
|---|---|
| 主线程阻塞 `recv()` | ❌ 网络一卡，游戏直接冻死 |
| **非阻塞 socket + 每帧轮询** | ✅ **选用**：单线程、无锁、无并发 bug |
| 独立接收线程 + 队列 | 可用，但引入线程同步问题 |

### 4.4 通信分层（**主线**）

| 数据类型 | 传输方式 | 理由 |
|---|---|---|
| 实时游戏数据 | **TCP 长连接 + 自定义二进制协议** | 高频、低延迟、需自己控制报文 |
| 账号 / 排行榜 | **HTTP 短连接（Django）** | 低频、请求-响应、开发快 |
| 排行榜缓存 | **Redis** | 高频读取、内存级响应 |
| 用户与分数持久化 | **MySQL** | 需要事务与长期存储 |

**两层如何衔接**：客户端先 HTTP 登录拿 **token**，再用该 token 在 TCP 连接上认证（`C_AUTH`）。

> **论文论点**：按数据类型选择通信方式，而非一套打天下。

> ⚠️ 客户端必须实现 HTTP 调用，且**不得阻塞游戏主循环**。
> 所有 HTTP 调用都发生在**游戏循环之外**（登录界面 / 排行榜界面 / 结算界面），天然不存在阻塞问题。

## 5. 游戏形态

### 5.1 一句话描述

> **竖版飞机大战（弹幕射击）：1~4 名玩家合作，操控几何飞船逐波清剿敌机，闯过 2 关并击败 BOSS。**

### 5.2 画面示意

```
┌──────────────────────────────────┐
│  TIME 02:15   WAVE 3/5   延迟 3ms │
│                                  │
│         ▼        ▼               │
│      ▼      ▼         ▼          │  敌机从上方来袭
│           ●  ●                   │
│         ●   ●  ●                 │  敌方弹幕
│                                  │
│      ▲                           │
│    ╱   ╲                         │
│   ╱ 你  ╲    ▲                   │  玩家飞船（几何）
│  ╱───────╲ ╱   ╲                 │
│                                  │
│  HP ♥♥♥   POWER ▮▮▮▯▯   SCORE 340 │
└──────────────────────────────────┘
```

### 5.3 玩家

| 项 | 值 |
|---|---|
| 移动 | **左右移动**（键盘 A/D 或 ←/→） |
| 射击 | **自动向上射击**（无需按键） |
| HP | **3 点** |
| 无敌帧 | 被击中后 **1.5 秒**闪白无敌 |
| 复活 | 阵亡后 **10 秒**自动复活，**HP 恢复满血** |
| 阵亡期间 | **不能移动、不能射击、不会被击中** |

### 5.4 火力系统（5 级，三重递进）

| 等级 | 形态 | 每发伤害 | 射击冷却 | 弹数 | 理论 DPS |
|---|---|---|---|---|---|
| **1** | 单发直线 | 1 | 0.20 s | 1 | 5.0 |
| **2** | 单发直线（更快） | 1 | 0.15 s | 1 | 6.7 |
| **3** | **双发直线** | 1 | 0.15 s | 2 | 13.3 |
| **4** | 双发直线（更强） | 2 | 0.15 s | 2 | 26.7 |
| **5** | **三发扇形** | 2 | 0.13 s | 3 | 46.2 |

```
  Lv1~2          Lv3~4           Lv5
    │            │   │         ╲   │   ╱
    │            │   │          ╲  │  ╱
    ●            ●   ●           ●  ●  ●
```

> **数值全部可配置**（见 §6），实机试玩后再调，不硬编码。

### 5.5 道具与惩罚

```
击杀敌机   → 15% 概率掉落「火力道具」（发光几何菱形，缓慢上下浮动）
拾取道具   → 火力等级 +1（最高 5 级）
满级后拾取 → 转化为分数 +50
被击中     → 火力等级 -1（最低 1 级）+ HP -1
阵亡复活   → 火力等级重置为 1
```

**设计意图**：

- 掉落创造「为了道具而冒险」的动力（经典飞机大战的核心乐趣）
- 死亡降级使惩罚有分量，而不只是掉血

### 5.6 敌机与弹幕

**敌机 3 种**

| 种类 | 行为 | HP | 弹幕 | 掉落率 |
|---|---|---|---|---|
| **直线俯冲** | 从上方直冲而下 | 1 | 直线散射 | 10% |
| **横向移动** | 左右摆动下降 | 2 | 直线散射 | 15% |
| **追踪玩家** | 朝玩家方向缓慢移动 | 2 | 扇形 / 追踪弹 | 20% |

> **攻击性越强的敌人掉落率越高** —— 鼓励玩家挑战难的，是经典设计。

**弹幕 3 种**

| 模式 | 形态 | 使用者 |
|---|---|---|
| **直线散射** | 3~5 发小角度 | 普通敌机 |
| **扇形** | 8~12 发铺开 | 精英敌机 / BOSS |
| **追踪弹** | 缓慢转向玩家 | BOSS 第二阶段 |

### 5.7 关卡与 BOSS

**关卡编排**

| 关 | 波次数 | 各波敌机数 | 合计 | 同屏峰值 |
|---|---|---|---|---|
| **第 1 关** | 5 | 5 / 8 / 10 / 12 / 15 | **50** | 15 |
| **第 2 关** | 5 | 12 / 14 / 16 / 18 / 20 | **80** | 25 |

**波次推进规则**

```
本波敌机全部清完  →  等 2 秒  →  进入下一波
     或
本波超时 25 秒    →  立即进入下一波（先到者为准）
```

> 典型每波约 22 秒（多数波次会提前清完），超时上限 25 秒。

**BOSS**

| 项 | 值 |
|---|---|
| 数量 | **1 个**（第 2 关第 5 波清完后出场） |
| 阶段 | **3 个**，每阶段切换弹幕模式 |
| 血量 | **1250 × 进入时玩家数**（4 人 → 5000） |
| 判定范围 | **宽度 ≥ 200 px**（否则扇形弹幕大部分打空） |
| 血量重算 | **进入时算一次，中途不变** |

> ⚠️ **血量系数 1250 假设玩家平均火力 Lv4**。若玩家火力低会打很久，满级则偏快。
> **该系数为配置项，实机试玩后调整。**

**一局时长**

```
两关 10 波 × 约 22 秒  ≈ 220 秒
BOSS 战                ≈  50 秒
────────────────────────────────
合计                   ≈ 4.5 分钟
```

### 5.8 失败与重开

| 情形 | 处理 |
|---|---|
| 单个玩家阵亡 | 10 秒后自动复活（火力重置为 1） |
| **全员同时阵亡** | **本局失败，进入结算界面** |
| 一局结束 | 结算 → 返回房间 → 房主可再次开始 |
| 玩家断线 | **移除该玩家，其余人继续**（不暂停） |
| 中途加入 | **不允许**（开局后锁房） |

### 5.9 视觉规范（几何风格）

| 元素 | 实现方式 |
|---|---|
| 玩家飞船 | `draw.polygon` 几何多边形，机头朝上 |
| 敌机 | 几何多边形，**形状与颜色区分种类** |
| 子弹 | 小圆 / 短线，按 `type` 区分外观 |
| 道具 | 发光几何菱形，缓慢上下浮动 |
| BOSS | 大型多边形组合，随阶段改变颜色 |
| 外发光 | 由外向内 2~3 层递减 alpha，`BLEND_RGB_ADD` 叠加 |

## 7. 性能约束（**已实测**）

### 7.1 基准测试结果

```
--------------------------------------------------------------------

```

**测试环境**：AMD Ryzen 7 7735H（8 核 16 线程）/ 31.2 GB RAM
**测试内容**：位置推进 + 朴素 O(子弹×敌机) 碰撞检测 + 二进制快照序列化

### 7.2 由此导出的硬约束

| 约束 | 值 | 原因 |
|---|---|---|
| **同屏敌机上限** | **30** | 超过则 tick 耗时逼近 50 ms 预算 |
| **同屏子弹上限** | **300** | 同上 |
| 设计目标规模 | 4 人 + 30 敌机 + 200 子弹 | 占 8.9% 单核，余量充足 |

### 7.3 保险机制

**刷怪前必须检查当前敌机数**：

```
if 当前敌机数 >= 30:
    延后本波剩余敌机的刷新
else:
    正常刷新
```

> **不会死锁** —— 敌机被击杀后释放名额，刷新继续，只是节奏变慢。

## 11. 测试环境方案（无第二台设备）

> **2026-10-19 更新（重要）**：下面 §11.1 / §11.2 的“连本机局域网 IP”方案已被实测否定——
> Windows 会把发往本机地址的流量短路到回环（D-016）。网络指标实验改用
> **VMware VMnet1 仅主机模式 + `tc netem`**；桥接 WiFi 也已实测不可用
> （校园网拒绝 VM MAC；热点下 host→VM RTT 仍为 0.00 ms）。
> 下面保留原始分析，作为方案演进记录。

### 11.1 选定方案：本机多进程

在同一台机器上启动 1 个服务端 + N 个客户端进程，模拟多客户端环境。

| 优点 | 说明 |
|---|---|
| 零成本 | 不需要装任何虚拟机软件 |
| 覆盖逻辑与协议 | 连接、房间、同步、并发、粘包拆包**全部可验证** |
| 便于压测 | 配合机器人客户端可跑到 50+ 连接 |

### 11.2 ⚠️ 关键要求：不要连 `127.0.0.1`

**必须让客户端连接本机的局域网 IP**（如 `192.168.x.x`），而不是 `127.0.0.1`。

| 连接方式 | 流量路径 | 真实网络指标 |
|---|---|---|
| `127.0.0.1` | 操作系统内部回环，**不经过网卡** | ❌ RTT ≈ 0.1 ms，无抖动无丢包 |
| **本机局域网 IP** | 经过 WiFi 网卡与协议栈 | ✅ 可能有真实 RTT 与抖动 |

**必须在阶段 1 实测验证**（`ping` 对比两者，或用 Wireshark 看 `WLAN` 接口是否有流量）：

- RTT 在 **2~10 ms** 量级 → 走了真实网卡，**实验数据可用，不需要虚拟机**
- RTT 在 **0.1 ms** 量级 → 被系统短路为回环，**网络实验无数据 → 必须改用虚拟机方案**

### 11.3 升级选项（按需启用）

| 方案 | 成本 | 说明 |
|---|---|---|
| 虚拟机 + **仅主机模式（VMware VMnet1）** | 免费 | **已采用**：guest 独立网络栈 + `tc netem`；桥接 WiFi 已实测不可用（D-016） |
| 树莓派 Zero 2 W | 约 ¥150 | 可选：真实第二主机 |
| 临时借用他人电脑 | 免费 | 可选：真实性交叉验证，不列入主线 |
