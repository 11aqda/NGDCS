## 1. 设计目标与原则

| 目标 | 具体做法 |
|---|---|
| **体积小** | 二进制编码，避免 JSON 的键名冗余 |
| **解析快** | 定长帧头 + 直接 `struct.unpack`，不做字符串解析 |
| **可扩展** | `type` 字段预留空间；未知类型安全忽略 |
| **可调试** | 魔数校验，能快速发现"错位"；提供报文解析工具 |
| **跨平台一致** | 统一**大端序**；避免浮点，改用定点整数 |

### 1.1 为什么不用 JSON

| | 二进制 | JSON |
|---|---|---|
| 8 个玩家快照 | ≈ 89 字节 | ≈ 420 字节 |
| 解析方式 | `struct.unpack` | 字符串解析 |
| 可读性 | 差（需工具） | 好 |

**5 倍体积差 × 20 Hz × N 客户端 = 显著的带宽与 CPU 差异** —— 这正是第 6 章要量化的内容。

> JSON 编码器**会被完整实现并保留**，作为对比实验的对照组，而不是被抛弃。

## 2. 传输层：TCP

**选择理由：**

| 理由 | 说明 |
|---|---|
| 可靠性 | 游戏状态不能丢——丢一个坐标包就是一次"瞬移" |
| 有序性 | 避免旧快照覆盖新快照 |
| 实现简单 | 无需自己做重传、序号重组、拥塞控制 |
| 粘包问题 | **恰好是本题目的核心考点**，必须处理 |

**已知代价（论文中讨论）：**

- **队头阻塞**：一个丢包会阻塞后续所有数据（TCP 特性）
- **无消息边界**：必须自己解决粘包/拆包 ← 见第 3 节
- 对延迟敏感的场景，UDP 通常更优（作为对比方案在论文中讨论）

## 3. 粘包 / 拆包方案

### 3.1 问题

TCP 是**字节流**，没有消息边界。一次 `recv()` 可能拿到：

```
情况一（正常）    [完整报文A]
情况二（粘包）    [完整报文A][完整报文B]
情况三（半包）    [完整报文A的前半部分]
情况四（混合）    [A的后半][B][C的前1/3]
```

### 3.2 三种方案对比

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 定长包 | 每条消息固定长度 | 实现最简单 | 载荷长度可变时浪费严重 |
| 分隔符 | 用特殊字节（如 `\n`）分界 | 可读性好 | **二进制载荷中可能出现该字节**，需转义 |
| **长度字段** | 帧头带长度，按长度截取 | **二进制安全、无转义开销** | 帧头有固定开销 |

### 3.3 选定方案：长度字段前缀 ✅

**理由**：本协议载荷是**任意二进制**（坐标、位掩码），采用分隔符就必须转义，既增加体积又增加复杂度。长度字段是最干净的做法。

### 3.4 拆包算法（接收端）

```
维护一个接收缓冲区 buffer（bytes）

每收到一段数据:
    buffer += 新数据
    循环:
        若 len(buffer) < 帧头长度(12): 跳出（等更多数据）
        读取帧头，解析出 length
        若 length > MAX_PAYLOAD:     报错并断开（防恶意超大包）
        若 len(buffer) < 12 + length: 跳出（半包，等更多数据）
        截取完整报文 → 交给解码器
        buffer = buffer[12+length:]  （移除已消费部分）
```

**关键点**：必须**循环**处理，因为一次 `recv()` 可能包含多个完整报文。这是最容易写错的地方。

**必须有单元测试覆盖**：半包、粘包、边界（长度恰好）、超大包、空载荷。

## 4. 报文格式

### 4.1 帧头（固定 12 字节）

**所有字段均为大端序（网络字节序）。**

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 2 | `magic` | uint16 | 固定 `0x4A59`（"JY"），用于校验对齐 |
| 2 | 1 | `version` | uint8 | 协议版本，当前 `1` |
| 3 | 1 | `type` | uint8 | 消息类型，见第 5 节 |
| 4 | 4 | `seq` | uint32 | 发送方递增序列号 |
| 8 | 4 | `length` | uint32 | **载荷**字节数（不含帧头） |
| 12 | N | `payload` | bytes | 载荷，格式由 `type` 决定 |

**帧头开销分析**：空载荷时帧头占 12 字节。对小消息而言**头部开销占比很高**（例如输入包载荷仅 1 字节，头部是它的 12 倍）。
这是真实成本，也是论文里讨论「**批量合并发送**」优化的动机。

### 4.2 `seq` 的作用

| 用途 | 说明 |
|---|---|
| 请求-响应关联 | 响应包回带请求的 `seq`，用于计算 **RTT**（心跳测量） |
| 丢失检测 | 序号跳跃可判断丢包（TCP 下少见，但可验证） |
| 防重放 | 服务端拒绝重复 `seq` 的敏感请求 |

> 4 字节对游戏快照偏大，但为了 RTT 测量与统一简单，保留 uint32。

### 4.3 编码约定

| 类型 | 编码方式 |
|---|---|
| 整数 | 大端序，`struct` 格式符 `>` |
| 字符串 | `uint16 长度` + UTF-8 字节 |
| 坐标 | `uint16`，单位 **1 像素**（竞技场 960×640，够用） |
| 角度 | `uint8`，`0~255` 线性映射到 `0~360°`（分辨率约 1.4°） |
| 布尔/状态 | 位掩码 `uint8` 或 `uint16` |
| **浮点数** | **禁用** |

**为什么禁用浮点**：不同平台/版本的浮点表示与舍入可能存在差异，且 IEEE754 双精度占 8 字节。统一用定点整数，既保证一致又省体积。

### 4.4 常用位掩码

**输入位掩码（1 字节）**

| 位 | 含义 |
|---|---|
| 0 | 上 (W / ↑) |
| 1 | 下 (S / ↓) |
| 2 | 左 (A / ←) |
| 3 | 右 (D / →) |
| 4-7 | 保留 |

**玩家状态位（1 字节）**

| 位 | 含义 |
|---|---|
| 0 | 在线 |
| 1-7 | 保留 |

## 5. 消息类型表

**约定**：`0x0X` 为客户端→服务端（C→S），`0x8X` 为服务端→客户端（S→C）。最高位区分方向，便于快速判断。

### 5.1 客户端 → 服务端

| type | 名称 | 载荷 | 说明 |
|---|---|---|---|
| `0x01` | `C_AUTH` | token | 用 HTTP 登录得到的 token 认证 |
| `0x02` | `C_JOIN_ROOM` | room_code | 加入房间 |
| `0x03` | `C_LEAVE_ROOM` | — | 离开房间 |
| `0x04` | `C_INPUT` | seq, keys | 上报输入（**只发输入，不发坐标**） |
| `0x05` | `C_HEARTBEAT` | client_time | 心跳 |
| `0x06` | `C_CHAT` | text | 可选：房间内文字消息 |

### 5.2 服务端 → 客户端

| type | 名称 | 载荷 | 说明 |
|---|---|---|---|
| `0x81` | `S_AUTH_OK` | player_id | 认证成功 |
| `0x82` | `S_AUTH_FAIL` | code | 认证失败 |
| `0x83` | `S_ROOM_STATE` | room_code, players[] | 房间内玩家列表（静态信息） |
| `0x84` | `S_SNAPSHOT` | tick, players[] | **20 Hz 状态快照** |
| `0x85` | `S_PLAYER_JOIN` | player_id, name, color | 有玩家加入 |
| `0x86` | `S_PLAYER_LEAVE` | player_id | 有玩家离开 |
| `0x87` | `S_HEARTBEAT_ACK` | client_time, server_time | 心跳响应（算 RTT 用） |
| `0x88` | `S_ERROR` | code, message | 通用错误 |
| `0x89` | `S_PHASE_CHANGE` | phase, zone | 缩圈阶段推进 |
| `0x8A` | `S_PLAYER_ELIMINATED` | player_id, max_phase, survive_seconds | 玩家被淘汰 |

> **注意**：登录本身走 **HTTP**（Django），TCP 连接用 token 认证。
> 这正是 `01-系统架构.md §4.4` 所述「长连接 / 短连接分层」的落地方式。

## 6. 载荷定义

### 6.1 `C_INPUT` (0x04)

| 字段 | 类型 | 说明 |
|---|---|---|
| `seq` | uint32 | 已包含在帧头中，此处不重复 |
| `keys` | uint8 | 输入位掩码（见 §4.4） |

**载荷仅 1 字节** —— 这是帧头开销占比最高的消息。

### 6.2 `S_SNAPSHOT` (0x84) ⭐ 最高频消息

| 字段 | 类型 | 说明 |
|---|---|---|
| `tick` | uint32 | 服务端逻辑帧号（单调递增） |
| `phase` | uint16 | 当前缩圈阶段编号 |
| `zone` | 4 × uint16 | 当前场地边界 `x1, y1, x2, y2` |
| `player_count` | uint8 | 玩家数 |
| `players[]` | 见下 | 每个玩家 9 字节 |

**每个玩家条目（9 字节）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `player_id` | uint16 | 玩家 ID |
| `x` | uint16 | 横坐标（像素） |
| `y` | uint16 | 纵坐标（像素） |
| `angle` | uint8 | 朝向（0~255 → 0~360°） |
| `color` | uint8 | 调色板索引 |
| `flags` | uint8 | 状态位（在线 / 界外 / 已淘汰） |

**体积计算（8 人）**

```
帧头           12 字节
tick            4 字节
phase           2 字节
zone            8 字节
player_count    1 字节
8 × 9          72 字节
─────────────────────
合计           99 字节

20 Hz × 99 B = 1980 B/s ≈ 1.9 KB/s  （每客户端）
```

**对比 JSON 版本**（键名冗余）：

```json
{"tick":1,"phase":3,"zone":[100,80,860,560],
 "players":[{"id":1,"x":100,"y":200,"a":90,"c":3,"f":1}, ...]}
```
约 470 字节 → **9.4 KB/s**，**相差约 5 倍**。

> **值得注意**：`zone` 有 8 字节，但它**每 30 秒才变化一次**，
> 却要随 20 Hz 的快照重复发送 600 次。这是「**全量 vs 增量同步**」讨论的绝佳素材（见 `03-实验清单.md` E6）。
> 在 8 人场景下全量仍只有 99 字节，**增量收益有限** —— 而这个结论本身就是实验要验证的内容。

### 6.3 `S_HEARTBEAT_ACK` (0x87)

| 字段 | 类型 | 说明 |
|---|---|---|
| `client_time` | uint32 | 原样回带客户端时间戳（毫秒） |
| `server_time` | uint32 | 服务端时间戳 |

**客户端据此计算 RTT**：`RTT = 当前时间 - client_time`
这是实验数据里**延迟指标的唯一来源**。

### 6.4 `S_ROOM_STATE` (0x83)

| 字段 | 类型 | 说明 |
|---|---|---|
| `room_code` | string | 房间码 |
| `player_count` | uint8 | 玩家数 |
| `players[]` | 见下 | 每个玩家不定长 |

**玩家条目**

| 字段 | 类型 | 说明 |
|---|---|---|
| `player_id` | uint16 | |
| `name` | string | 昵称（长度前缀 + UTF-8） |
| `color` | uint8 | 配色索引 |

---

### 6.5 `S_PHASE_CHANGE` (0x89)

**触发时机**：场地收缩进入新阶段时，服务端向房间内所有客户端广播。

| 字段 | 类型 | 说明 |
|---|---|---|
| `phase` | uint16 | 新的阶段编号 |
| `x1` | uint16 | 新边界左 |
| `y1` | uint16 | 新边界上 |
| `x2` | uint16 | 新边界右 |
| `y2` | uint16 | 新边界下 |
| `next_shrink_ms` | uint32 | 距下次收缩的毫秒数（供客户端做倒计时动画） |

**为什么单独发一条消息**：快照里已经带了 `zone`，但**事件**（"刚进入第 N 阶段"）需要
一次性触发客户端播放动画/音效，与「当前值是多少」是两回事。这是**状态同步与事件同步并存**的典型场景。

---

### 6.6 `S_PLAYER_ELIMINATED` (0x8A)

**触发时机**：某玩家出界超过宽限时间，被判定淘汰。

| 字段 | 类型 | 说明 |
|---|---|---|
| `player_id` | uint16 | 被淘汰的玩家 |
| `max_phase` | uint16 | 该玩家到达的最高阶段 |
| `survive_seconds` | uint32 | 存活时长 |

> **注意**：成绩由**服务端**写入，客户端只负责展示，不上报（见 `04-API接口设计.md §7.1`）。
> 这是「服务端权威」原则从游戏状态延伸到成绩记录的体现。

## 7. 心跳与超时

| 参数 | 值 | 说明 |
|---|---|---|
| 客户端心跳间隔 | **5 s** | 发 `C_HEARTBEAT` |
| 服务端超时判定 | **15 s** | 超过则判定断线，清理会话 |
| 超时倍数 | 3 × 心跳间隔 | 容忍偶发丢包与瞬时卡顿 |

**服务端逻辑**：每个连接维护 `last_recv_time`，游戏循环每秒检查一次：

```
若 now - last_recv_time > 15s:
    关闭连接 → 广播 S_PLAYER_LEAVE → 清理房间内状态
```

**为什么超时是心跳的 3 倍**：单次心跳丢失不应导致误判断线。

## 8. 错误码

| 码 | 名称 | 说明 |
|---|---|---|
| `0x01` | `ERR_AUTH_FAILED` | token 无效或过期 |
| `0x02` | `ERR_ROOM_NOT_FOUND` | 房间码不存在 |
| `0x03` | `ERR_ROOM_FULL` | 房间人数已满 |
| `0x04` | `ERR_VERSION_MISMATCH` | 协议版本不匹配 |
| `0x05` | `ERR_MALFORMED` | 报文格式错误（长度、魔数、载荷解析失败） |
| `0x06` | `ERR_NOT_IN_ROOM` | 未加入房间却发送房间内消息 |
| `0x07` | `ERR_RATE_LIMITED` | 消息频率超限（防洪） |

## 9. 版本协商

**简化方案**（不做事后协商）：

1. 客户端在 `C_AUTH` 载荷中携带自己的 `version`
2. 服务端比对，不匹配则回 `S_ERROR(ERR_VERSION_MISMATCH)` 并断开
3. 帧头中的 `version` 字段用于**逐包校验**，双重保险

**理由**：局域网客户端与服务端同步部署，不需要复杂协商。但保留字段以便将来扩展。

## 10. 协议状态机

```
        连接建立
            │
            ▼
      ┌───────────┐
      │  未认证    │──C_AUTH──▶ 校验 token
      └───────────┘                 │
                          ┌─────────┴─────────┐
                       成功                 失败
                          │                   │
                          ▼                   ▼
                   ┌───────────┐      S_AUTH_FAIL + 断开
                   │  已认证    │
                   └─────┬─────┘
                         │ C_JOIN_ROOM
                         ▼
                   ┌───────────┐
                   │  房间中    │◀──┐
                   └─────┬─────┘   │
                         │         │ 收到 S_SNAPSHOT /
                   游戏进行中       │ 收发输入
                         │         │
                         └─────────┘
```

**状态约束**：未认证的连接只能发 `C_AUTH`；未进房间的连接发 `C_INPUT` 返回 `ERR_NOT_IN_ROOM`。

## 11. 一次完整交互示例

```
① 客户端 HTTP 登录（Django）
   POST /api/login  {"username":"anria","password":"***"}
   ← 200 {"token":"eyJhbGci...", "player_id":42}

② TCP 建立连接 → 发 C_AUTH(token)
   字节流: 4A 59 | 01 | 01 | 00 00 00 01 | 00 00 00 24 | <token 36字节>

③ ← S_AUTH_OK(player_id=42)

④ → C_JOIN_ROOM("LC5WTF")
⑤ ← S_ROOM_STATE(room_code="LC5WTF", players=[...])
⑥ ← S_PLAYER_JOIN(...)  （其他人加入时）

⑦ 进入游戏，20 Hz 循环：
   → C_INPUT(keys=0b0001)   ← 按了"上"
   ← S_SNAPSHOT(tick=1, players=[...])

⑧ 每 5 秒心跳：
   → C_HEARTBEAT(client_time=12345678)
   ← S_HEARTBEAT_ACK(client_time=12345678, server_time=...)
   客户端算得 RTT
```
