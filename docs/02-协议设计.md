## 1. 设计目标与原则

| 目标 | 具体做法 |
|---|---|
| **体积小** | 二进制编码，避免 JSON 的键名冗余 |
| **解析快** | 定长帧头 + 直接 `struct.unpack`，不做字符串解析 |
| **可扩展** | `type` 字段预留空间；未知类型安全忽略 |
| **可调试** | 魔数校验，能快速发现「错位」；提供报文解析工具 |
| **跨平台一致** | 统一**大端序**；避免浮点，改用定点整数 |

### 1.1 为什么不用 JSON

| | 二进制 | JSON |
|---|---|---|
| 设计目标快照（**含 5 道具**的纸面推算） | ≈ **1974 字节** | ≈ **11000 字节** |
| **E1 实测**（30/200、**无道具**） | **1927 字节** | **9048 字节** |
| 解析方式 | `struct.unpack` | 字符串解析 |
| 可读性 | 差（需工具） | 好 |

**实测体积差 4.7 倍**（E1，2026-10-26）× 20 Hz × N 客户端 = 显著的带宽与 CPU 差异。

> ⚠️ **两行口径不同，不可混用**：第一行是 `§7.4` 的**设计推算**（二进制侧含 5 个道具）；
> 第二行才是**实测**（不带道具）。早期文档引用的「5.6 倍」出自第一行，
> **已被 E1 的 4.7 倍取代**。

> JSON 编码器**会被完整实现并保留**，作为对比实验的对照组，而不是被抛弃。

## 2. 传输层：TCP

**选择理由：**

| 理由 | 说明 |
|---|---|
| 可靠性 | 游戏状态不能丢 —— 丢一个坐标包就是一次「瞬移」 |
| 有序性 | 避免旧快照覆盖新快照 |
| 实现简单 | 无需自己做重传、序号重组、拥塞控制 |
| 粘包问题 | **恰好是本题目的核心考点**，必须处理 |

**已知代价（论文中讨论）：**

- **队头阻塞**：一个丢包会阻塞后续所有数据（TCP 特性）
- **无消息边界**：必须自己解决粘包/拆包 ← 见第 3 节
- 对延迟敏感的场景，UDP 通常更优（作为对比方案在论文中讨论）

## 3. 粘包 / 拆包方案

### 3.1 问题

TCP 是**字节流**，没有消息边界。一次 `recv()` 可能拿到：

```
情况一（正常）    [完整报文A]
情况二（粘包）    [完整报文A][完整报文B]
情况三（半包）    [完整报文A的前半部分]
情况四（混合）    [A的后半][B][C的前1/3]
```

### 3.2 三种方案对比

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 定长包 | 每条消息固定长度 | 实现最简单 | 载荷长度可变时浪费严重 |
| 分隔符 | 用特殊字节（如 `\n`）分界 | 可读性好 | **二进制载荷中可能出现该字节**，需转义 |
| **长度字段** | 帧头带长度，按长度截取 | **二进制安全、无转义开销** | 帧头有固定开销 |

### 3.3 选定方案：帧头内的长度字段 ✅

**理由**：本协议载荷是**任意二进制**（坐标、位掩码、血量），采用分隔符就必须转义，既增加体积又增加复杂度。长度字段是最干净的做法。

> ⚠️ **措辞澄清（2026-10-26）**：长度字段是**帧头的一部分**（12 B 帧头内的 `length`，偏移 8），
> **不是帧头前面再加一个独立的 4 B 前缀**。「长度前缀」这个叫法容易让人误解，
> 后面统一说「帧头内的长度字段」。第 2 步的临时设计确实用过 4 B 纯长度前缀，
> 第 4 步扩展成 12 B 帧头后就不存在了（见 D-017、D-019）。

### 3.4 拆包算法（接收端）

```
维护一个接收缓冲区 buffer（bytes）

每收到一段数据:
    buffer += 新数据
    循环:
        若 len(buffer) < 帧头长度(12): 跳出（等更多数据）
        读取帧头，解析出 length
        若 length > MAX_PAYLOAD:     报错并断开（防恶意超大包）
        若 len(buffer) < 12 + length: 跳出（半包，等更多数据）
        截取完整报文 → 交给解码器
        buffer = buffer[12+length:]  （移除已消费部分）
```

**关键点**：必须**循环**处理，因为一次 `recv()` 可能包含多个完整报文。这是最容易写错的地方。

**必须有单元测试覆盖**：半包、粘包、边界（长度恰好）、超大包、空载荷、一次收到 N 个报文。

> **已实现（2026-10-19）**：`tests/test_framing.py` **19 个用例**覆盖上述清单 + magic / version / type / seq 校验；
> 运行 `python -X utf8 -m unittest discover -s tests -t . -v`。
> 第 4 步已按 12 字节帧头更新（`protocol/framing.py`）。

## 4. 报文格式

### 4.1 帧头（固定 12 字节）

**所有字段均为大端序（网络字节序）。**

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 2 | `magic` | uint16 | 固定 `0x4A59`，用于校验对齐 |
| 2 | 1 | `version` | uint8 | 协议版本，当前 `1` |
| 3 | 1 | `type` | uint8 | 消息类型，见第 5 节 |
| 4 | 4 | `seq` | uint32 | 发送方递增序列号 |
| 8 | 4 | `length` | uint32 | **载荷**字节数（不含帧头） |
| 12 | N | `payload` | bytes | 载荷，格式由 `type` 决定 |

**帧头开销分析**：空载荷时帧头占 12 字节。对小消息而言**头部开销占比很高**（例如输入包载荷仅 1 字节，头部是它的 12 倍）。
这是真实成本，也是论文里讨论「**批量合并发送**」优化的动机。

> **已实现（2026-10-19）**：`protocol/framing.py` 中 `HEADER = struct.Struct("!HBBII")`；
> `tests/test_framing.py` 19 个用例覆盖 12 B 帧头、magic / version 校验、半包 / 粘包 / 超大包。

### 4.2 `seq` 的作用

| 用途 | 说明 |
|---|---|
| 请求-响应关联 | 响应包回带请求的 `seq`，用于计算 **RTT**（心跳测量） |
| 丢失检测 | 序号跳跃可判断丢包（TCP 下少见，但可验证） |
| 防重放 | 服务端拒绝重复 `seq` 的敏感请求 |

### 4.3 编码约定

| 类型 | 编码方式 |
|---|---|
| 整数 | 大端序，`struct` 格式符 `>` |
| 字符串 | `uint16 长度` + UTF-8 字节 |
| 坐标 | `uint16`，单位 **1 像素** |
| 角度 | `uint8`，`0~255` 线性映射到 `0~360°`（分辨率约 1.4°）；**0° = 正上方，顺时针**（见 §4.5） |
| 布尔/状态 | 位掩码 `uint8` 或 `uint16` |
| **浮点数** | **禁用** |

**为什么禁用浮点**：不同平台/版本的浮点表示与舍入可能存在差异，且双精度占 8 字节。统一用定点整数，既保证一致又省体积。

### 4.4 ⚠️ 坐标值域问题（已发现的真实 Bug）

**背景**：基准测试时发现 —— 子弹飞出屏幕后坐标为**负数**，而 `uint16` 只能表示 `0~65535`：

```
struct.error: 'H' format requires 0 <= number <= 65535
```

**三种解法：**

| 方案 | 说明 | 评价 |
|---|---|---|
| **A. 出屏即剔除** | 坐标越界的实体**不同步**，客户端据此删除该实体 | ✅ **采用** |
| B. 改用有符号 `int16` | 支持 `-32768~32767` | 浪费一半值域 |
| C. 序列化时截断 | 最简单 | ❌ 数据错误 |

**采用方案 A**，并且它带来两个额外好处：

1. **省带宽** —— 越界实体本来就不需要渲染
2. **客户端逻辑更简单** —— 「快照里没有的实体」= 「该删掉了」（**快照即全量真相**）

> **设计原则确立**：**快照是全量真相**。客户端每收到一帧快照，就**完全以快照为准**重建本地实体表
> —— 快照里没有的实体一律删除。这样无需额外的「删除实体」消息。

### 4.5 常用位掩码

**输入位掩码（1 字节）**

| 位 | 含义 |
|---|---|
| 0 | 左 (A / ←) |
| 1 | 右 (D / →) |
| 2-7 | 保留 |

> 竖版飞机大战只需左右移动，射击是**自动**的（服务端根据冷却自动生成子弹），
> 因此输入载荷**只有 1 字节** —— 这是帧头开销占比最高的消息。

**玩家状态位（1 字节）**

| 位 | 含义 |
|---|---|
| 0 | 在线 |
| 1 | 阵亡中（等待复活） |
| 2 | 无敌中（受击后闪烁） |
| 3-7 | 保留 |

**子弹类型（1 字节）**

| 值 | 含义 |
|---|---|
| `0x01` | 玩家 Lv1 子弹 |
| `0x02` | 玩家 Lv2 子弹 |
| `0x03` | 玩家 Lv3 双发 |
| `0x04` | 玩家 Lv4 双发 |
| `0x05` | 玩家 Lv5 扇形 |
| `0x11` | 敌方直线散射弹 |
| `0x12` | 敌方扇形弹 |
| `0x13` | 敌方追踪弹 |
| `0x21` | BOSS 弹幕 |

> **⚠️ 角度基准（2026-10-24 补充，此前未定义）**：**0° = 正上方**，**顺时针**增加 ——
> `0` = 正上、`64` = 正右、`128` = 正下、`192` = 正左。
>
> **为什么 0° 在正上而不是数学习惯的正右**：竖版飞机大战里「向上」是主方向
> （玩家子弹向上、敌机向下），0 放在正上时最常见的两个方向恰好是 `0` 和 `128`，
> 都在整数档上；若 0 放在正右，玩家子弹就得写成 `192`，反直觉且容易写错。
>
> **量化**：占位实体阶段把 `0~255` 量化到 **8 个方向**（每档 32），全整数无三角函数
> （`02 §4.3` 禁用浮点）；真实弹幕阶段（散射 / 扇形 / 追踪）再按需要细化。
> 实现见 `server/entities.py` 的 `angle_to_delta()`。

**敌机类型（1 字节）**

| 值 | 含义 |
|---|---|
| `0x01` | 直线俯冲 |
| `0x02` | 横向移动 |
| `0x03` | 追踪玩家 |
| `0xFF` | **BOSS** |

**道具类型（1 字节）**

| 值 | 含义 |
|---|---|
| `0x01` | 火力道具 |

## 5. 消息类型表

**约定**：`0x0X` 为客户端→服务端（C→S），`0x8X` 为服务端→客户端（S→C）。最高位区分方向，便于快速判断。

### 5.1 客户端 → 服务端

| type | 名称 | 载荷 | 说明 |
|---|---|---|---|
| `0x01` | `C_AUTH` | version, token | 用 HTTP 登录得到的 token 认证 |
| `0x02` | `C_JOIN_ROOM` | room_code | 加入房间 |
| `0x03` | `C_LEAVE_ROOM` | — | 离开房间 |
| `0x04` | `C_READY` | ready | 准备 / 取消准备 |
| `0x05` | `C_START_GAME` | — | 房主开始游戏 |
| `0x06` | `C_INPUT` | keys | 上报输入（**只发输入，不发坐标**） |
| `0x07` | `C_HEARTBEAT` | client_time | 心跳 |

### 5.2 服务端 → 客户端

| type | 名称 | 载荷 | 说明 |
|---|---|---|---|
| `0x81` | `S_AUTH_OK` | player_id, nickname | 认证成功 |
| `0x82` | `S_AUTH_FAIL` | code | 认证失败 |
| `0x83` | `S_ROOM_STATE` | room_code, players[] | 房间内玩家列表（静态信息） |
| `0x84` | `S_SNAPSHOT` | 见 §6.2 | **20 Hz 全量状态快照** ⭐ |
| `0x85` | `S_PLAYER_JOIN` | player_id, nickname, color | 有玩家加入房间 |
| `0x86` | `S_PLAYER_LEAVE` | player_id | 有玩家离开房间 |
| `0x87` | `S_HEARTBEAT_ACK` | client_time, server_time | 心跳响应（算 RTT 用） |
| `0x88` | `S_ERROR` | code, message | 通用错误 |
| `0x89` | `S_GAME_START` | level, wave | 开局 / 关卡开始 |
| `0x8A` | `S_WAVE_START` | level, wave, enemy_total | 新一波开始 |
| `0x8B` | `S_BOSS_SPAWN` | boss_id, hp, phase | BOSS 出场 |
| `0x8C` | `S_BOSS_PHASE` | phase | BOSS 切换阶段 |
| `0x8D` | `S_PLAYER_DOWN` | player_id, revive_ms | 玩家阵亡 |
| `0x8E` | `S_PLAYER_REVIVE` | player_id | 玩家复活 |
| `0x8F` | `S_GAME_OVER` | result, scores[] | 本局结束（全员阵亡） |

> **阶段 1 临时消息**：`S_WELCOME = 0x7C` 只用于占位阶段分配 `player_id / color`，
> 正式认证成功后由 `S_AUTH_OK (0x81)` 返回玩家信息；第 10 步替换。

> **已实现**：`C_INPUT (0x06)`、`C_HEARTBEAT (0x07)`、`S_HEARTBEAT_ACK (0x87)`（2026-10-23，D-023）；
> **`C_AUTH (0x01)`、`S_AUTH_OK (0x81)`、`S_AUTH_FAIL (0x82)`**（2026-11-01，步骤 10b / D-031）。
> 其余类型待步骤 11（游戏内容）实现。

#### 认证消息的字节布局（2026-11-01 补定义）

上面 §5.1/§5.2 只给了消息类型，没给载荷格式。实现时定死如下（都在 `protocol/messages.py`）：

| 消息 | 载荷布局 | 长度 |
|---|---|---|
| `C_AUTH` | `version` uint8 + `token` 变长 ASCII | 1 + 1~64 B |
| `S_AUTH_OK` | `player_id` uint16 + `nickname_len` uint8 + `nickname` UTF-8 | 3 + 1~20 B |
| `S_AUTH_FAIL` | `code` uint8（`0x01` = `ERR_AUTH_FAILED`） | 1 B |

**三处刻意的设计**：

1. **token 用变长而不是定长 64 字节** —— 现在 HTTP 层发的是 64 位十六进制串，
   但将来换短 token 或换格式时**不用动协议版本**
2. **`nickname` 长度按字节算**（不是字符数），且带显式长度前缀 ——
   中文昵称是 UTF-8 多字节，只靠"载荷总长减去头"在将来加字段时会立刻失效
3. **畸形载荷一律抛 `ProtocolError`，绝不降级成"匿名登录"** ——
   否则一个写错的客户端会静默地以匿名身份进服，问题极难定位

> 认证是**可选**的：不发 `C_AUTH` 的连接就是匿名玩家（机器人、压测工具都不发）。
> 只有"已认证 + 开了 `--persist-scores`"的连接才在断开时结算写库。

### 5.3 ⭐ 状态同步 vs 事件同步

本协议**同时使用两种同步方式**，这是设计上的一个重要区分：

| 类型 | 消息 | 特点 |
|---|---|---|
| **状态同步** | `S_SNAPSHOT` | 周期性发送「**现在是什么样**」，丢失一帧无妨（下一帧补上） |
| **事件同步** | `S_WAVE_START`、`S_BOSS_SPAWN`、`S_PLAYER_DOWN` 等 | 一次性发送「**刚刚发生了什么**」，用于触发客户端动画/音效/UI |

**为什么要分开**：

- 快照里已经有 `wave` 字段，能表达「现在是第 3 波」
- 但客户端还需要知道「**刚刚进入**第 3 波」这个**瞬间**，才能播放波次提示动画
- 「值是多少」和「刚刚变成这个值」是两件事

> **这是一个可以在论文里展开讨论的设计点。**

## 6. 载荷定义

### 6.1 `C_INPUT` (0x06)

| 字段 | 类型 | 说明 |
|---|---|---|
| `keys` | uint8 | 输入位掩码（见 §4.5） |

**载荷仅 1 字节** —— 帧头（12 字节）是它的 12 倍。

> **已实现（2026-10-23）**：`INPUT = struct.Struct("!B")`；
> `pack_keys()` / `unpack_keys()` 只校验长度与值域，**保留位由业务层用 `KEYS_MASK` 掩掉**
> （前向兼容：将来加「上下移动」bit 2 时，旧服务端不会因不认识新位而断连）。
> 客户端定频 **20 Hz** 上报「当前按住什么」（状态而非事件，丢一帧下一帧自动纠正），
> 服务端按 keys 移动玩家（`server/movement.py`，整数 15 px/tick = 300 px/s），
> 并给输入设 **0.5 s 保质期**防止客户端失联后「幽灵移动」。
> 实测：10 个机器人 × 20 Hz → 服务端统计 `in 198~203/s`。详见 D-023。

> 敌机 / 子弹 / 道具计数固定为 0，`unpack_snapshot()` 会拒绝非 0 计数。完整格式后续扩展。

**敌机条目（9 字节）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `enemy_id` | uint16 | 敌机 ID |
| `x` | uint16 | 横坐标 |
| `y` | uint16 | 纵坐标 |
| `type` | uint8 | 敌机类型（`0xFF` = BOSS） |
| `hp` | uint16 | 当前血量 |

**子弹条目（8 字节）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `owner_id` | uint16 | 发射者（敌方子弹为 `0`） |
| `x` | uint16 | 横坐标 |
| `y` | uint16 | 纵坐标 |
| `type` | uint8 | 子弹类型（决定外观与伤害） |
| `angle` | uint8 | **飞行方向**（0~255 → 0~360°） |

> **`angle` 是必需的** —— 敌方弹幕方向各异（散射、扇形、追踪），客户端必须知道子弹往哪飞。

**道具条目（7 字节）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `item_id` | uint16 | 道具 ID |
| `x` | uint16 | 横坐标 |
| `y` | uint16 | 纵坐标 |
| `type` | uint8 | 道具类型 |

> **已实现（2026-10-24）**：四类条目已在 `protocol/snapshot.py` 全部落地，
> 条目大小断言写进了 `tests/test_snapshot.py`（**13 / 11 / 9 / 8 / 7 B**）——
> 差一个字节整条流就会错位。`pack_snapshot()` 会校验各计数是否超出
> `uint8` / `uint16` 上限；`boss_present` 由敌机列表里的 `0xFF` **推导**而不单独传参，
> 这样它和敌机类型永远不会互相矛盾。

### 6.3 快照体积计算（设计目标）

```
帧头                                        12 B
快照头                                      13 B
  tick(4) level(1) wave(1) wave_state(1)
  player_count(1) enemy_count(1) bullet_count(2)
  item_count(1) boss_present(1)

玩家   4 × 11 B                             44 B
敌机  30 ×  9 B                            270 B
子弹 200 ×  8 B                           1600 B
道具   5 ×  7 B                             35 B
────────────────────────────────────────────────
合计                                    ≈ 1974 B

@ 20 Hz = 39.5 KB/s  （每客户端）
```

> **已实现并实测（2026-10-24）**：`protocol/snapshot.py` 现在实现了全部四类条目，
> `server/entities.py` 用**占位实体**（无 AI、匀速直线）把实体数变成可配自变量。
>
> 4 人 + 30 敌机 + 200 子弹 + **0 道具**的实测 **快照载荷 = 1927 B**，
> 含 12 B 帧头则是 **1939 B/帧**，@20 Hz = **38.8 KB/s per 客户端** ——
> 与上表 `13 + 44 + 270 + 1600 = 1927` **逐字节吻合**
> （上表的 1974 B 多了 5 个道具的 35 B，别把两个数搞混）。
>
> 一个重要推论：**子弹条目没有唯一 ID**（只有 `owner_id`），所以客户端
> **无法按实体逐帧匹配子弹**，也就**不能对子弹做插值** —— 这是协议设计的代价
> （省下 2 B/颗 × 200 颗 = 400 B/帧，占快照 20%），不是实现遗漏。
> 玩家与敌机都有 id，不受影响。

**对比 JSON 版本**：

```json
{"tick":1234,"level":1,"wave":3,"players":[{"id":1,"x":100,"y":800,"power":3,"c":2,"f":1,"score":120}, ...],
 "enemies":[{"id":10,"x":200,"y":300,"t":1,"hp":2}, ...],
 "bullets":[{"o":1,"x":100,"y":780,"t":3,"a":0}, ...], ...}
```
约 **11000 字节** → **220 KB/s**，**相差约 5.6 倍**。

> ⚠️ **这是含 5 道具的纸面推算**（与上表第一行同源）。
> **E1 实测（30/200、无道具）为 9048 字节 / 178 KB/s，4.7 倍** —— 以实测为准。

## 7. 心跳与超时

| 参数 | 值 | 说明 |
|---|---|---|
| 客户端心跳间隔 | **5 s** | 发 `C_HEARTBEAT` |
| 服务端超时判定 | **15 s** | 超过则判定断线，清理会话 |
| 超时倍数 | 3 × 心跳间隔 | 容忍偶发丢包与瞬时卡顿 |

**服务端逻辑**：每个连接维护 `last_recv_time`，游戏循环每秒检查一次：

```
若 now - last_recv_time > 15s:
    关闭连接 → 广播 S_PLAYER_LEAVE → 清理房间内状态
    （若房间空了 → 销毁房间；若在局内 → 其余玩家继续，不暂停）
```

**为什么超时是心跳的 3 倍**：单次心跳丢失不应导致误判断线。

> **已实现（2026-10-23）**：客户端每 5 s 发 `C_HEARTBEAT`，服务端回 `S_HEARTBEAT_ACK`
> 并把 `client_time` **原样回显** —— RTT 完全由客户端本地计算，**不依赖两端时钟同步**
> （时间戳用 `time.monotonic()` 毫秒取低 32 位，差值用无符号 `(now - sent) & 0xFFFFFFFF`，
> 天然容忍回绕）。服务端超时检查**每秒一次而非每 tick**；`check_timeouts()` 只判定、
> 关闭由 `tick_loop` 做、**清理统一在 `handle_client` 的 `finally`**（唯一清理点，避免两处改同一字典）。
> 连接维护的字段在代码里叫 `last_recv_at`，且由**任何**收到的消息更新，不只是心跳。
>
> `--timeout 0` 可关闭超时判定，用于「纯广播」基线实验（分离变量）。
> 实测：`--timeout 5` 下心跳间隔 2 s 活满 12 s；什么都不发约 6 s 被踢。
>
> ⚠️ 本阶段的 `S_PLAYER_LEAVE (0x86)` **未实现**：§4.4 的「快照是全量真相」已覆盖该语义
> （玩家断开后不再出现在下一帧快照里，客户端自然删除），
> 事件同步留给游戏内容阶段（见 §5.3）。详见 D-023。

## 8. 错误码

| 码 | 名称 | 说明 |
|---|---|---|
| `0x01` | `ERR_AUTH_FAILED` | token 无效或过期 |
| `0x02` | `ERR_ROOM_NOT_FOUND` | 房间码不存在 |
| `0x03` | `ERR_ROOM_FULL` | 房间人数已满 |

| `0x09` | `ERR_NOT_HOST` | 非房主却尝试开始游戏 |

## 9. 版本协商

**简化方案**（不做事后协商）：

1. 客户端在 `C_AUTH` 载荷中携带自己的 `version`
2. 服务端比对，不匹配则回 `S_ERROR(ERR_VERSION_MISMATCH)` 并断开
3. 帧头中的 `version` 字段用于**逐包校验**，双重保险

**理由**：局域网客户端与服务端同步部署，不需要复杂协商。但保留字段以便将来扩展。

## 10. 协议状态机

```
        连接建立
            │
            ▼
      ┌───────────┐
      │  未认证    │──C_AUTH──▶ 校验 token
      └───────────┘                 │
                          ┌─────────┴─────────┐
                       成功                 失败
                          │                   │
                          ▼                   ▼
                   ┌───────────┐      S_AUTH_FAIL + 断开
                   │  已认证    │
                   └─────┬─────┘
                         │ C_JOIN_ROOM
                         ▼
                   ┌───────────┐
                   │  房间中    │◀──┐
                   │  (未开局)  │   │
                   └─────┬─────┘   │
                         │ C_START_GAME（仅房主）
                         ▼         │
                   ┌───────────┐   │
                   │  对局中    │───┘ 全员阵亡 → 回合结束
                   │  20Hz 快照 │
                   └───────────┘
```

**状态约束**：

| 当前状态 | 允许发送 | 违规响应 |
|---|---|---|
| 未认证 | 仅 `C_AUTH` | 断开连接 |
| 已认证 | `C_JOIN_ROOM`、`C_HEARTBEAT` | `ERR_NOT_IN_ROOM` |
| 房间中（未开局） | `C_READY`、`C_START_GAME`、`C_LEAVE_ROOM` | 忽略 |
| 对局中 | `C_INPUT`、`C_HEARTBEAT` | `ERR_GAME_IN_PROGRESS` |

## 11. 一次完整交互示例

```
① 客户端 HTTP 登录（Django）
   POST /api/login  {"username":"anria","password":"***"}
   ← 200 {"token":"eyJhbGci...", "player_id":42}

② TCP 建立连接 → 发 C_AUTH(version=1, token)
   字节流: 4A 59 | 01 | 01 | 00 00 00 01 | 00 00 00 25 | <version + token>

③ ← S_AUTH_OK(player_id=42, nickname="anria")

④ → C_JOIN_ROOM("LC5WTF")
⑤ ← S_ROOM_STATE(room_code="LC5WTF", players=[...])
⑥ ← S_PLAYER_JOIN(...)  （其他人加入时）

⑦ → C_READY(1)
   ← S_ROOM_STATE(...)  （房间状态刷新）

⑧ → C_START_GAME()   （仅房主）
   ← S_GAME_START(level=1, wave=1)
   ← S_WAVE_START(level=1, wave=1, enemy_total=5)

⑨ 进入 20 Hz 循环：
   → C_INPUT(keys=0b01)        ← 按了「左」
   ← S_SNAPSHOT(tick=1, level=1, wave=1, players=[...], enemies=[...], bullets=[...], items=[])

   → C_INPUT(keys=0b10)        ← 按了「右」
   ← S_SNAPSHOT(tick=2, ...)

⑩ 波次推进：
   ← S_WAVE_START(level=1, wave=2, enemy_total=8)

⑪ 玩家中弹阵亡：
   ← S_PLAYER_DOWN(player_id=42, revive_ms=10000)
   ← S_SNAPSHOT(...)           ← 该玩家 flags 的第 1 位置 1
   ... 10 秒后 ...
   ← S_PLAYER_REVIVE(player_id=42)

⑫ BOSS 出场（第 2 关第 5 波清完后）：
   ← S_BOSS_SPAWN(boss_id=1000, hp=5000, phase=1)
   ← S_BOSS_PHASE(phase=2)
   ← S_BOSS_PHASE(phase=3)

⑬ 全员阵亡：
   ← S_GAME_OVER(result=0, scores=[...])
   （服务端随后把分数直接写入数据库）

⑭ 每 5 秒心跳：
   → C_HEARTBEAT(client_time=12345678)
   ← S_HEARTBEAT_ACK(client_time=12345678, server_time=...)
   客户端算得 RTT
```
