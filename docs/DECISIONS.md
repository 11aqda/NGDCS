## D-001 数据库驱动用 PyMySQL，而不是 mysqlclient

- **日期**：2026-10-10
- **决定**：Django 连接 MySQL 使用 `PyMySQL`，配合 `pymysql.install_as_MySQLdb()`
- **理由**：
  1. **Windows 友好** —— `mysqlclient` 是 C 扩展，Windows 上安装需要编译环境（Visual C++ Build Tools），经常装不上；PyMySQL 是纯 Python，`pip install` 即可
  2. 本机是 Windows 开发环境，优先保证「装得上、跑得通」
- **备选方案**：`mysqlclient`（性能更好，但 Windows 安装门槛高）
- **代价 / 风险**：
  - PyMySQL 是纯 Python 实现，批量操作性能约为 mysqlclient 的 1/2 ~ 1/5
  - 需要额外安装 `cryptography`（MySQL 8 的 `caching_sha2_password` 认证需要）
- **落地方式**：项目包 `__init__.py` 中

  ```python
  import pymysql
  pymysql.install_as_MySQLdb()
  ```

- **答辩可能被问**：为什么不用官方推荐的 mysqlclient？
  → 答：Windows 环境下 C 扩展编译门槛高，PyMySQL 保证可移植性；性能差距在当前并发量级下可以忽略。

## D-002 降 Django 到 5.2 LTS，而不是升级 MySQL 到 8.4

- **日期**：2026-10-10
- **背景**：venv 中安装的 Django 6.1.2 连接 MySQL 8.0.41 时直接抛错：

  ```
  django.db.utils.NotSupportedError: MySQL 8.4 or later is required (found 8.0.41).
  ```

  经查 Django 官方 ticket [#36624](https://code.djangoproject.com/ticket/36624)：**Django 6.1 起将 MySQL 最低版本提高到 8.4**。这是框架源码里的硬性检查，没有任何配置项可以绕过。

- **决定**：把 venv 中的 Django 降到 **5.2 LTS**（实际安装 5.2.18）
- **理由**：
  1. **动作最小** —— 只更换 venv 中的一个包；升级 MySQL 需要下载 MSI、运行图形安装器、重启服务，并承担数据迁移风险
  2. Django 5.2 是 **LTS 版本**，维护到 2028 年，稳定性有保障
  3. Django 5.2 支持 MySQL 8.0.11+，与本机 8.0.41 匹配
  4. 毕设周期内不需要 Django 6.x 的新特性
- **备选方案**：升级 MySQL 到 8.4 LTS
- **代价 / 约束**：
  - ⚠️ **在升级 MySQL 之前，不能把 Django 升到 6.x**
  - 系统 Python 里另有一个 Django 5.0.3，与 venv 隔离；**运行项目必须使用 venv 的解释器**
- **验证结果**：降级后实测通过

  ```
  ('8.0.41', 'myproject', 'django_user@localhost', 'utf8mb4_unicode_ci')
  Django version : 5.2.18
  ```

- **答辩可能被问**：为什么不用最新版 Django？
  → 答：框架版本应在满足需求的前提下选择稳定版；5.2 是 LTS，且与本机数据库版本兼容，避免了升级数据库带来的额外风险。

## D-003 渲染采用几何多边形飞船，不使用位图素材

- **日期**：2026-10-10
- **决定**：玩家角色用 `pygame.draw.polygon` 绘制几何多边形（箭头/三角），机头指向行进方向
- **理由**：
  1. **零素材** —— 不需要找图、不存在版权问题
  2. **风格天然统一** —— 素材风格不统一是「廉价感」的头号来源
  3. **永不失真** —— 矢量绘制任意分辨率都锐利（对比：现有 `enemy0.png` 20×15 被拉到 30×30 已变形）
  4. **染色 / 发光 / 拖尾都容易加**
  5. 有朝向，符合「飞机大战」的直觉
- **备选方案**：位图精灵（`hero.png` 可染色复用，但仅 40×50，放大发虚且难统一风格）
- **代价 / 风险**：视觉上限低于精细美术资源（但本项目重点不是美术）
- **可逆性**：**完全可逆** —— 渲染层不影响通信系统
- **答辩可能被问**：为什么不用图片素材？→ 答：实时游戏的重点是通信；几何渲染保证风格统一、零素材依赖，且不影响任何网络层设计。

## D-004 游戏形态定为「竖版飞机大战 + 关卡 + BOSS」

- **日期**：2026-10-10（**取代同日早先的「极简多人」版本**）
- **决定**：游戏做**竖版飞机大战（弹幕射击）**：
  - **1~4 人合作**，**2 关 × 5 波**，**1 个三阶段 BOSS**
  - **3 种敌机**（直线俯冲 / 横向移动 / 追踪玩家）、**3 种弹幕**（直线散射 / 扇形 / 追踪弹）
  - **5 级火力**（伤害 + 射速 + 形态三重递进）、**拾取道具**升级
  - **几何绘制，零素材**，**720 × 960 竖版**窗口
- **演进过程（诚实记录）**：完整双摇杆 → 极简多人 → 抢靶 → **飞机大战**
- **理由**：
  1. **弹幕游戏是实时同步负载最重的类型之一** —— 200+ 颗子弹的高频生成/移动/销毁，是真正的同步难题，
     比「几个方块移动」有料得多（快照从 ~200 B 涨到 ~1974 B，带宽差 5 倍）
  2. **实测证明硬件撑得住**：4 人 + 30 敌机 + 200 子弹 = **0.45 ms/tick = 8.9% 单核**
  3. **天然有死亡条件**（被敌机/弹幕击中掉血），解决了抢靶方案「游戏永不结束」的漏洞
  4. **可复用现有代码约 80%** —— 玩家、敌机、子弹、碰撞的结构都已存在
  5. **动机**：学员明确表示想做飞机大战。**5 个月的项目，动力比省时间重要**
- **备选方案**：
  - 「极简多人」（只有方块移动）→ 同步负载太轻，实验数据单薄
  - 「抢靶方案」→ 无死亡条件，游戏不会结束（已否决）
- **代价 / 风险**：
  - ⚠️ 游戏内容代码从约 160 行升至约 **540 行**，多约 **13~17 小时**
  - ⚠️ 时间预算从约 218 h 升至约 **222 h**（超预算约 10%）
  - **兜底**：优先级 **④（游戏内容）排在最后，超时第一个砍**，论文不受影响
- **答辩可能被问**：为什么做弹幕游戏而不是更简单的？
  → 答：弹幕游戏的同步实体数量最多（200+ 子弹），是最能暴露实时同步问题的场景；
  实测证明单机性能足够（仅占 8.9% 单核），不存在做不动的风险。

## D-005 加入 HTTP 短连接层，与 TCP 长连接分层

- **日期**：2026-10-10
- **决定**：保留 Django，作为**主线的一部分**（非可选）：
  - **TCP 长连接**：实时同步（玩家位置、房间状态）
  - **HTTP 短连接（Django）**：登录、排行榜、玩家战绩
  - **MySQL**：用户与分数持久化
  - **Redis**：排行榜缓存
- **理由**：
  1. 题目是「数据通信**系统**」，分层设计比单一 TCP 服务器更完整
  2. 「按数据类型选择通信方式」是有质量的论文论点
  3. 环境（Django 5.2.18 / MySQL 8.0.41 / Redis）已就绪，边际成本可控
  4. TCP 连接用 HTTP 登录得到的 **token 认证**，两层自然衔接
- **备选方案**：纯 TCP 项目（省约 30 小时，但论文少一个论点）
- **代价 / 风险**：
  - ⚠️ **时间预算上升约 30 小时**（原估算 218 h → 约 248 h，而预算是 200 h）
  - ⚠️ **接口需要有调用方** —— 客户端要实现 HTTP 调用，且**不能在游戏主循环里阻塞**（见 D-007）
  - ⚠️ **排行榜缺少数据来源**（见 D-004）：当前玩法没有分数，需用玩家战绩类指标替代，或给玩法补一个极简得分机制
- **答辩可能被问**：为什么要两套通信方式？→ 答：实时数据要求低延迟高频次，适合长连接自定义协议；账号与战绩是低频请求-响应，HTTP 更简单可靠。按数据类型分层可降低系统整体复杂度。

## D-006 同步模型：服务端权威，客户端只上报输入

- **日期**：2026-10-10
- **决定**：客户端**只上报输入**（按键位掩码），坐标由服务端计算并广播。
- **理由**：
  1. **防篡改** —— 客户端无法直接伪造坐标
  2. 状态一致性由单一权威裁定，避免多端分歧
  3. 局域网 RTT < 5 ms，远小于一个 50 ms 的 tick，**不做客户端预测也不会感觉滞后**
- **备选方案**：
  - 客户端权威上报坐标（实现更简单，但可被任意篡改）
  - 服务端权威 + 客户端预测回滚（手感最好，但实现与调试成本高，列为进阶项 F12）
- **代价 / 风险**：
  - 客户端必须做**插值**，才能把 20 Hz 快照渲染成 60 fps 平滑动画
  - 服务端承担全部游戏逻辑计算（本项目规模下无压力）

## D-007 客户端网络 IO 采用非阻塞 socket + 每帧轮询

- **日期**：2026-10-10
- **决定**：客户端 socket 设为非阻塞，在 pygame 主循环中**每帧检查一次**可读性。
- **理由**：
  1. **绝不能阻塞渲染主循环** —— 阻塞式 `recv()` 会让游戏在网络卡顿时直接冻死
  2. 单线程、无锁、无并发 bug，逻辑简单可预测
  3. 便于调试（所有事情都发生在主循环里，没有线程交错）
- **备选方案**：独立接收线程 + 队列（编程模型更熟悉，但引入线程同步与退出处理问题）
- **代价 / 风险**：
  - 需要自己处理**部分写**（`send` 未发送完）与发送缓冲队列
  - 每帧轮询引入最多 1 帧（约 16 ms）接收延迟 —— 局域网场景下可忽略
- **答辩可能被问**：为什么不用多线程？→ 答：避免线程同步复杂度；游戏主循环本身就是天然的轮询驱动，非阻塞 IO 与它天然契合。

## D-009 游戏内容：射击 + 关卡 + BOSS（取代 D-008 的缩圈方案）

- **日期**：2026-10-10
- **决定**：
  - **玩家**：左右移动 + **自动向上射击**，3 点 HP，受击后 1.5 s 无敌帧
  - **火力**：**5 级**，伤害 + 射速 + 形态三重递进（单发 → 双发 → 三发扇形）
  - **道具**：击杀 15% 掉落，拾取升级；满级后转分数；**被击中降 1 级**
  - **敌机 3 种**：直线俯冲 / 横向移动 / 追踪玩家
  - **弹幕 3 种**：直线散射 / 扇形 / 追踪弹
  - **关卡**：2 关 × 5 波（50 + 80 架），波次「清完或超时 25 秒」推进
  - **BOSS**：1 个，3 阶段，血量 = **1250 × 进入时人数**
  - **失败条件**：玩家阵亡 10 秒后自动复活（火力重置为 1）；**全员同时阵亡才结束本局**
- **理由**：
  1. **一次解决三个问题**：排行榜有数据（分数）、关卡进度有名目、游戏有结束条件
  2. **同步负载大幅提升** —— 从「几个方块」变成 200+ 子弹，快照 1974 B（**39.5 KB/s**），
     序列化对比实验的差异从「不明显」变成「5.6 倍」
  3. **引入真实的同步难题** —— 高频瞬时实体的生成/销毁，是实时网络同步的经典问题
  4. **服务端权威有更多体现** —— 命中判定、伤害计算、火力等级、计分全在服务端
- **备选方案**：
  - 缩圈方案（D-008，已否决）
  - 「子弹 + 静态靶子」抢靶方案 → 无死亡条件，且同步实体种类少
- **代价 / 风险**：
  - ⚠️ 游戏代码从约 160 行升至约 **540 行**（+13~17 h）
  - ⚠️ BOSS 血量系数 1250 假设玩家平均火力 Lv4，**需实机调整**
- **答辩可能被问**：为什么要做 BOSS？
  → 答：BOSS 是一个**多阶段状态机**的同步对象（血量 + 阶段），
  与普通敌机、子弹、道具的同步策略不同，能覆盖更多同步场景。

## D-010 三阶段解耦：占位对象 → 完整游戏

- **日期**：2026-10-10
- **背景**：优先级 ④（游戏内容）排在最后（见 D-013），
  但阶段 ①~③（通信 / 抓包 / 性能）**必须先有可同步的对象**才能验证。
- **决定**：把**网络层与游戏层解耦**，分三阶段演进：

  | 阶段 | 同步对象 | 目的 |
  |---|---|---|
  | 阶段 1~3（第 1~13 周） | **极简占位**：几个方块在场地内移动 | 独立验证通信系统 |
  | 阶段 4（第 14~17 周） | 逐步替换为敌机、子弹、道具 | 增加负载与复杂度 |
  | 最终 | 完整飞机大战（含 BOSS） | 演示效果 |

- **理由**：
  1. **通信系统可独立验证** —— 用最简单的对象证明协议、粘包、同步、并发都是对的
  2. **占位方块是最好的协议测试工具** —— 排查问题时排除游戏逻辑干扰
  3. **风险前移** —— 最难的部分先做完，游戏内容可随时削减
- **关键约束**：占位阶段的**实体结构、同步机制、渲染管线与最终版本一致**，只是实体类型少。
  **替换游戏内容时通信层不用改。**
- **答辩可能被问**：占位阶段是不是白做了？
  → 答：不是。它证明了通信系统独立于游戏内容可用，这正是「数据通信系统」作为交付物的核心论点。

## D-011 性能硬约束：同屏实体上限

- **日期**：2026-10-10
- **背景**：实跑基准测试（Ryzen 7 7735H / 31.2 GB）：

  ```
  players enemies bullets   |  ms/tick | snapshot | CPU@20Hz
  --------------------------------------------------------------------
        4      30     200   |    0.45  |    1655 B |   8.9 %   ← 设计目标
        8      50     400   |    1.21  |    3231 B |  24.1 %
       16     100     800   |    4.37  |    6453 B |  87.3 %   ← 单核极限
  ```

- **决定**：
  - **同屏敌机上限 = 30**
  - **同屏子弹上限 = 300**
  - **刷怪前必须检查当前敌机数**，超上限则延后本波剩余敌机的刷新
- **理由**：
  1. tick 预算为 50 ms（20 Hz）；超过上限会让单帧耗时逼近预算，**导致掉帧**
  2. **这是硬件决定的，不是设计偏好** —— 因此它必须现在定，而不是"后面调"
  3. 该保险机制**不会死锁** —— 敌机被击杀后释放名额，刷新继续，只是节奏变慢
- **代价 / 风险**：
  - ⚠️ 关卡编排（每波敌机数）受此约束，不能"一口气刷 60 个敌人"
  - 实验 E2（并发测试）会主动突破此约束以寻找性能拐点 —— **这是有意的**
- **答辩可能被问**：为什么定 30 而不是 50？
  → 答：实测得出。50 个敌机时单核占用已达 24%，再叠加子弹增长会逼近预算；
  30 个时仅占 8.9%，留出 5 倍余量应对峰值。

## D-012 协议坐标值域：出屏即剔除

- **日期**：2026-10-10
- **背景**：基准测试时发现的**真实 Bug**：

  ```
  struct.error: 'H' format requires 0 <= number <= 65535
  ```

  子弹飞出屏幕后坐标为**负数**，而协议坐标用 `uint16`（只能表示 0~65535），**编码直接崩溃**。

- **决定**：**出屏即剔除** —— 坐标越界的实体**不写入快照**，客户端据此删除该实体。
- **理由**（对比另外两个方案）：

  | 方案 | 评价 |
  |---|---|
  | **A. 出屏即剔除** | ✅ **采用**：省带宽 + 客户端逻辑更简单 |
  | B. 改用 `int16` | 支持负坐标，但浪费一半值域 |
  | C. 序列化时截断 | ❌ 数据错误 |

- **衍生设计原则**：**快照是全量真相**。
  客户端每收到一帧快照，就**完全以快照为准**重建本地实体表 —— 快照里没有的实体一律删除。
  **因此无需额外的「删除实体」消息。**
- **答辩可能被问**：协议设计时怎么考虑数据值域？
  → 答：坐标用 `uint16` 是无符号的，而实体越界后会产生负值。
  这提醒我们协议字段的值域必须与业务数据的实际范围对齐；本项目的解法是「不同步越界实体」，
  既避开了值域问题，又顺带省了带宽。

## D-013 优先级顺序与时间预算

## D-014 asyncio 服务端中不能使用阻塞式数据库驱动

- **日期**：2026-10-10
- **背景**：TCP 服务端在一局结束时要写 MySQL（成绩）和 Redis（排行榜）。
  但服务端是 **asyncio 单线程事件循环**，而 `pymysql` 是**阻塞式**驱动 ——
  一次数据库写入会**阻塞整个事件循环**，导致同一时刻所有客户端掉帧。
- **决定**：
  1. **MySQL 写入放到线程池** —— `await asyncio.to_thread(...)`（Python 3.9+），不要把阻塞调用直接放进协程
  2. **Redis 用异步客户端** —— `redis.asyncio`（`redis` 包已自带，无需额外依赖）
  3. **写入失败必须重试 + 落盘兜底** —— 成绩不能因为数据库抖动而丢失
  4. 数据库操作**只在结算时发生**，不在 20 Hz 的游戏循环里
- **理由**：
  1. 「事件循环里不能有阻塞调用」是 asyncio 的核心纪律，违反会拖垮全部并发连接
  2. 结算是一局一次的低频操作，放线程池的额外开销可忽略
  3. 成绩是毕设里唯一的持久化数据，**丢了就白打了**
- **备选方案**：
  - 改用异步 MySQL 驱动（`aiomysql`）→ 更纯粹，但多一个依赖、生态较小
  - 用独立进程处理数据库写入（消息队列）→ 过度设计
- **代价 / 风险**：
  - `asyncio.to_thread` 会占用线程池线程，高并发结算时需要留意线程池大小
  - **必须在早期就做对** —— 后期发现事件循环被阻塞，排查成本很高
- **答辩可能被问**：为什么数据库写入要放线程池？
  → 答：asyncio 是单线程事件循环，任何阻塞调用都会卡住**所有**连接。
  `pymysql` 是同步驱动，必须 `to_thread` 隔离；这也是「事件驱动模型下如何与阻塞式组件共存」的典型问题。

## D-015 第 1 步用阻塞式单客户端回声程序起步，不直接上 asyncio

- **日期**：2026-10-19
- **决定**：阶段 1 的第 1 步只写两个最小脚本：
  - `server/echo_server.py`：阻塞式 `accept` / `recv` / `sendall`，一次只服务一个客户端，**不加消息边界**
  - `client/echo_client.py`：命令行发送一行、打印回显与 RTT

  长度前缀留到第 2 步，asyncio 留到第 5 步。
- **理由**：
  1. **让 socket 的基本语义可见**：`accept` 等连接、`recv` 返回“当前能读到的字节”而不是“一条消息”、`sendall` 负责把数据发完
  2. **先看见阻塞模型的缺陷**（一次只能服务一个客户端、一个慢客户端会卡住所有人），第 5 步再引入 asyncio，才知道它解决了什么问题
  3. 逻辑约 30 行，变量少，出错时容易定位，适合作为第一步建立信心
- **备选方案**：
  - 直接用 asyncio 写回声服务器 → 这确实是最终架构，但 `await reader.read()` 把“字节流无边界”藏了起来，容易误以为“一次 read 就是一条消息”
  - 用 `SocketServer` / Twisted 等框架 → 封装太厚，不适合作为理解底层的第一步
- **代价 / 风险**：
  - 这段代码**不是最终服务端**，第 5 步会被 asyncio 版本取代；但 `recv` / `sendall` / `accept` 的概念与排错经验完全复用
  - **单客户端是刻意保留的限制，不是 Bug**
- **答辩可能被问**：为什么不用 asyncio 一步到位？
  → 答：先理解阻塞 IO 的行为和瓶颈，才能说清 asyncio 解决了什么问题；最终服务端确实用 asyncio，但那是第 5 步的重构目标。

## D-016 网络实验环境：VMware VMnet1 仅主机 + netem（桥接 WiFi 已实测否决）

- **日期**：2026-10-19（同日追加桥接实测，方案定稿）
- **背景**：`01-系统架构.md §11.2` 要求阶段 1 实测“客户端连本机局域网 IP 能否拿到真实 RTT / 抖动”。两轮实测后，结论如下。

### 第一轮：本机自连局域网 IP（代码侧实测）

- `ping 127.0.0.1` 与 `ping 10.140.71.127` 均 **< 1 ms**
- 回声 RTT **0.03~0.14 ms**
- 向 `10.140.71.127` 传 16 MB：**1145.8 MB/s**，WLAN 网卡收发增量仅 **0.001 / 0.012 MB**
- **结论**：Windows 把发往本机地址的流量短路到回环，根本没经过网卡；`§11.2` 的兜底条件（0.1 ms 量级）触发。

### 第二轮：VMware 桥接 WiFi（用户亲自实测）

| 测试 | 结果 |
|---|---|
| 桥接 + 校园网 `GDPZ-student-5G` | **虚拟机拿不到 IPv4**（校园网拒绝虚拟机 MAC） |
| 桥接 + 手机热点 | 虚拟机拿到 `10.152.181.161/24`，能 ping 通 |
| host → VM（热点、桥接） | **RTT = 0.00 ms，20/20 全成功** |
| host → 网关 `10.152.181.188` | **RTT = 4.67 ms（1~6 ms）**；8000 字节包 **9.60 ms** |
| 加静态路由强制走网关 | `route add 10.152.181.161 mask 255.255.255.255 10.152.181.188` 后**仍为 0 ms** |

**关键判断**：

- 网关 RTT 4.67 ms、大包 9.60 ms，说明 **ping 本身有精度**；VM 的 0.00 ms 是**真 0**，不是“测不出来”
- 改 L3 路由表仍然 0 ms → **VMware 的桥接在 L2（链路层）直接截获，绕不过去**
- 因此：**桥接 WiFi 这条路彻底放弃**；已改回 NAT，残留静态路由已删除

### 最终决定

1. **不装 VirtualBox、不重装 Ubuntu Server**：使用现有 **VMware Workstation + Ubuntu Desktop**（能登录、能跑 `tc`）
2. 虚拟机只用 **仅主机模式（VMnet1）** 跑服务端；宿主客户端连 VM 的 VMnet1 地址
3. **延迟 / 丢包类实验（E4 / E5）**：在 Ubuntu 内用 **`tc netem`** 注入，参数精确、可复现
4. **抓包（E7）**：Npcap 回环适配器，或 Ubuntu 内 `tcpdump -w` 导出 pcap
5. **本机多进程**继续用于：协议、粘包、并发、房间逻辑、抓包字段核对
6. **借设备 + 手机热点**：降级为**可选**，只做真实性交叉验证，不列入主线
7. **第 13 周性能测试前**完成 VMnet1 + netem 配置与验证

### 理由

1. 桥接实测 0 ms 且静态路由无效，**桥接不可用**；校园网还直接拒绝 VM MAC
2. 仅主机模式不依赖校园网 / 热点，链路稳定，guest 有独立 TCP/IP 栈
3. `tc netem` 在**内核态**做排队 / 延迟 / 抖动 / 乱序 / 丢包，比应用层 `sleep` 更接近真实网络，且可精确复现
4. 现有环境已具备，零安装、零重装，避免引入第二个虚拟化平台

### 备选方案（均不采用）

- **桥接 WiFi** → 实测否决（校园网拒绝 MAC；热点下 0 ms）
- **应用层注入**（发送前 `sleep` / 随机延迟）→ 只影响应用线程，模拟不了内核排队 / 乱序；否决
- **VirtualBox / Hyper-V** → 需要新装或重装，引入第二平台；否决
- **借第二台设备 + 热点** → 真实性最好，但不可重复、协调成本高；只保留为可选验证

### 代价 / 风险

- VMnet1 的基线 RTT 也接近 0；必须用 netem **主动注入**可观测的延迟 / 抖动，论文中要写清这是**受控仿真**，不是真实 WiFi
- netem 默认作用于 guest **出口**；若要双向对称延迟，需要在 guest ingress 用 `ifb`，或再加一台 Linux 路由 VM（按实验需要）
- Npcap 安装时要勾选 loopback support；若抓不到，改用 Ubuntu 内 `tcpdump -w` 导出 pcap
- VMnet1 的 IP 可能随 VM 重启变化；实验脚本要**动态读取**，不要硬编码

### 答辩可能被问

- **为什么不用桥接？** → 实测 host→VM 20/20 次 0.00 ms，网关 4.67 ms；加静态路由仍 0 ms，说明 VMware 桥接在 L2 截获，桥接 WiFi 拿不到真实链路指标。
- **为什么用 netem，不用应用层 sleep？** → netem 在内核态排队，能模拟延迟 / 抖动 / 乱序 / 丢包；应用层 sleep 只延迟发送线程，无法模拟队列和乱序，也不可精确复现。
- **host-only 的数据算网络实验吗？** → guest 有独立 TCP/IP 栈，netem 提供可控链路参数；外部有效性再用借设备做一次性验证。

## D-017 第 2 步用 4 字节大端长度前缀划清消息边界

- **日期**：2026-10-19
- **决定**：
  - 本步帧格式：`uint32 大端长度 + payload`，长度**只算 payload**，不含 4 B 头
  - 接收端用 `recv_exact()` 循环读满；`recv_frame()` 先读 4 B 长度，再读 N B
  - 单帧载荷上限 `MAX_PAYLOAD = 64 KiB`；超限抛 `ProtocolError` 并断开连接
  - 第 4 步把 4 B 长度扩展成 **12 B 帧头**（magic / version / type / seq / length），
    “先读长度、再读载荷”的核心不变
- **理由**：
  1. **二进制安全**：长度前缀对任意字节都成立；分隔符（`\n`）遇到载荷里的 `\n` 必须转义
  2. **大端 = 网络字节序**：`struct` 的 `!I` 明确表达跨平台一致
  3. **把“可能只收到一部分”的循环收敛到一个函数**：业务代码只看到完整消息，不必重复写 while
  4. **64 KiB 上限**：防止对端声明 4 GB 长度把内存吃光；本项目快照约 2 KB，留了 30 倍余量
- **备选方案**：
  - 分隔符（`\n` / `\0`）→ 二进制载荷要转义，体积和复杂度都上升（否决）
  - 定长包 → 载荷可变时浪费带宽（否决）
  - 每次 `recv(65536)` 后自己切 → 还是要处理半包 / 粘包，且缓冲区逻辑散落各处
- **代价 / 风险**：
  - 每帧多 4 B；1 B 的输入包头部是载荷的 4 倍（第 4 步变 12 B 后是 12 倍，见 `02 §4.1`）
  - `recv_exact()` 是**阻塞版本**；第 6 步客户端改非阻塞后，要换成“缓冲区 + 状态机”的 FrameParser
- **答辩可能被问**：长度字段为什么用 4 字节，不用 2 字节？
  → 答：2 字节上限 65535 B，当前快照够用，但扩展余量小；4 字节是通用做法，只多 2 B，
  并且后面加 seq / type 时帧头本身就会超过 4 字节。

## D-019 第 4 步落地 12 字节帧头：magic / version / type / seq / length

- **日期**：2026-10-19
- **决定**：
  - `HEADER = struct.Struct("!HBBII")`，固定 12 B
  - 字段：`magic=0x4A59`、`version=1`、`type=uint8`、`seq=uint32`、`length=uint32`
  - `recv_frame()` 返回 `Frame(msg_type, seq, payload)`；magic / version / length 在**读载荷之前**校验
  - `pack_frame()` 显式检查 type / seq 值域；`ProtocolError` 统一表示帧错误
  - 阶段 1 回声用临时 type `0x7F`，避开正式 `C→S 0x0X` / `S→C 0x8X`
- **理由**：
  1. type 让一条连接承载多种消息；seq 支持请求-响应 RTT、丢包检测、防重放
  2. magic / version 让“连错端口 / 协议版本不匹配”在帧层快速失败，不把垃圾当消息解析
  3. 长度仍在帧头里，第 2 步的拆包逻辑不变，只是偏移从 0 变成 8
  4. 12 B 是 `02 §4.1` 已定稿的格式，代码与文档一致
- **备选方案**：
  - 只有 4 B 长度（第 2 步）→ 没有 type / seq，无法区分消息、关联响应；否决
  - 8 B（magic + length）→ 省 4 B，但丢掉 version / type / seq；否决
  - JSON 文本协议 → 可读性好但解析慢、体积大（02 §1.1 已否决）
- **代价 / 风险**：
  - 每帧 12 B；1 B 的 `C_INPUT` 载荷头部是 12 倍（02 §4.1），后续用“批量合并”优化
  - 帧层只做结构校验，type 的业务合法性留给第 5 步的消息分发
  - `recv_exact()` 仍假设阻塞 socket；第 6 步非阻塞要改 FrameParser
- **答辩可能被问**：为什么帧头要 12 B，不能只留长度？
  → 答：长度只解决“消息边界”；type 决定交给谁处理，seq 用于请求-响应关联 / RTT / 防重放，
  magic / version 让错误在帧层快速失败。12 B 是功能与开销的折中，且与 `02 §4.1` 一致。

## D-020 第 5 步：asyncio 单线程 + 20 Hz tick + 全量玩家快照广播

- **日期**：2026-10-21
- **决定**：
  1. 服务端用 **asyncio 单线程事件循环**（`asyncio.start_server`），不用“每连接一个线程”
  2. `tick_loop` 固定 20 Hz，用 deadline 累加（`next_tick += 0.05`），避免 `sleep(0.05)` 漂移
  3. 服务端权威：占位玩家坐标由服务端算，客户端只收快照（D-006）
  4. 快照用正式 `S_SNAPSHOT=0x84`，本阶段只带**玩家条目（11 B）**；敌机 / 子弹 / 道具计数固定 0
  5. 连接时服务端发临时 `S_WELCOME=0x7C`（player_id + color）；正式认证第 10 步再接
  6. `protocol/framing.py` 增加 `parse_header` / `recv_frame_async` / `send_frame_async`，同步 / 异步共用校验
- **理由**：
  1. 20 Hz 广播是实时同步的骨架；先跑通“多客户端 + tick + 广播”，再谈房间 / 输入 / 游戏内容
  2. 用正式快照头 + 玩家条目，第 6 步渲染时不用重写协议
  3. asyncio 单线程无锁，符合 D-007 / D-014 的并发纪律；慢客户端问题后面用发送队列解决
  4. 服务端权威避免客户端伪造坐标（D-006）
- **备选方案**：
  - 每连接一个线程 → 锁 / 同步复杂度高，否决
  - `selectors` → 更底层、代码更多；asyncio 已封装好，否决
  - JSON 快照 → 体积大、解析慢，否决
  - 增量快照 → 第 3 梯队 E6 再考虑，当前全量足够（D-012）
- **代价 / 风险**：
  - 广播是 O(客户端数)，且 `await drain()` 是串行的；慢客户端会拖慢 tick，后续改为每客户端队列 / 丢旧帧
  - 快照只支持玩家；`unpack_snapshot` 会拒绝非 0 的敌机 / 子弹 / 道具计数，后续扩展
  - `S_WELCOME` 是临时类型，第 10 步认证后替换
  - 当前没有输入，坐标是占位摆动；第 6 步接 `C_INPUT`
- **答辩可能被问**：为什么用 asyncio 单线程？20 Hz 怎么保证？为什么全量快照？
  → 答：asyncio 单线程避免了线程锁和共享状态竞争，20 Hz 用固定 deadline 累加而不是 `sleep` 漂移；
  全量快照让客户端“以快照为准”重建实体表，逻辑简单且天然处理删除（D-012），当前 4 人规模带宽足够。

## D-021 第 6 步：非阻塞客户端 + FrameParser + 一帧线性插值

- **日期**：2026-10-21
- **决定**：
  1. 客户端 socket 非阻塞，pygame 主循环每帧 `poll()` 一次；连接建立时允许阻塞（D-007）
  2. 新增 `FrameParser`：`bytearray` + `feed()` / `next_frame()`；半包留在用户态缓冲区，不阻塞主循环
  3. 插值：保存上一帧 / 当前帧快照，在 50 ms 内用 `alpha 0→1` 线性过渡；**一帧（50 ms）滞后**
  4. 窗口 720×960；桌面高度 < 1000 px 时降为 600×800，坐标按比例缩放
  5. 本步不做键盘输入；服务端占位摆动
- **理由**：
  1. 阻塞 `recv` 会冻住 60 fps 主循环；非阻塞 + `FrameParser` 是 D-007 的落地
  2. 20 Hz 快照直接画会一跳一跳；线性插值把 20 Hz 补成 60 fps，代码少且可解释
  3. 一帧滞后换来“不做预测”的简单性；局域网 50 ms 可接受，预测回滚是第三梯队
  4. 占位方块先验证渲染 / 插值管线，游戏内容最后加（D-010）
- **备选方案**：
  - 独立接收线程 + 队列 → 线程同步复杂，D-007 已否决
  - asyncio 客户端 + pygame → 两个事件循环集成麻烦；本阶段用非阻塞 socket 更直接
  - 指数平滑 → 简单，但和快照时间无关，实验误差不好解释
  - 快照延迟缓冲（渲染 `now - 100 ms`）→ 更标准，但复杂度高；E4/E5 前再升级
- **代价 / 风险**：
  - 一帧 50 ms 视觉滞后；对占位演示足够
  - 没有输入；服务端不会因客户端操作改变位置
  - 断线提示 / 自动重连未做；当前显示 disconnected，按 ESC 退出
  - `FrameParser` 缓冲区没有硬上限，但单帧受 `MAX_PAYLOAD` 限制，完整帧会及时消费
- **答辩可能被问**：为什么不用独立线程收包？为什么要插值？
  → 答：独立线程会引入锁和退出同步问题；主循环本身就是 60 fps 的天然轮询，非阻塞 socket + 用户态
  缓冲区与它最契合。20 Hz 快照直接渲染会跳，插值用两帧之间的线性过渡把画面补平滑；
  代价是一帧延迟，但换来了不做预测的简单性。

## D-023 7b：定频输入 + 服务端权威运动学 + 回显式心跳

- **日期**：2026-10-23
- **前置**：7a（D-022）只验证了「连接 + 广播」，服务端收到客户端消息后直接丢弃。
  7b 接通**客户端 → 服务端**的上行链路。

### 决定一：输入用**定频 20 Hz** 发送（与 tick 同频）

- 载荷只有 1 字节位掩码（`02 §4.5`），整帧 13 B；20 Hz → **260 B/s/客户端**
- 发送的是「**当前按住什么**」（状态），不是「刚刚按了什么」（事件）
- 客户端用 `next_input_at += INPUT_INTERVAL`（deadline 累加），不是 `= now + 间隔`
- **理由**：
  1. 与 tick 同频，服务端每个 tick 用最新 keys 算一次位移，不重复应用也不漏
  2. 内容是状态 → **天然冗余，丢一帧下一帧自动补上**，不需要 ACK / 重传
  3. E9 要测「输入处理负载」，定频才有稳定的自变量
- **备选方案（否决）**：
  - **按键变化时才发**：带宽最省（随机输入下约 200 B/s），但万一「松开」那条没送到，
    服务端会以为玩家还按着 → 角色一直走。要修就得加 ACK / 冗余，复杂度不划算。
    它的真实优势只是「按键后最多省 50 ms」，而 D-006 已认定局域网不做预测也不滞后
  - **每帧 60 Hz 发**：780 B/s，服务端只用 20 Hz，多出的 2/3 是纯浪费
- **实测**：`next_input_at = now + 间隔` 会被**帧率量化** —— 60 fps 下 50 ms 不是
  16.7 ms 的整数倍，服务端实测只收到 **17 次/秒**；改成累加后稳定 **20 次/秒**。
  （服务端 `tick_loop` 早就用的是累加模式，这里统一了。）

### 决定二：服务端权威运动学（`server/movement.py`）

1. **坐标只在服务端算**，客户端发的是意图（D-006）；快照里**不回传 keys**
2. **整数像素 / tick**：`PLAYER_SPEED_PER_TICK = 15` → 300 px/s，2.4 s 横穿 720 px
3. **左右同时按 = 抵消不动**（`0b11` → dx=0）
4. **边界钳制 `[20, 700]`**：方块按中心点绘制，不留余量会有半个身子出屏
5. **输入保质期 `INPUT_TTL = 0.5 s`**：超时未收到新输入即视为松手
6. **保留位先掩掉**（`keys &= KEYS_MASK`），不报 `ERR_MALFORMED`
- **理由**：
  1. 整数定点满足 `02 §4.3` 的「禁用浮点」，且带来**确定性** ——
     同样的输入序列必然得到同样的轨迹，实验可逐帧对账；浮点累加的末位误差会让复现变成玄学
  2. 抵消是真实玩家会做的事（同时按 A/D），抵消比「左优先」更符合直觉
  3. 保质期防的是「幽灵移动」：客户端卡死/断网前的最后一帧若是「按住左」，
     角色会一直走到 15 s 超时 —— 观感上是闹鬼
  4. 掩保留位是**前向兼容**：将来加「上下移动」（bit 2）时，旧服务端只是「当没看见」，不会断连
- **备选方案（否决）**：
  - 浮点速度 × 时间 → 违反 `02 §4.3`，且破坏确定性
  - 不设 TTL，一直用旧 keys → 出现上述幽灵移动
  - 保留位非 0 就报 `ERR_MALFORMED` → 将来加新位会导致新旧版本互不兼容
- **代价**：15 px/tick 的粒度不支持「加速 30%」这类道具；届时要改「定点 1/16 像素」

### 决定三：心跳 —— **原样回显 `client_time`**

- `C_HEARTBEAT(client_time)` → `S_HEARTBEAT_ACK(client_time, server_time)`
- 服务端把 `client_time` **原样抄回**，客户端本地算 `rtt_ms()`；帧头 `seq` 回带请求的 `seq`（`02 §4.2`）
- 时间戳 = **`time.monotonic()` 毫秒取低 32 位**；差值用无符号 `(now - sent) & 0xFFFFFFFF`
- 超时 = **15 s**（3 × 心跳间隔，`02 §7`），**每秒检查一次**（不是每 tick）
- `last_recv_at` 由**任何**收到的消息更新，不只是心跳
- **理由**：
  1. 回显式让 RTT 完全在客户端本地算，**不依赖两端时钟同步** —— 钟差会直接污染 RTT
  2. `monotonic` 只增不减；`time.time()` 被 NTP 回拨时 `now - sent` 会变成负数
  3. 无符号差值一行掩码即免疫 32 位回绕（49.7 天），
     例：`sent=0xFFFFFFF0, now=0x00000010` → 32 ms 而不是负数
  4. 每秒检查一次够了：超时精度差 50 ms 无所谓，省下的 tick 预算留给游戏逻辑
- **备选方案（否决）**：用两端时间戳相减 → 必须先对表；微秒时间戳 → 32 位只能表示 71 分钟，回绕太频繁

### 决定四：「判定 / 关闭 / 清理」三段分离

- `check_timeouts(now)` **只返回超时列表**，不关连接、不改字典
- `tick_loop` 负责 `writer.close()`；**唯一清理点**是 `handle_client` 的 `finally`
- **理由**：
  1. **可测** —— 测试塞一个假的 `now` 就能验 15 s 超时，不用真的等 15 秒
  2. 避免两处都改 `self.clients` 字典（删两次 / 删错人）
- **`--timeout 0` 关闭判定**：做「纯广播」基线实验时，客户端不发心跳也不会被踢 —— 用于**分离变量**

### 决定五：机器人与服务端统计

1. **单个机器人拆成 3 个协程**（`bot/agent.py`）：`_recv_loop` / `_input_loop` / `_heartbeat_loop`
   - 7a 单协程够用是因为它只收不发；`recv` 一阻塞发送就停，20 Hz 会退化成「有快照才发」
   - asyncio 单线程，`writer.write()` 同步追加，两个协程并发发**不会撕裂帧**；`drain()` 只是背压
   - 每个协程自己把异常收进 `result.errors` —— `TaskGroup` 中一个任务抛异常会**取消同组其他任务**，
     那会连统计一起清掉
2. **观察者与输入机器人是同一个机器人**，靠 `--input-hz 0` 切换；`--seed` 固定随机种子（第 i 个用 `seed+i`）
   - 避免「两份几乎一样的机器人，改一处忘一处」
3. **服务端每秒打印 tick 耗时 + 输入帧速率**（`server/stats.py` 的 `TickStats`）
   - D-022 要测「输入处理负载」，但 bot 只看得到自己这边的收发；
     服务端每 tick 花多少毫秒只有服务端知道（D-011 的 0.45 ms/tick 就是这么来的）
4. 机器人逻辑与 CLI 分家：`bot/agent.py`（怎么工作）+ `bot/main.py`（开几个、怎么汇总）

### 决定六：连带影响与文件划分

- **`client/console.py` 必须加心跳**：7b 起服务端有 15 s 超时，不发消息的调试客户端会被踢
- **观察者 bot 默认也发心跳**：同理；想复现 7a 的纯广播基线用 `--heartbeat 0` + 服务端 `--timeout 0`
- **`client/net.py` 补发送队列**（7a 遗留的 TODO）：非阻塞 socket 的 `send()` 可能部分写甚至零写，
  所以 `send()` 只排队、`flush()` 在每帧 `poll()` 里尽量写；`MAX_OUTBOX = 64 KiB` 防内存无限涨
- **新增 `protocol/world.py`**：世界尺寸（720×960 / 边距 20）放协议包
  - 理由：快照坐标的语义**依赖世界尺寸**，服务端边界与客户端缩放必须共用一份定义；
    各写一份会静默漂移（改了窗口忘了边界，玩家能走到看不见的地方，且不报错）
- **本步不实现 `S_PLAYER_LEAVE (0x86)`**：D-012 的「快照是全量真相」已覆盖
  （玩家断开后不再出现在下一帧快照里），事件同步留给游戏内容阶段（`02 §5.3`）
- **不实现防洪 `ERR_RATE_LIMITED`**：等有认证和真实玩家再说

### 代价 / 风险

- 上行**每帧 13 B 里 12 B 是帧头**（`02 §4.1`）；100 客户端 ≈ 26 KB/s 纯帧头开销
  → 「批量合并发送」仍是未做的优化项（`02 §12`）
- 没有客户端预测：按键到画面动隔一个 RTT + 最多一帧（第三梯队 F12）
- 广播仍是 O(客户端数²)，慢客户端的独立发送队列是 D-020 记的账，7b 没还
- 心跳只给 RTT，不给丢包率（TCP 保证不丢，丢包统计要等 E5 用 netem 注入）
- 新增 4 个模块文件（`protocol/world.py`、`server/movement.py`、`server/stats.py`、`bot/agent.py`）；
  `server/main.py` 从 162 行涨到 **241 行**，`bot/main.py` 反而从 177 行降到 **129 行**（机器人逻辑搬进了 `bot/agent.py`）

### 实测（本机 loopback，**不是最终网络实验数据**，D-016）

| 场景 | 连接 | 快照 | 输入 | 心跳 ack | 间隔 p50/p95 | RTT p50/p95 | errors |
|---|---|---|---|---|---|---|---|

### 答辩可能被问

- **为什么输入要定频发，不按需发？** → 答：发的是「当前按住什么」而不是事件，
  所以丢一帧下一帧自动纠正，不需要确认重传；按需发一旦丢了「松开」消息，
  服务端会以为玩家还按着，角色会一直走。
- **为什么坐标不让客户端算？** → 答：坐标是结果，客户端能直接说自己在哪里就能伪造位置。
  只发按键意图、服务端统一计算，保证单一权威（D-006）。代价是要等一个往返，局域网可忽略。
- **心跳为什么回显客户端时间？** → 答：RTT 完全在客户端本地算，不依赖两端时钟同步；
  若用两端时间戳相减，钟差会直接算进 RTT。时间戳用单调时钟并取无符号差值，连 32 位回绕也免疫。
- **为什么要给输入设保质期？** → 答：定频发送维持的是「最后状态」，
  客户端失联后服务端会继续按最后的按键移动角色。0.5 s 保质期把输入变成有有效期的意图。

## D-024 8a：用「占位实体」造出 E9 的自变量，并修通指标采集链路

  - **等游戏内容做完再测**：违反 D-013 的优先级，且游戏内容是唯一可砍项（风险顺序颠倒）
- **代价 / 风险**：
  - 占位实体**没有碰撞检测**，而 `01 §7.1` 那份基准（100 敌机 + 800 子弹 = 4.37 ms/tick、87.3% 单核）
    **包含「朴素 O(子弹×敌机) 碰撞检测」= 每 tick 8 万次判定**，那才是 CPU 大头。
    实测我们同规模只有 **1.396 ms / 1.7%** → **图 6-17 / 6-19 的拐点出不来**
  - ⚠️ **这是 8b 开工前必须拍板的事**（A 只测通信层 / B 补一段占位碰撞判定），
    详见 `PROGRESS.md §2.14` 末尾。**图 6-19 的「50% 舒适线」只有 B 碰得到**，
    而 D-011 的「敌机 ≤ 30、子弹 ≤ 300」正是基于 B 那份基准定的

### 决定二：数量必须**恒定**（出屏剔除后立即补足）

- 每 tick：**移动 → 出屏即剔除（D-012）→ 补足到目标数量**
- **理由**：E9 的自变量是「**同屏**实体数」。若实体只出不进，数量随时间衰减，自变量就不稳定，
  六档实验之间不可比。补足后实测 `e/b` 全程稳定
- **顺带收益**：剔除让**越界坐标永远进不了编码器**，直接杜绝 D-012 记录的那个
  `struct.error: 'H' format requires 0 <= number <= 65535`
- **代价**：实体是「凭空补」的，不是真的被打掉后刷新；占位阶段不需要真实刷怪逻辑

### 决定三：角度用 **8 方向整数表**，并补上协议缺失的**角度基准**

- `angle >> 5` 取 8 个方向（每档 32），整数查表，无三角函数
- **同时补进 `02 §4.3 / §4.5`：`0° = 正上方，顺时针`** ——
  **协议文档此前只写了「0~255 线性映射到 0~360°」，没定义 0° 指向哪里**，
  子弹必须有方向，这是文档漏洞，本次补上
- **理由**：
  1. 竖版飞机大战「向上」是主方向（玩家子弹向上、敌机向下），0 放在正上时
     最常见的两个方向恰好是 `0` 和 `128`，都在整数档上；若 0 放正右，玩家子弹得写 `192`，反直觉易错
  2. 无三角函数 → 满足 `02 §4.3` 禁用浮点，且**同样的输入必然得到同样的轨迹**（可复现）
  3. `& 0x07` 保证角度越界时不会数组越界
- **备选方案（否决）**：`math.cos/sin` 逐角度算 → 违反禁用浮点，且末位差异破坏可复现性
- **代价**：斜向位移是 1.41 倍（未归一化）。真实弹幕阶段要么把表细化到 256 档，要么用定点数归一化

### 决定四：`boss_present` **推导**而不传参

- `boss_present = 1 if any(e.type == ENEMY_BOSS) else 0`
- **理由**：它和「敌机里有 `type == 0xFF`」表达同一件事。两边各传各的必然出现
  「flag 说有 BOSS 但敌机列表里没有」的矛盾，而这种矛盾**不会崩溃**，
  只会让客户端显示一个不存在的血条，极难排查
- **代价**：无（推导成本是每 tick 一次 `any()`）

### 决定五：指标采集 —— 1 秒窗口、追加写、双时间戳

| 项 | 决定 | 理由 |
|---|---|---|
| 窗口 | **1 秒**（20 tick），不是 `03 §4.1` 写的 5 秒 | **原始数据细，聚合可以后做；反过来不行**。5 秒是展示粒度，不是采集粒度 |
| 写入 | 追加写 + **每行 flush** | §4.3 原则；Ctrl+C 也不丢已采数据 |
| 表头 | 文件为空时才写 | 分段跑多次实验不会写出两份表头 |
| 时间戳 | **`t_mono`（单调，分析用）+ `timestamp`（墙上时钟，人看）** | 只用墙上时钟不安全（NTP 调整会让时间倒流），只用单调时钟没法对「几点跑的」 |
| CPU | **自己算 ΔCPU秒 ÷ Δ墙钟秒 × 100**，不用 `psutil.Process.cpu_percent()` | 那个 API 把阻塞/非阻塞两种语义混在一起，非阻塞还要乘 `cpu_count()`，量纲易错；自己算则定义明确且可单测。**100% = 一个核跑满**，与 D-011 同量纲 |
| CPU 校验 | 忙等 0.5 s/秒 → **49.95%**；0.1 s/秒 → **9.37%**；空闲 → **0.0%** | 量纲正确，精度优于 0.1% |
| psutil 缺失 | 只留空两列并提示一次，不崩 | 少一个包不该让整个实验跑不起来 |

### 决定六：⭐ `tick_ms` 与 `CPU%` 是两个不同量纲，必须同时报

**实测发现**（4 人 + 100 敌机 + 800 子弹）：

| 指标 | 值 | 含义 |
|---|---|---|
| `tick_ms` | 1.396 ms | tick 主体的**墙钟**耗时（**含** `await drain()` 等待与事件循环调度） |
| `cpu_percent` | 1.7% | **真正的 CPU 时间** → 约 **0.87 ms/tick** |

差额（约 0.5 ms/tick）是 I/O 等待与调度。

- **意义**：`tick_ms` 回答「50 ms 帧预算还剩多少、会不会掉帧」；
  `CPU%` 回答「还剩多少算力、能再加多少负载」。只看一个会得出错误结论
- **对旧数据的补充说明**：D-011 的「0.45 ms/tick」同样包含等待，**不能直接当成 CPU 时间用**

### 决定七：其他

- **matplotlib 缓存目录**：在 `import matplotlib` **之前**设 `MPLCONFIGDIR` 指向项目内 `.cache/matplotlib`。
  默认位置（`%LOCALAPPDATA%\matplotlib`）不可写时，matplotlib 会**在当前工作目录建临时目录** ——
  等于往仓库根目录拉屎，且每次重建、导入慢几秒。`.cache/` 已进 `.gitignore`
- **`data/` 进 `.gitignore`**：指标 CSV 是生成物，可重新跑出来；图表（`docs/figures/`）**不忽略**，是要进论文的
- **`client/main.py` 的子弹不做插值**：协议里子弹条目**没有唯一 ID**（只有 `owner_id`），
  客户端无法把这一帧的子弹与上一帧对应起来。这是**协议设计的代价**
  （省 2 B/颗 × 200 颗 = 400 B/帧，约占快照 20%），不是实现遗漏

### 代价 / 风险

- 新增 3 个模块文件（`server/entities.py`、`server/metrics.py`、`tools/plot.py`）+ 4 个测试文件
- 测试从 88 → **153 个**
- 占位实体没有 AI / 碰撞 / 伤害 / 掉落（第 11 步），因此 **CPU 曲线很平**（见决定一的代价）
- 指标 CSV 默认开启，随手试玩也会写 `adhoc` 场景的行（用 `--no-metrics` 关闭，出图时可按 `scenario_id` 过滤）

### 答辩可能被问

- **为什么要做"假"的敌机子弹，不直接做游戏？** → 答：这是三阶段解耦（D-010）。
  占位实体用的是**真实的协议条目与序列化路径**，只有行为是简化的；
  它让性能测试能先于游戏内容完成，符合 D-013 的优先级——
  任何一周停下来手上都有可交付成果。替换成真实 AI 时通信层不用改。
- **为什么不能用填充字节模拟大快照？** → 答：填充只影响带宽，
  而 E9 还要测服务端的实体遍历与序列化开销，那才是 CPU 的主要部分；填充测出来是假数据。
- **tick 耗时和 CPU 占用有什么区别？** → 答：实测同规模下 tick 墙钟 1.396 ms
  但纯 CPU 只占 0.87 ms/tick，差额是 I/O 等待与调度。
  前者决定帧预算是否充足，后者决定算力是否还有余量，实验中同时记录并区分。
