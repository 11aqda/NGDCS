## D-001 数据库驱动用 PyMySQL，而不是 mysqlclient

- **日期**：2026-10-10
- **决定**：Django 连接 MySQL 使用 `PyMySQL`，配合 `pymysql.install_as_MySQLdb()`
- **理由**：
  1. **Windows 友好** —— `mysqlclient` 是 C 扩展，Windows 上安装需要编译环境（Visual C++ Build Tools），经常装不上；PyMySQL 是纯 Python，`pip install` 即可
  2. 本机是 Windows 开发环境，优先保证「装得上、跑得通」
- **备选方案**：`mysqlclient`（性能更好，但 Windows 安装门槛高）
- **代价 / 风险**：
  - PyMySQL 是纯 Python 实现，批量操作性能约为 mysqlclient 的 1/2 ~ 1/5
  - 需要额外安装 `cryptography`（MySQL 8 的 `caching_sha2_password` 认证需要）
- **落地方式**：项目包 `__init__.py` 中

  ```python
  import pymysql
  pymysql.install_as_MySQLdb()
  ```

- **答辩可能被问**：为什么不用官方推荐的 mysqlclient？
  → 答：Windows 环境下 C 扩展编译门槛高，PyMySQL 保证可移植性；性能差距在当前并发量级下可以忽略。

## D-002 降 Django 到 5.2 LTS，而不是升级 MySQL 到 8.4

- **日期**：2026-10-10
- **背景**：venv 中安装的 Django 6.1.2 连接 MySQL 8.0.41 时直接抛错：

  ```
  django.db.utils.NotSupportedError: MySQL 8.4 or later is required (found 8.0.41).
  ```

  经查 Django 官方 ticket [#36624](https://code.djangoproject.com/ticket/36624)：**Django 6.1 起将 MySQL 最低版本提高到 8.4**。这是框架源码里的硬性检查，没有任何配置项可以绕过。

- **决定**：把 venv 中的 Django 降到 **5.2 LTS**（实际安装 5.2.18）
- **理由**：
  1. **动作最小** —— 只更换 venv 中的一个包；升级 MySQL 需要下载 MSI、运行图形安装器、重启服务，并承担数据迁移风险
  2. Django 5.2 是 **LTS 版本**，维护到 2028 年，稳定性有保障
  3. Django 5.2 支持 MySQL 8.0.11+，与本机 8.0.41 匹配
  4. 毕设周期内不需要 Django 6.x 的新特性
- **备选方案**：升级 MySQL 到 8.4 LTS
- **代价 / 约束**：
  - ⚠️ **在升级 MySQL 之前，不能把 Django 升到 6.x**
  - 系统 Python 里另有一个 Django 5.0.3，与 venv 隔离；**运行项目必须使用 venv 的解释器**
- **验证结果**：降级后实测通过

  ```
  ('8.0.41', 'myproject', 'django_user@localhost', 'utf8mb4_unicode_ci')
  Django version : 5.2.18
  ```

- **答辩可能被问**：为什么不用最新版 Django？
  → 答：框架版本应在满足需求的前提下选择稳定版；5.2 是 LTS，且与本机数据库版本兼容，避免了升级数据库带来的额外风险。

## D-003 渲染采用几何多边形飞船，不使用位图素材

- **日期**：2026-10-10
- **决定**：玩家角色用 `pygame.draw.polygon` 绘制几何多边形（箭头/三角），机头指向行进方向
- **理由**：
  1. **零素材** —— 不需要找图、不存在版权问题
  2. **风格天然统一** —— 素材风格不统一是「廉价感」的头号来源
  3. **永不失真** —— 矢量绘制任意分辨率都锐利（对比：现有 `enemy0.png` 20×15 被拉到 30×30 已变形）
  4. **染色 / 发光 / 拖尾都容易加**
  5. 有朝向，符合「飞机大战」的直觉
- **备选方案**：位图精灵（`hero.png` 可染色复用，但仅 40×50，放大发虚且难统一风格）
- **代价 / 风险**：视觉上限低于精细美术资源（但本项目重点不是美术）
- **可逆性**：**完全可逆** —— 渲染层不影响通信系统
- **答辩可能被问**：为什么不用图片素材？→ 答：实时游戏的重点是通信；几何渲染保证风格统一、零素材依赖，且不影响任何网络层设计。

## D-004 游戏形态定为「极简多人」，放弃完整玩法

- **日期**：2026-10-10
- **决定**：游戏只做「多名玩家的几何飞船在同一竞技场内自由移动 + 位置朝向同步」。
  **不做**：敌人、AI、子弹、碰撞、波次、关卡、道具、分数、音效。
- **理由**：
  1. **题目是「数据通信系统」**，游戏只是验证通信的场景
  2. 网络工程的技术含量（协议、并发、同步、测试、抓包）**与游戏复杂度无关**
  3. 按 200 小时预算，完整玩法会超出预算（估算 218 h）
  4. 数据量可由**机器人客户端数量**调节，不依赖游戏内容
- **备选方案**：完整多人游戏（俯视角双摇杆 + 敌人波次）—— 工作量翻倍，超出预算
- **代价 / 风险**：
  - 答辩演示画面较朴素 → 用发光/拖尾/延迟显示/机器人群增加观感
  - ⚠️ **由此产生的问题**：没有分数与关卡，导致「排行榜」「关卡进度」类需求**缺少数据来源**（见 D-005）
- **答辩可能被问**：这算「网络游戏」吗？→ 答：题目要求的是**网络游戏的数据通信系统**，重点在通信；游戏提供真实的实时数据流作为负载。

## D-005 加入 HTTP 短连接层，与 TCP 长连接分层

- **日期**：2026-10-10
- **决定**：保留 Django，作为**主线的一部分**（非可选）：
  - **TCP 长连接**：实时同步（玩家位置、房间状态）
  - **HTTP 短连接（Django）**：登录、排行榜、玩家战绩
  - **MySQL**：用户与分数持久化
  - **Redis**：排行榜缓存
- **理由**：
  1. 题目是「数据通信**系统**」，分层设计比单一 TCP 服务器更完整
  2. 「按数据类型选择通信方式」是有质量的论文论点
  3. 环境（Django 5.2.18 / MySQL 8.0.41 / Redis）已就绪，边际成本可控
  4. TCP 连接用 HTTP 登录得到的 **token 认证**，两层自然衔接
- **备选方案**：纯 TCP 项目（省约 30 小时，但论文少一个论点）
- **代价 / 风险**：
  - ⚠️ **时间预算上升约 30 小时**（原估算 218 h → 约 248 h，而预算是 200 h）
  - ⚠️ **接口需要有调用方** —— 客户端要实现 HTTP 调用，且**不能在游戏主循环里阻塞**（见 D-007）
  - ⚠️ **排行榜缺少数据来源**（见 D-004）：当前玩法没有分数，需用玩家战绩类指标替代，或给玩法补一个极简得分机制
- **答辩可能被问**：为什么要两套通信方式？→ 答：实时数据要求低延迟高频次，适合长连接自定义协议；账号与战绩是低频请求-响应，HTTP 更简单可靠。按数据类型分层可降低系统整体复杂度。

## D-006 同步模型：服务端权威，客户端只上报输入

- **日期**：2026-10-10
- **决定**：客户端**只上报输入**（按键位掩码），坐标由服务端计算并广播。
- **理由**：
  1. **防篡改** —— 客户端无法直接伪造坐标
  2. 状态一致性由单一权威裁定，避免多端分歧
  3. 局域网 RTT < 5 ms，远小于一个 50 ms 的 tick，**不做客户端预测也不会感觉滞后**
- **备选方案**：
  - 客户端权威上报坐标（实现更简单，但可被任意篡改）
  - 服务端权威 + 客户端预测回滚（手感最好，但实现与调试成本高，列为进阶项 F12）
- **代价 / 风险**：
  - 客户端必须做**插值**，才能把 20 Hz 快照渲染成 60 fps 平滑动画
  - 服务端承担全部游戏逻辑计算（本项目规模下无压力）

## D-007 客户端网络 IO 采用非阻塞 socket + 每帧轮询

- **日期**：2026-10-10
- **决定**：客户端 socket 设为非阻塞，在 pygame 主循环中**每帧检查一次**可读性。
- **理由**：
  1. **绝不能阻塞渲染主循环** —— 阻塞式 `recv()` 会让游戏在网络卡顿时直接冻死
  2. 单线程、无锁、无并发 bug，逻辑简单可预测
  3. 便于调试（所有事情都发生在主循环里，没有线程交错）
- **备选方案**：独立接收线程 + 队列（编程模型更熟悉，但引入线程同步与退出处理问题）
- **代价 / 风险**：
  - 需要自己处理**部分写**（`send` 未发送完）与发送缓冲队列
  - 每帧轮询引入最多 1 帧（约 16 ms）接收延迟 —— 局域网场景下可忽略
- **答辩可能被问**：为什么不用多线程？→ 答：避免线程同步复杂度；游戏主循环本身就是天然的轮询驱动，非阻塞 IO 与它天然契合。

## D-008 采用「缩圈关卡」机制，为排行榜与档案提供数据来源

- **日期**：2026-10-10
- **背景**：D-004 把游戏砍成「极简多人」（只有飞船移动），
  但需求中包含「排行榜」与「关卡进度」。**没有分数、没有关卡，这两个需求就没有数据来源。**
- **决定**：加入**缩圈关卡**机制 —— 场地每隔 S 秒向内收缩，玩家须往内移动；
  出界后有 5 秒宽限，超时即淘汰。成绩为 `max_phase`（到达的最高阶段）与 `survive_seconds`。
- **理由**：
  1. **成本低**：约 165 行 / 10~15 小时（占预算 5~7%）
  2. **不引入敌人 AI** —— 纯逻辑，不滚雪球
  3. **一次解决两个问题**：排行榜有数据、`关卡进度` 名正言顺
  4. **增加可测内容**：边界同步字段、阶段事件、淘汰事件 → 论文素材变多
  5. **演示更生动** —— 场地收缩是肉眼可见的变化，比静止圆点有说服力
  6. **可先单机开发**：不依赖网络，接入时只是多同步一个字段
- **备选方案**：
  - 用玩家战绩类指标（存活时长 / 移动距离）替代 → 成本几乎为零，但「排行榜」名不副实
  - 加回敌人波次 → 成本 +250 行以上，**会使预算超支 40%+，不可行**
- **代价 / 风险**：
  - ⚠️ 时间预算已超支约 20%，本项再加 5~7%
  - ⚠️ **必须实现淘汰机制**，否则玩家永不失败、成绩对所有人相同、排行榜失去意义
- **实施安排（重要）**：

  | 项 | 安排 |
  |---|---|
  | 阶段 | 第 5~6 阶段（核心同步跑通**之后**） |
  | 排序理由 | 依赖同步框架，顺序反过来会返工 |
  | **砍掉条件** | 第 12 周时进度落后超过 2 周 → **直接砍** |
  | 砍掉后替代 | 排行榜改用存活时长，`关卡进度` 改称 `玩家档案` |

- **答辩可能被问**：为什么不做真正的关卡？→ 答：题目是**数据通信系统**，
  关卡只需提供可同步的进度与成绩数据；缩圈以 5% 的成本实现了这一点，而无敌人 AI 就不会拖垮主线。
