## D-001 数据库驱动用 PyMySQL，而不是 mysqlclient

- **日期**：2026-10-10
- **决定**：Django 连接 MySQL 使用 `PyMySQL`，配合 `pymysql.install_as_MySQLdb()`
- **理由**：
  1. **Windows 友好** —— `mysqlclient` 是 C 扩展，Windows 上安装需要编译环境（Visual C++ Build Tools），经常装不上；PyMySQL 是纯 Python，`pip install` 即可
  2. 本机是 Windows 开发环境，优先保证「装得上、跑得通」
- **备选方案**：`mysqlclient`（性能更好，但 Windows 安装门槛高）
- **代价 / 风险**：
  - PyMySQL 是纯 Python 实现，批量操作性能约为 mysqlclient 的 1/2 ~ 1/5
  - 需要额外安装 `cryptography`（MySQL 8 的 `caching_sha2_password` 认证需要）
- **落地方式**：项目包 `__init__.py` 中

  ```python
  import pymysql
  pymysql.install_as_MySQLdb()
  ```

- **答辩可能被问**：为什么不用官方推荐的 mysqlclient？
  → 答：Windows 环境下 C 扩展编译门槛高，PyMySQL 保证可移植性；性能差距在当前并发量级下可以忽略。

## D-002 降 Django 到 5.2 LTS，而不是升级 MySQL 到 8.4

- **日期**：2026-10-10
- **背景**：venv 中安装的 Django 6.1.2 连接 MySQL 8.0.41 时直接抛错：

  ```
  django.db.utils.NotSupportedError: MySQL 8.4 or later is required (found 8.0.41).
  ```

  经查 Django 官方 ticket [#36624](https://code.djangoproject.com/ticket/36624)：**Django 6.1 起将 MySQL 最低版本提高到 8.4**。这是框架源码里的硬性检查，没有任何配置项可以绕过。

- **决定**：把 venv 中的 Django 降到 **5.2 LTS**（实际安装 5.2.18）
- **理由**：
  1. **动作最小** —— 只更换 venv 中的一个包；升级 MySQL 需要下载 MSI、运行图形安装器、重启服务，并承担数据迁移风险
  2. Django 5.2 是 **LTS 版本**，维护到 2028 年，稳定性有保障
  3. Django 5.2 支持 MySQL 8.0.11+，与本机 8.0.41 匹配
  4. 毕设周期内不需要 Django 6.x 的新特性
- **备选方案**：升级 MySQL 到 8.4 LTS
- **代价 / 约束**：
  - ⚠️ **在升级 MySQL 之前，不能把 Django 升到 6.x**
  - 系统 Python 里另有一个 Django 5.0.3，与 venv 隔离；**运行项目必须使用 venv 的解释器**
- **验证结果**：降级后实测通过

  ```
  ('8.0.41', 'myproject', 'django_user@localhost', 'utf8mb4_unicode_ci')
  Django version : 5.2.18
  ```

- **答辩可能被问**：为什么不用最新版 Django？
  → 答：框架版本应在满足需求的前提下选择稳定版；5.2 是 LTS，且与本机数据库版本兼容，避免了升级数据库带来的额外风险。

## D-003 渲染采用几何多边形飞船，不使用位图素材

- **日期**：2026-10-10
- **决定**：玩家角色用 `pygame.draw.polygon` 绘制几何多边形（箭头/三角），机头指向行进方向
- **理由**：
  1. **零素材** —— 不需要找图、不存在版权问题
  2. **风格天然统一** —— 素材风格不统一是「廉价感」的头号来源
  3. **永不失真** —— 矢量绘制任意分辨率都锐利（对比：现有 `enemy0.png` 20×15 被拉到 30×30 已变形）
  4. **染色 / 发光 / 拖尾都容易加**
  5. 有朝向，符合「飞机大战」的直觉
- **备选方案**：位图精灵（`hero.png` 可染色复用，但仅 40×50，放大发虚且难统一风格）
- **代价 / 风险**：视觉上限低于精细美术资源（但本项目重点不是美术）
- **可逆性**：**完全可逆** —— 渲染层不影响通信系统
- **答辩可能被问**：为什么不用图片素材？→ 答：实时游戏的重点是通信；几何渲染保证风格统一、零素材依赖，且不影响任何网络层设计。

## D-004 游戏形态定为「竖版飞机大战 + 关卡 + BOSS」

- **日期**：2026-10-10（**取代同日早先的「极简多人」版本**）
- **决定**：游戏做**竖版飞机大战（弹幕射击）**：
  - **1~4 人合作**，**2 关 × 5 波**，**1 个三阶段 BOSS**
  - **3 种敌机**（直线俯冲 / 横向移动 / 追踪玩家）、**3 种弹幕**（直线散射 / 扇形 / 追踪弹）
  - **5 级火力**（伤害 + 射速 + 形态三重递进）、**拾取道具**升级
  - **几何绘制，零素材**，**720 × 960 竖版**窗口
- **演进过程（诚实记录）**：完整双摇杆 → 极简多人 → 抢靶 → **飞机大战**
- **理由**：
  1. **弹幕游戏是实时同步负载最重的类型之一** —— 200+ 颗子弹的高频生成/移动/销毁，是真正的同步难题，
     比「几个方块移动」有料得多（快照从 ~200 B 涨到 ~1974 B，带宽差 5 倍）
  2. **实测证明硬件撑得住**：4 人 + 30 敌机 + 200 子弹 = **0.45 ms/tick = 0.90 % 单核**
     （⚠️ 2026-10-26 量纲更正：原文写 8.9 %，是按 200 Hz 误算的，见 **D-027**；
     E9 正式实测同规模为 **1.016 ms / 2.0 %**）
  3. **天然有死亡条件**（被敌机/弹幕击中掉血），解决了抢靶方案「游戏永不结束」的漏洞
  4. **可复用现有代码约 80%** —— 玩家、敌机、子弹、碰撞的结构都已存在
  5. **动机**：学员明确表示想做飞机大战。**5 个月的项目，动力比省时间重要**
- **备选方案**：
  - 「极简多人」（只有方块移动）→ 同步负载太轻，实验数据单薄
  - 「抢靶方案」→ 无死亡条件，游戏不会结束（已否决）
- **代价 / 风险**：
  - ⚠️ 游戏内容代码从约 160 行升至约 **540 行**，多约 **13~17 小时**
  - ⚠️ 时间预算从约 218 h 升至约 **222 h**（超预算约 10%）
  - **兜底**：优先级 **④（游戏内容）排在最后，超时第一个砍**，论文不受影响
- **答辩可能被问**：为什么做弹幕游戏而不是更简单的？
  → 答：弹幕游戏的同步实体数量最多（200+ 子弹），是最能暴露实时同步问题的场景；
  实测证明单机性能足够（仅占 **0.90 %** 单核；E9 正式实测 2.0 %），不存在做不动的风险。

## D-005 加入 HTTP 短连接层，与 TCP 长连接分层

- **日期**：2026-10-10
- **决定**：保留 Django，作为**主线的一部分**（非可选）：
  - **TCP 长连接**：实时同步（玩家位置、房间状态）
  - **HTTP 短连接（Django）**：登录、排行榜、玩家战绩
  - **MySQL**：用户与分数持久化
  - **Redis**：排行榜缓存
- **理由**：
  1. 题目是「数据通信**系统**」，分层设计比单一 TCP 服务器更完整
  2. 「按数据类型选择通信方式」是有质量的论文论点
  3. 环境（Django 5.2.18 / MySQL 8.0.41 / Redis）已就绪，边际成本可控
  4. TCP 连接用 HTTP 登录得到的 **token 认证**，两层自然衔接
- **备选方案**：纯 TCP 项目（省约 30 小时，但论文少一个论点）
- **代价 / 风险**：
  - ⚠️ **时间预算上升约 30 小时**（原估算 218 h → 约 248 h，而预算是 200 h）
  - ⚠️ **接口需要有调用方** —— 客户端要实现 HTTP 调用，且**不能在游戏主循环里阻塞**（见 D-007）
  - ⚠️ **排行榜缺少数据来源**（见 D-004）：当前玩法没有分数，需用玩家战绩类指标替代，或给玩法补一个极简得分机制
- **答辩可能被问**：为什么要两套通信方式？→ 答：实时数据要求低延迟高频次，适合长连接自定义协议；账号与战绩是低频请求-响应，HTTP 更简单可靠。按数据类型分层可降低系统整体复杂度。

## D-006 同步模型：服务端权威，客户端只上报输入

- **日期**：2026-10-10
- **决定**：客户端**只上报输入**（按键位掩码），坐标由服务端计算并广播。
- **理由**：
  1. **防篡改** —— 客户端无法直接伪造坐标
  2. 状态一致性由单一权威裁定，避免多端分歧
  3. 局域网 RTT < 5 ms，远小于一个 50 ms 的 tick，**不做客户端预测也不会感觉滞后**
- **备选方案**：
  - 客户端权威上报坐标（实现更简单，但可被任意篡改）
  - 服务端权威 + 客户端预测回滚（手感最好，但实现与调试成本高，列为进阶项 F12）
- **代价 / 风险**：
  - 客户端必须做**插值**，才能把 20 Hz 快照渲染成 60 fps 平滑动画
  - 服务端承担全部游戏逻辑计算（本项目规模下无压力）

## D-007 客户端网络 IO 采用非阻塞 socket + 每帧轮询

- **日期**：2026-10-10
- **决定**：客户端 socket 设为非阻塞，在 pygame 主循环中**每帧检查一次**可读性。
- **理由**：
  1. **绝不能阻塞渲染主循环** —— 阻塞式 `recv()` 会让游戏在网络卡顿时直接冻死
  2. 单线程、无锁、无并发 bug，逻辑简单可预测
  3. 便于调试（所有事情都发生在主循环里，没有线程交错）
- **备选方案**：独立接收线程 + 队列（编程模型更熟悉，但引入线程同步与退出处理问题）
- **代价 / 风险**：
  - 需要自己处理**部分写**（`send` 未发送完）与发送缓冲队列
  - 每帧轮询引入最多 1 帧（约 16 ms）接收延迟 —— 局域网场景下可忽略
- **答辩可能被问**：为什么不用多线程？→ 答：避免线程同步复杂度；游戏主循环本身就是天然的轮询驱动，非阻塞 IO 与它天然契合。

## D-008 采用「缩圈关卡」机制，为排行榜与档案提供数据来源

- **日期**：2026-10-10
- **状态**：⛔ **已被 D-009 取代**（保留记录，不删除）
- **背景**：D-004 当时把游戏砍成「极简多人」（只有飞船移动），
  但需求中包含「排行榜」与「关卡进度」，**没有分数、没有关卡，这两个需求就没有数据来源**。

- **保留价值**：作为「方案演进」的记录，论文的「方案选型」一节可以对比讨论

## D-009 游戏内容：射击 + 关卡 + BOSS（取代 D-008 的缩圈方案）

- **日期**：2026-10-10
- **决定**：
  - **玩家**：左右移动 + **自动向上射击**，3 点 HP，受击后 1.5 s 无敌帧
  - **火力**：**5 级**，伤害 + 射速 + 形态三重递进（单发 → 双发 → 三发扇形）
  - **道具**：击杀 15% 掉落，拾取升级；满级后转分数；**被击中降 1 级**
  - **敌机 3 种**：直线俯冲 / 横向移动 / 追踪玩家
  - **弹幕 3 种**：直线散射 / 扇形 / 追踪弹
  - **关卡**：2 关 × 5 波（50 + 80 架），波次「清完或超时 25 秒」推进
  - **BOSS**：1 个，3 阶段，血量 = **1250 × 进入时人数**
  - **失败条件**：玩家阵亡 10 秒后自动复活（火力重置为 1）；**全员同时阵亡才结束本局**
- **理由**：
  1. **一次解决三个问题**：排行榜有数据（分数）、关卡进度有名目、游戏有结束条件
  2. **同步负载大幅提升** —— 从「几个方块」变成 200+ 子弹，快照 1974 B（**39.5 KB/s**），
     序列化对比实验的差异从「不明显」变成可观
     （⚠️ 当时写的「5.6 倍」是**含 5 道具的纸面估算**；**E1 实测 4.7 倍**，见 E1 实验记录）
  3. **引入真实的同步难题** —— 高频瞬时实体的生成/销毁，是实时网络同步的经典问题
  4. **服务端权威有更多体现** —— 命中判定、伤害计算、火力等级、计分全在服务端
- **备选方案**：
  - 缩圈方案（D-008，已否决）
  - 「子弹 + 静态靶子」抢靶方案 → 无死亡条件，且同步实体种类少
- **代价 / 风险**：
  - ⚠️ 游戏代码从约 160 行升至约 **540 行**（+13~17 h）
  - ⚠️ BOSS 血量系数 1250 假设玩家平均火力 Lv4，**需实机调整**
- **答辩可能被问**：为什么要做 BOSS？
  → 答：BOSS 是一个**多阶段状态机**的同步对象（血量 + 阶段），
  与普通敌机、子弹、道具的同步策略不同，能覆盖更多同步场景。

## D-010 三阶段解耦：占位对象 → 完整游戏

- **日期**：2026-10-10
- **背景**：优先级 ④（游戏内容）排在最后（见 D-013），
  但阶段 ①~③（通信 / 抓包 / 性能）**必须先有可同步的对象**才能验证。
- **决定**：把**网络层与游戏层解耦**，分三阶段演进：

  | 阶段 | 同步对象 | 目的 |
  |---|---|---|
  | 阶段 1~3（第 1~13 周） | **极简占位**：几个方块在场地内移动 | 独立验证通信系统 |
  | 阶段 4（第 14~17 周） | 逐步替换为敌机、子弹、道具 | 增加负载与复杂度 |
  | 最终 | 完整飞机大战（含 BOSS） | 演示效果 |

- **理由**：
  1. **通信系统可独立验证** —— 用最简单的对象证明协议、粘包、同步、并发都是对的
  2. **占位方块是最好的协议测试工具** —— 排查问题时排除游戏逻辑干扰
  3. **风险前移** —— 最难的部分先做完，游戏内容可随时削减
- **关键约束**：占位阶段的**实体结构、同步机制、渲染管线与最终版本一致**，只是实体类型少。
  **替换游戏内容时通信层不用改。**
- **答辩可能被问**：占位阶段是不是白做了？
  → 答：不是。它证明了通信系统独立于游戏内容可用，这正是「数据通信系统」作为交付物的核心论点。

## D-011 性能硬约束：同屏实体上限

> ### ⚠️ 量纲更正（2026-10-26，见 D-027）
>
> 本条下方基准表的 **CPU 列整整放大了 10 倍**：它是按 **200 Hz** 算出来的
> （= `ms/tick × 200`），而本协议 tick 率是 **20 Hz**。
> 正确值应为 `ms/tick × 20 ÷ 1000 × 100`，即**原表数值 ÷ 10**：
>
> | 规模 | 原表 CPU | **更正后（20 Hz）** |
> |---|---|---|
> | 4 / 30 / 200 | 8.9 % | **0.90 %** |
> | 8 / 50 / 400 | 24.1 % | **2.42 %** |
> | 16 / 100 / 800 | 87.3 % | **8.74 %** |
>
> **因此本条理由 1「超过上限会让单帧耗时逼近预算」在 20 Hz 下是不成立的** ——
> 原型最大规模（16/100/800）的 4.37 ms 只占 50 ms 预算的 **8.7 %**。
> **30 / 300 这两个上限值本身保留**（它是保守设计选择，为完整游戏逻辑留余量，
> 而且从没被推翻过），但**原来的量化依据作废**。
>
> ✅ **E9 正式实验（2026-10-25，9 档 × 2 轮）已取代该原型基准**：
> 30/200 实测 **1.016 ms / 2.0 % 单核**、100/800 = 5.738 ms / 10.5 %、
> 250/2000 = 30.797 ms / **61.0 %**（跨过 50 % 舒适线，拐点约 215/1720）。
> 详见 `docs/experiments/E9-实体数影响.md`。

- **日期**：2026-10-10
- **背景**：实跑基准测试（Ryzen 7 7735H / 31.2 GB）：

  ```
  players enemies bullets   |  ms/tick | snapshot | CPU@20Hz（⚠️ 实为 200 Hz，见上方更正）
  --------------------------------------------------------------------
        4      30     200   |    0.45  |    1655 B |   8.9 %   ← 设计目标   （更正：0.90 %）
        8      50     400   |    1.21  |    3231 B |  24.1 %              （更正：2.42 %）
       16     100     800   |    4.37  |    6453 B |  87.3 %   ← 单核极限   （更正：8.74 %）
  ```

- **决定**：
  - **同屏敌机上限 = 30**
  - **同屏子弹上限 = 300**
  - **刷怪前必须检查当前敌机数**，超上限则延后本波剩余敌机的刷新
- **理由**：
  1. ~~tick 预算为 50 ms（20 Hz）；超过上限会让单帧耗时逼近预算，**导致掉帧**~~
     → **已作废**（量纲更正后不成立，见上方）
  2. **这是硬件决定的，不是设计偏好** —— 因此它必须现在定，而不是"后面调"
     → 更正后仍是**保守的设计余量**，为其后叠加完整游戏逻辑（AI / 弹幕 / 道具 / 伤害结算）留空间
  3. 该保险机制**不会死锁** —— 敌机被击杀后释放名额，刷新继续，只是节奏变慢
- **代价 / 风险**：
  - ⚠️ 关卡编排（每波敌机数）受此约束，不能"一口气刷 60 个敌人"
  - 实验 E2（并发测试）会主动突破此约束以寻找性能拐点 —— **这是有意的**
  - 更正后可知：**真实余量比原先认为的大得多**（30/200 只占 2.0 %），
    上限若日后想放宽，有 E9 数据可依
- **答辩可能被问**：为什么定 30 而不是 50？
  → 答：这是**保守的设计余量**，为完整游戏逻辑叠加留空间。
  ⚠️ 注意：本条原始的量化依据（"50 个敌机时单核占用已达 24 %"）**是量纲错误的**，
  更正后应为 2.42 %；按 E9 正式实测，30/200 仅占 2.0 % 单核。**回答时不要引用旧数字。**

## D-012 协议坐标值域：出屏即剔除

- **日期**：2026-10-10
- **背景**：基准测试时发现的**真实 Bug**：

  ```
  struct.error: 'H' format requires 0 <= number <= 65535
  ```

  子弹飞出屏幕后坐标为**负数**，而协议坐标用 `uint16`（只能表示 0~65535），**编码直接崩溃**。

- **决定**：**出屏即剔除** —— 坐标越界的实体**不写入快照**，客户端据此删除该实体。
- **理由**（对比另外两个方案）：

  | 方案 | 评价 |
  |---|---|
  | **A. 出屏即剔除** | ✅ **采用**：省带宽 + 客户端逻辑更简单 |
  | B. 改用 `int16` | 支持负坐标，但浪费一半值域 |
  | C. 序列化时截断 | ❌ 数据错误 |

- **衍生设计原则**：**快照是全量真相**。
  客户端每收到一帧快照，就**完全以快照为准**重建本地实体表 —— 快照里没有的实体一律删除。
  **因此无需额外的「删除实体」消息。**
- **答辩可能被问**：协议设计时怎么考虑数据值域？
  → 答：坐标用 `uint16` 是无符号的，而实体越界后会产生负值。
  这提醒我们协议字段的值域必须与业务数据的实际范围对齐；本项目的解法是「不同步越界实体」，
  既避开了值域问题，又顺带省了带宽。

## D-014 asyncio 服务端中不能使用阻塞式数据库驱动

- **日期**：2026-10-10
- **背景**：TCP 服务端在一局结束时要写 MySQL（成绩）和 Redis（排行榜）。
  但服务端是 **asyncio 单线程事件循环**，而 `pymysql` 是**阻塞式**驱动 ——
  一次数据库写入会**阻塞整个事件循环**，导致同一时刻所有客户端掉帧。
- **决定**：
  1. **MySQL 写入放到线程池** —— `await asyncio.to_thread(...)`（Python 3.9+），不要把阻塞调用直接放进协程
  2. **Redis 用异步客户端** —— `redis.asyncio`（`redis` 包已自带，无需额外依赖）
  3. **写入失败必须重试 + 落盘兜底** —— 成绩不能因为数据库抖动而丢失
  4. 数据库操作**只在结算时发生**，不在 20 Hz 的游戏循环里
- **理由**：
  1. 「事件循环里不能有阻塞调用」是 asyncio 的核心纪律，违反会拖垮全部并发连接
  2. 结算是一局一次的低频操作，放线程池的额外开销可忽略
  3. 成绩是毕设里唯一的持久化数据，**丢了就白打了**
- **备选方案**：
  - 改用异步 MySQL 驱动（`aiomysql`）→ 更纯粹，但多一个依赖、生态较小
  - 用独立进程处理数据库写入（消息队列）→ 过度设计
- **代价 / 风险**：
  - `asyncio.to_thread` 会占用线程池线程，高并发结算时需要留意线程池大小
  - **必须在早期就做对** —— 后期发现事件循环被阻塞，排查成本很高
- **答辩可能被问**：为什么数据库写入要放线程池？
  → 答：asyncio 是单线程事件循环，任何阻塞调用都会卡住**所有**连接。
  `pymysql` 是同步驱动，必须 `to_thread` 隔离；这也是「事件驱动模型下如何与阻塞式组件共存」的典型问题。

## D-015 第 1 步用阻塞式单客户端回声程序起步，不直接上 asyncio

- **日期**：2026-10-19

  - 直接用 asyncio 写回声服务器 → 这确实是最终架构，但 `await reader.read()` 把“字节流无边界”藏了起来，容易误以为“一次 read 就是一条消息”

- **代价 / 风险**：
  - 这段代码**不是最终服务端**，第 5 步会被 asyncio 版本取代；但 `recv` / `sendall` / `accept` 的概念与排错经验完全复用
  - **单客户端是刻意保留的限制，不是 Bug**
- **答辩可能被问**：为什么不用 asyncio 一步到位？
  → 答：先理解阻塞 IO 的行为和瓶颈，才能说清 asyncio 解决了什么问题；最终服务端确实用 asyncio，但那是第 5 步的重构目标。

## D-016 网络实验环境：VMware VMnet1 仅主机 + netem（桥接 WiFi 已实测否决）

- **日期**：2026-10-19（同日追加桥接实测，方案定稿）
- **背景**：`01-系统架构.md §11.2` 要求阶段 1 实测“客户端连本机局域网 IP 能否拿到真实 RTT / 抖动”。两轮实测后，结论如下。

### 第一轮：本机自连局域网 IP（代码侧实测）

- `ping 127.0.0.1` 与 `ping 10.140.71.127` 均 **< 1 ms**
- 回声 RTT **0.03~0.14 ms**
- 向 `10.140.71.127` 传 16 MB：**1145.8 MB/s**，WLAN 网卡收发增量仅 **0.001 / 0.012 MB**
- **结论**：Windows 把发往本机地址的流量短路到回环，根本没经过网卡；`§11.2` 的兜底条件（0.1 ms 量级）触发。

### 第二轮：VMware 桥接 WiFi（用户亲自实测）

| 测试 | 结果 |
|---|---|
| 桥接 + 校园网 `GDPZ-student-5G` | **虚拟机拿不到 IPv4**（校园网拒绝虚拟机 MAC） |
| 桥接 + 手机热点 | 虚拟机拿到 `10.152.181.161/24`，能 ping 通 |
| host → VM（热点、桥接） | **RTT = 0.00 ms，20/20 全成功** |
| host → 网关 `10.152.181.188` | **RTT = 4.67 ms（1~6 ms）**；8000 字节包 **9.60 ms** |
| 加静态路由强制走网关 | `route add 10.152.181.161 mask 255.255.255.255 10.152.181.188` 后**仍为 0 ms** |

**关键判断**：

- 网关 RTT 4.67 ms、大包 9.60 ms，说明 **ping 本身有精度**；VM 的 0.00 ms 是**真 0**，不是“测不出来”
- 改 L3 路由表仍然 0 ms → **VMware 的桥接在 L2（链路层）直接截获，绕不过去**
- 因此：**桥接 WiFi 这条路彻底放弃**；已改回 NAT，残留静态路由已删除

### 最终决定

1. **不装 VirtualBox、不重装 Ubuntu Server**：使用现有 **VMware Workstation + Ubuntu Desktop**（能登录、能跑 `tc`）
2. 虚拟机只用 **仅主机模式（VMnet1）** 跑服务端；宿主客户端连 VM 的 VMnet1 地址
3. **延迟 / 丢包类实验（E4 / E5）**：在 Ubuntu 内用 **`tc netem`** 注入，参数精确、可复现
4. **抓包（E7）**：Npcap 回环适配器，或 Ubuntu 内 `tcpdump -w` 导出 pcap
5. **本机多进程**继续用于：协议、粘包、并发、房间逻辑、抓包字段核对
6. **借设备 + 手机热点**：降级为**可选**，只做真实性交叉验证，不列入主线
7. **第 13 周性能测试前**完成 VMnet1 + netem 配置与验证

### 理由

1. 桥接实测 0 ms 且静态路由无效，**桥接不可用**；校园网还直接拒绝 VM MAC
2. 仅主机模式不依赖校园网 / 热点，链路稳定，guest 有独立 TCP/IP 栈
3. `tc netem` 在**内核态**做排队 / 延迟 / 抖动 / 乱序 / 丢包，比应用层 `sleep` 更接近真实网络，且可精确复现
4. 现有环境已具备，零安装、零重装，避免引入第二个虚拟化平台

### 备选方案（均不采用）

- **桥接 WiFi** → 实测否决（校园网拒绝 MAC；热点下 0 ms）
- **应用层注入**（发送前 `sleep` / 随机延迟）→ 只影响应用线程，模拟不了内核排队 / 乱序；否决
- **VirtualBox / Hyper-V** → 需要新装或重装，引入第二平台；否决
- **借第二台设备 + 热点** → 真实性最好，但不可重复、协调成本高；只保留为可选验证

### 代价 / 风险

- VMnet1 的基线 RTT 也接近 0；必须用 netem **主动注入**可观测的延迟 / 抖动，论文中要写清这是**受控仿真**，不是真实 WiFi
- netem 默认作用于 guest **出口**；若要双向对称延迟，需要在 guest ingress 用 `ifb`，或再加一台 Linux 路由 VM（按实验需要）
- Npcap 安装时要勾选 loopback support；若抓不到，改用 Ubuntu 内 `tcpdump -w` 导出 pcap
- VMnet1 的 IP 可能随 VM 重启变化；实验脚本要**动态读取**，不要硬编码

### 答辩可能被问

- **为什么不用桥接？** → 实测 host→VM 20/20 次 0.00 ms，网关 4.67 ms；加静态路由仍 0 ms，说明 VMware 桥接在 L2 截获，桥接 WiFi 拿不到真实链路指标。
- **为什么用 netem，不用应用层 sleep？** → netem 在内核态排队，能模拟延迟 / 抖动 / 乱序 / 丢包；应用层 sleep 只延迟发送线程，无法模拟队列和乱序，也不可精确复现。
- **host-only 的数据算网络实验吗？** → guest 有独立 TCP/IP 栈，netem 提供可控链路参数；外部有效性再用借设备做一次性验证。

## D-017 第 2 步用 4 字节大端长度前缀划清消息边界

- **日期**：2026-10-19
- **决定**：
  - 本步帧格式：`uint32 大端长度 + payload`，长度**只算 payload**，不含 4 B 头
  - 接收端用 `recv_exact()` 循环读满；`recv_frame()` 先读 4 B 长度，再读 N B
  - 单帧载荷上限 `MAX_PAYLOAD = 64 KiB`；超限抛 `ProtocolError` 并断开连接
  - 第 4 步把 4 B 长度扩展成 **12 B 帧头**（magic / version / type / seq / length），
    “先读长度、再读载荷”的核心不变
- **理由**：
  1. **二进制安全**：长度前缀对任意字节都成立；分隔符（`\n`）遇到载荷里的 `\n` 必须转义
  2. **大端 = 网络字节序**：`struct` 的 `!I` 明确表达跨平台一致
  3. **把“可能只收到一部分”的循环收敛到一个函数**：业务代码只看到完整消息，不必重复写 while
  4. **64 KiB 上限**：防止对端声明 4 GB 长度把内存吃光；本项目快照约 2 KB，留了 30 倍余量
- **备选方案**：
  - 分隔符（`\n` / `\0`）→ 二进制载荷要转义，体积和复杂度都上升（否决）
  - 定长包 → 载荷可变时浪费带宽（否决）
  - 每次 `recv(65536)` 后自己切 → 还是要处理半包 / 粘包，且缓冲区逻辑散落各处
- **代价 / 风险**：
  - 每帧多 4 B；1 B 的输入包头部是载荷的 4 倍（第 4 步变 12 B 后是 12 倍，见 `02 §4.1`）
  - `recv_exact()` 是**阻塞版本**；第 6 步客户端改非阻塞后，要换成“缓冲区 + 状态机”的 FrameParser
- **答辩可能被问**：长度字段为什么用 4 字节，不用 2 字节？
  → 答：2 字节上限 65535 B，当前快照够用，但扩展余量小；4 字节是通用做法，只多 2 B，
  并且后面加 seq / type 时帧头本身就会超过 4 字节。

## D-019 第 4 步落地 12 字节帧头：magic / version / type / seq / length

- **日期**：2026-10-19
- **决定**：
  - `HEADER = struct.Struct("!HBBII")`，固定 12 B
  - 字段：`magic=0x4A59`、`version=1`、`type=uint8`、`seq=uint32`、`length=uint32`
  - `recv_frame()` 返回 `Frame(msg_type, seq, payload)`；magic / version / length 在**读载荷之前**校验
  - `pack_frame()` 显式检查 type / seq 值域；`ProtocolError` 统一表示帧错误
  - 阶段 1 回声用临时 type `0x7F`，避开正式 `C→S 0x0X` / `S→C 0x8X`
- **理由**：
  1. type 让一条连接承载多种消息；seq 支持请求-响应 RTT、丢包检测、防重放
  2. magic / version 让“连错端口 / 协议版本不匹配”在帧层快速失败，不把垃圾当消息解析
  3. 长度仍在帧头里，第 2 步的拆包逻辑不变，只是偏移从 0 变成 8
  4. 12 B 是 `02 §4.1` 已定稿的格式，代码与文档一致
- **备选方案**：
  - 只有 4 B 长度（第 2 步）→ 没有 type / seq，无法区分消息、关联响应；否决
  - 8 B（magic + length）→ 省 4 B，但丢掉 version / type / seq；否决
  - JSON 文本协议 → 可读性好但解析慢、体积大（02 §1.1 已否决）
- **代价 / 风险**：
  - 每帧 12 B；1 B 的 `C_INPUT` 载荷头部是 12 倍（02 §4.1），后续用“批量合并”优化
  - 帧层只做结构校验，type 的业务合法性留给第 5 步的消息分发
  - `recv_exact()` 仍假设阻塞 socket；第 6 步非阻塞要改 FrameParser
- **答辩可能被问**：为什么帧头要 12 B，不能只留长度？
  → 答：长度只解决“消息边界”；type 决定交给谁处理，seq 用于请求-响应关联 / RTT / 防重放，
  magic / version 让错误在帧层快速失败。12 B 是功能与开销的折中，且与 `02 §4.1` 一致。

## D-020 第 5 步：asyncio 单线程 + 20 Hz tick + 全量玩家快照广播

- **日期**：2026-10-21
- **决定**：
  1. 服务端用 **asyncio 单线程事件循环**（`asyncio.start_server`），不用“每连接一个线程”
  2. `tick_loop` 固定 20 Hz，用 deadline 累加（`next_tick += 0.05`），避免 `sleep(0.05)` 漂移
  3. 服务端权威：占位玩家坐标由服务端算，客户端只收快照（D-006）
  4. 快照用正式 `S_SNAPSHOT=0x84`，本阶段只带**玩家条目（11 B）**；敌机 / 子弹 / 道具计数固定 0
  5. 连接时服务端发临时 `S_WELCOME=0x7C`（player_id + color）；正式认证第 10 步再接
  6. `protocol/framing.py` 增加 `parse_header` / `recv_frame_async` / `send_frame_async`，同步 / 异步共用校验
- **理由**：
  1. 20 Hz 广播是实时同步的骨架；先跑通“多客户端 + tick + 广播”，再谈房间 / 输入 / 游戏内容
  2. 用正式快照头 + 玩家条目，第 6 步渲染时不用重写协议
  3. asyncio 单线程无锁，符合 D-007 / D-014 的并发纪律；慢客户端问题后面用发送队列解决
  4. 服务端权威避免客户端伪造坐标（D-006）
- **备选方案**：
  - 每连接一个线程 → 锁 / 同步复杂度高，否决
  - `selectors` → 更底层、代码更多；asyncio 已封装好，否决
  - JSON 快照 → 体积大、解析慢，否决
  - 增量快照 → 第 3 梯队 E6 再考虑，当前全量足够（D-012）
- **代价 / 风险**：
  - 广播是 O(客户端数)，且 `await drain()` 是串行的；慢客户端会拖慢 tick，后续改为每客户端队列 / 丢旧帧
  - 快照只支持玩家；`unpack_snapshot` 会拒绝非 0 的敌机 / 子弹 / 道具计数，后续扩展
  - `S_WELCOME` 是临时类型，第 10 步认证后替换
  - 当前没有输入，坐标是占位摆动；第 6 步接 `C_INPUT`
- **答辩可能被问**：为什么用 asyncio 单线程？20 Hz 怎么保证？为什么全量快照？
  → 答：asyncio 单线程避免了线程锁和共享状态竞争，20 Hz 用固定 deadline 累加而不是 `sleep` 漂移；
  全量快照让客户端“以快照为准”重建实体表，逻辑简单且天然处理删除（D-012），当前 4 人规模带宽足够。

## D-021 第 6 步：非阻塞客户端 + FrameParser + 一帧线性插值

- **日期**：2026-10-21
- **决定**：
  1. 客户端 socket 非阻塞，pygame 主循环每帧 `poll()` 一次；连接建立时允许阻塞（D-007）
  2. 新增 `FrameParser`：`bytearray` + `feed()` / `next_frame()`；半包留在用户态缓冲区，不阻塞主循环
  3. 插值：保存上一帧 / 当前帧快照，在 50 ms 内用 `alpha 0→1` 线性过渡；**一帧（50 ms）滞后**
  4. 窗口 720×960；桌面高度 < 1000 px 时降为 600×800，坐标按比例缩放
  5. 本步不做键盘输入；服务端占位摆动
- **理由**：
  1. 阻塞 `recv` 会冻住 60 fps 主循环；非阻塞 + `FrameParser` 是 D-007 的落地
  2. 20 Hz 快照直接画会一跳一跳；线性插值把 20 Hz 补成 60 fps，代码少且可解释
  3. 一帧滞后换来“不做预测”的简单性；局域网 50 ms 可接受，预测回滚是第三梯队
  4. 占位方块先验证渲染 / 插值管线，游戏内容最后加（D-010）
- **备选方案**：
  - 独立接收线程 + 队列 → 线程同步复杂，D-007 已否决
  - asyncio 客户端 + pygame → 两个事件循环集成麻烦；本阶段用非阻塞 socket 更直接
  - 指数平滑 → 简单，但和快照时间无关，实验误差不好解释
  - 快照延迟缓冲（渲染 `now - 100 ms`）→ 更标准，但复杂度高；E4/E5 前再升级
- **代价 / 风险**：
  - 一帧 50 ms 视觉滞后；对占位演示足够
  - 没有输入；服务端不会因客户端操作改变位置
  - 断线提示 / 自动重连未做；当前显示 disconnected，按 ESC 退出
  - `FrameParser` 缓冲区没有硬上限，但单帧受 `MAX_PAYLOAD` 限制，完整帧会及时消费
- **答辩可能被问**：为什么不用独立线程收包？为什么要插值？
  → 答：独立线程会引入锁和退出同步问题；主循环本身就是 60 fps 的天然轮询，非阻塞 socket + 用户态
  缓冲区与它最契合。20 Hz 快照直接渲染会跳，插值用两帧之间的线性过渡把画面补平滑；
  代价是一帧延迟，但换来了不做预测的简单性。

## D-023 7b：定频输入 + 服务端权威运动学 + 回显式心跳

- **日期**：2026-10-23
- **前置**：7a（D-022）只验证了「连接 + 广播」，服务端收到客户端消息后直接丢弃。
  7b 接通**客户端 → 服务端**的上行链路。

### 决定一：输入用**定频 20 Hz** 发送（与 tick 同频）

- 载荷只有 1 字节位掩码（`02 §4.5`），整帧 13 B；20 Hz → **260 B/s/客户端**
- 发送的是「**当前按住什么**」（状态），不是「刚刚按了什么」（事件）
- 客户端用 `next_input_at += INPUT_INTERVAL`（deadline 累加），不是 `= now + 间隔`
- **理由**：
  1. 与 tick 同频，服务端每个 tick 用最新 keys 算一次位移，不重复应用也不漏
  2. 内容是状态 → **天然冗余，丢一帧下一帧自动补上**，不需要 ACK / 重传
  3. E9 要测「输入处理负载」，定频才有稳定的自变量
- **备选方案（否决）**：
  - **按键变化时才发**：带宽最省（随机输入下约 200 B/s），但万一「松开」那条没送到，
    服务端会以为玩家还按着 → 角色一直走。要修就得加 ACK / 冗余，复杂度不划算。
    它的真实优势只是「按键后最多省 50 ms」，而 D-006 已认定局域网不做预测也不滞后
  - **每帧 60 Hz 发**：780 B/s，服务端只用 20 Hz，多出的 2/3 是纯浪费
- **实测**：`next_input_at = now + 间隔` 会被**帧率量化** —— 60 fps 下 50 ms 不是
  16.7 ms 的整数倍，服务端实测只收到 **17 次/秒**；改成累加后稳定 **20 次/秒**。
  （服务端 `tick_loop` 早就用的是累加模式，这里统一了。）

### 决定二：服务端权威运动学（`server/movement.py`）

1. **坐标只在服务端算**，客户端发的是意图（D-006）；快照里**不回传 keys**
2. **整数像素 / tick**：`PLAYER_SPEED_PER_TICK = 15` → 300 px/s，2.4 s 横穿 720 px
3. **左右同时按 = 抵消不动**（`0b11` → dx=0）
4. **边界钳制 `[20, 700]`**：方块按中心点绘制，不留余量会有半个身子出屏
5. **输入保质期 `INPUT_TTL = 0.5 s`**：超时未收到新输入即视为松手
6. **保留位先掩掉**（`keys &= KEYS_MASK`），不报 `ERR_MALFORMED`
- **理由**：
  1. 整数定点满足 `02 §4.3` 的「禁用浮点」，且带来**确定性** ——
     同样的输入序列必然得到同样的轨迹，实验可逐帧对账；浮点累加的末位误差会让复现变成玄学
  2. 抵消是真实玩家会做的事（同时按 A/D），抵消比「左优先」更符合直觉
  3. 保质期防的是「幽灵移动」：客户端卡死/断网前的最后一帧若是「按住左」，
     角色会一直走到 15 s 超时 —— 观感上是闹鬼
  4. 掩保留位是**前向兼容**：将来加「上下移动」（bit 2）时，旧服务端只是「当没看见」，不会断连
- **备选方案（否决）**：
  - 浮点速度 × 时间 → 违反 `02 §4.3`，且破坏确定性
  - 不设 TTL，一直用旧 keys → 出现上述幽灵移动
  - 保留位非 0 就报 `ERR_MALFORMED` → 将来加新位会导致新旧版本互不兼容
- **代价**：15 px/tick 的粒度不支持「加速 30%」这类道具；届时要改「定点 1/16 像素」

### 决定三：心跳 —— **原样回显 `client_time`**

- `C_HEARTBEAT(client_time)` → `S_HEARTBEAT_ACK(client_time, server_time)`
- 服务端把 `client_time` **原样抄回**，客户端本地算 `rtt_ms()`；帧头 `seq` 回带请求的 `seq`（`02 §4.2`）
- 时间戳 = **`time.monotonic()` 毫秒取低 32 位**；差值用无符号 `(now - sent) & 0xFFFFFFFF`
- 超时 = **15 s**（3 × 心跳间隔，`02 §7`），**每秒检查一次**（不是每 tick）
- `last_recv_at` 由**任何**收到的消息更新，不只是心跳
- **理由**：
  1. 回显式让 RTT 完全在客户端本地算，**不依赖两端时钟同步** —— 钟差会直接污染 RTT
  2. `monotonic` 只增不减；`time.time()` 被 NTP 回拨时 `now - sent` 会变成负数
  3. 无符号差值一行掩码即免疫 32 位回绕（49.7 天），
     例：`sent=0xFFFFFFF0, now=0x00000010` → 32 ms 而不是负数
  4. 每秒检查一次够了：超时精度差 50 ms 无所谓，省下的 tick 预算留给游戏逻辑
- **备选方案（否决）**：用两端时间戳相减 → 必须先对表；微秒时间戳 → 32 位只能表示 71 分钟，回绕太频繁

### 决定四：「判定 / 关闭 / 清理」三段分离

- `check_timeouts(now)` **只返回超时列表**，不关连接、不改字典
- `tick_loop` 负责 `writer.close()`；**唯一清理点**是 `handle_client` 的 `finally`
- **理由**：
  1. **可测** —— 测试塞一个假的 `now` 就能验 15 s 超时，不用真的等 15 秒
  2. 避免两处都改 `self.clients` 字典（删两次 / 删错人）
- **`--timeout 0` 关闭判定**：做「纯广播」基线实验时，客户端不发心跳也不会被踢 —— 用于**分离变量**

### 决定五：机器人与服务端统计

1. **单个机器人拆成 3 个协程**（`bot/agent.py`）：`_recv_loop` / `_input_loop` / `_heartbeat_loop`
   - 7a 单协程够用是因为它只收不发；`recv` 一阻塞发送就停，20 Hz 会退化成「有快照才发」
   - asyncio 单线程，`writer.write()` 同步追加，两个协程并发发**不会撕裂帧**；`drain()` 只是背压
   - 每个协程自己把异常收进 `result.errors` —— `TaskGroup` 中一个任务抛异常会**取消同组其他任务**，
     那会连统计一起清掉
2. **观察者与输入机器人是同一个机器人**，靠 `--input-hz 0` 切换；`--seed` 固定随机种子（第 i 个用 `seed+i`）
   - 避免「两份几乎一样的机器人，改一处忘一处」
3. **服务端每秒打印 tick 耗时 + 输入帧速率**（`server/stats.py` 的 `TickStats`）
   - D-022 要测「输入处理负载」，但 bot 只看得到自己这边的收发；
     服务端每 tick 花多少毫秒只有服务端知道（D-011 的 0.45 ms/tick 就是这么来的）
4. 机器人逻辑与 CLI 分家：`bot/agent.py`（怎么工作）+ `bot/main.py`（开几个、怎么汇总）

### 决定六：连带影响与文件划分

- **`client/console.py` 必须加心跳**：7b 起服务端有 15 s 超时，不发消息的调试客户端会被踢
- **观察者 bot 默认也发心跳**：同理；想复现 7a 的纯广播基线用 `--heartbeat 0` + 服务端 `--timeout 0`
- **`client/net.py` 补发送队列**（7a 遗留的 TODO）：非阻塞 socket 的 `send()` 可能部分写甚至零写，
  所以 `send()` 只排队、`flush()` 在每帧 `poll()` 里尽量写；`MAX_OUTBOX = 64 KiB` 防内存无限涨
- **新增 `protocol/world.py`**：世界尺寸（720×960 / 边距 20）放协议包
  - 理由：快照坐标的语义**依赖世界尺寸**，服务端边界与客户端缩放必须共用一份定义；
    各写一份会静默漂移（改了窗口忘了边界，玩家能走到看不见的地方，且不报错）
- **本步不实现 `S_PLAYER_LEAVE (0x86)`**：D-012 的「快照是全量真相」已覆盖
  （玩家断开后不再出现在下一帧快照里），事件同步留给游戏内容阶段（`02 §5.3`）
- **不实现防洪 `ERR_RATE_LIMITED`**：等有认证和真实玩家再说

### 代价 / 风险

- 上行**每帧 13 B 里 12 B 是帧头**（`02 §4.1`）；100 客户端 ≈ 26 KB/s 纯帧头开销
  → 「批量合并发送」仍是未做的优化项（`02 §12`）
- 没有客户端预测：按键到画面动隔一个 RTT + 最多一帧（第三梯队 F12）
- 广播仍是 O(客户端数²)，慢客户端的独立发送队列是 D-020 记的账，7b 没还
- 心跳只给 RTT，不给丢包率（TCP 保证不丢，丢包统计要等 E5 用 netem 注入）
- 新增 4 个模块文件（`protocol/world.py`、`server/movement.py`、`server/stats.py`、`bot/agent.py`）；
  `server/main.py` 从 162 行涨到 **241 行**，`bot/main.py` 反而从 177 行降到 **129 行**（机器人逻辑搬进了 `bot/agent.py`）

### 实测（本机 loopback，**不是最终网络实验数据**，D-016）

| 场景 | 连接 | 快照 | 输入 | 心跳 ack | 间隔 p50/p95 | RTT p50/p95 | errors |
|---|---|---|---|---|---|---|---|
| 10 输入 bot / 8 s | 10/10 | 1600 | 1600 | 20/20 | 47.3 / 62.9 ms | 0.0 / 1.0 ms | 0 |

- **单元测试**：42 → **88 个全过**（0.10 s）

### 答辩可能被问

- **为什么输入要定频发，不按需发？** → 答：发的是「当前按住什么」而不是事件，
  所以丢一帧下一帧自动纠正，不需要确认重传；按需发一旦丢了「松开」消息，
  服务端会以为玩家还按着，角色会一直走。
- **为什么坐标不让客户端算？** → 答：坐标是结果，客户端能直接说自己在哪里就能伪造位置。
  只发按键意图、服务端统一计算，保证单一权威（D-006）。代价是要等一个往返，局域网可忽略。
- **心跳为什么回显客户端时间？** → 答：RTT 完全在客户端本地算，不依赖两端时钟同步；
  若用两端时间戳相减，钟差会直接算进 RTT。时间戳用单调时钟并取无符号差值，连 32 位回绕也免疫。
- **为什么要给输入设保质期？** → 答：定频发送维持的是「最后状态」，
  客户端失联后服务端会继续按最后的按键移动角色。0.5 s 保质期把输入变成有有效期的意图。

## D-024 8a：用「占位实体」造出 E9 的自变量，并修通指标采集链路

- **日期**：2026-10-24
- **背景（开工前发现的缺口）**：第 8 步原计划直接跑 E9「实体数 → 带宽 / CPU」，
  但到 7b 为止服务端**只有玩家方块**：敌机 / 子弹的协议条目**没有实现**，
  `unpack_snapshot()` 还会**主动拒绝**非 0 的敌机计数。
  **也就是说 E9 的自变量根本不存在。** 因此把第 8 步拆成
  **8a（造实体 + 修通采集，本次）** 与 **8b（跑六档位出图，下次）**，
  与 7a/7b 一样先隔离变量（沿用 D-022 的做法）。

### 决定一：用「占位实体」而不是灌水字节、也不是先做游戏

- **做法**：敌机 / 子弹使用与最终版本**完全相同的协议条目与序列化路径**
  （敌机 9 B、子弹 8 B），但行为退化为**匀速直线**；数量由 `--enemies` / `--bullets` 指定
- **理由**：
  1. **这是 `01 §3.4` 自己定的原则** ——「实体结构、同步机制、渲染管线与最终版本一致，
     只是实体类型少；替换游戏内容时通信层不用改」。8a 是它的兑现，
     第 11 步把「匀速直线」换成「追踪 AI + 弹幕」时，`snapshot.py` / `metrics.py` / `plot.py` 一行都不用改
  2. **E9 要测的是服务端处理实体的真实开销**：每 tick 遍历 900 个实体推进位置、
     逐个 `struct.pack`、广播时每个客户端多写 7 KB。灌水字节只有最后一项
  3. **顺序上不能等**：D-013 的优先级是 ① 通信 → ② 抓包 → ③ 性能测试 → ④ 游戏内容，
     且第 13 周「性能测试没数据」是**红线**；先做游戏会把性能测试挤到红线之后
- **备选方案（否决）**：
  - **灌水字节**（往快照塞随机字节凑到 1974 B）：只有带宽是真的，
    实体遍历与序列化的 CPU 开销完全没有，测出来的 CPU 曲线是假的
  - **等游戏内容做完再测**：违反 D-013 的优先级，且游戏内容是唯一可砍项（风险顺序颠倒）
- **代价 / 风险**：
  - 占位实体**没有碰撞检测**，而 `01 §7.1` 那份基准（100 敌机 + 800 子弹 = 4.37 ms/tick、87.3% 单核）
    **包含「朴素 O(子弹×敌机) 碰撞检测」= 每 tick 8 万次判定**，那才是 CPU 大头。
    ⚠️ **其中「87.3% 单核」是量纲错误，正确值 8.74%**（见 **D-027**）；
    但结论不受影响：**碰撞仍是 CPU 大头**，E9 实测该规模碰撞占 tick 的 78 %。
    实测我们同规模只有 **1.396 ms / 1.7%** → **图 6-17 / 6-19 的拐点出不来**
  - ⚠️ **这是 8b 开工前必须拍板的事**（A 只测通信层 / B 补一段占位碰撞判定），
    详见 `PROGRESS.md §2.14` 末尾。**图 6-19 的「50% 舒适线」只有 B 碰得到**，
    而 D-011 的「敌机 ≤ 30、子弹 ≤ 300」正是基于 B 那份基准定的
  - ✅ **2026-10-25 已拍板：选 B**（补 O(子弹×敌机) 占位碰撞判定），
    并追加要求「**碰撞耗时与通信耗时必须分开测、分开画**」→ 见 **D-025**

### 决定二：数量必须**恒定**（出屏剔除后立即补足）

- 每 tick：**移动 → 出屏即剔除（D-012）→ 补足到目标数量**
- **理由**：E9 的自变量是「**同屏**实体数」。若实体只出不进，数量随时间衰减，自变量就不稳定，
  六档实验之间不可比。补足后实测 `e/b` 全程稳定
- **顺带收益**：剔除让**越界坐标永远进不了编码器**，直接杜绝 D-012 记录的那个
  `struct.error: 'H' format requires 0 <= number <= 65535`
- **代价**：实体是「凭空补」的，不是真的被打掉后刷新；占位阶段不需要真实刷怪逻辑

### 决定三：角度用 **8 方向整数表**，并补上协议缺失的**角度基准**

- `angle >> 5` 取 8 个方向（每档 32），整数查表，无三角函数
- **同时补进 `02 §4.3 / §4.5`：`0° = 正上方，顺时针`** ——
  **协议文档此前只写了「0~255 线性映射到 0~360°」，没定义 0° 指向哪里**，
  子弹必须有方向，这是文档漏洞，本次补上
- **理由**：
  1. 竖版飞机大战「向上」是主方向（玩家子弹向上、敌机向下），0 放在正上时
     最常见的两个方向恰好是 `0` 和 `128`，都在整数档上；若 0 放正右，玩家子弹得写 `192`，反直觉易错
  2. 无三角函数 → 满足 `02 §4.3` 禁用浮点，且**同样的输入必然得到同样的轨迹**（可复现）
  3. `& 0x07` 保证角度越界时不会数组越界
- **备选方案（否决）**：`math.cos/sin` 逐角度算 → 违反禁用浮点，且末位差异破坏可复现性
- **代价**：斜向位移是 1.41 倍（未归一化）。真实弹幕阶段要么把表细化到 256 档，要么用定点数归一化

### 决定四：`boss_present` **推导**而不传参

- `boss_present = 1 if any(e.type == ENEMY_BOSS) else 0`
- **理由**：它和「敌机里有 `type == 0xFF`」表达同一件事。两边各传各的必然出现
  「flag 说有 BOSS 但敌机列表里没有」的矛盾，而这种矛盾**不会崩溃**，
  只会让客户端显示一个不存在的血条，极难排查
- **代价**：无（推导成本是每 tick 一次 `any()`）

### 决定五：指标采集 —— 1 秒窗口、追加写、双时间戳

| 项 | 决定 | 理由 |
|---|---|---|
| 窗口 | **1 秒**（20 tick），不是 `03 §4.1` 写的 5 秒 | **原始数据细，聚合可以后做；反过来不行**。5 秒是展示粒度，不是采集粒度 |
| 写入 | 追加写 + **每行 flush** | §4.3 原则；Ctrl+C 也不丢已采数据 |
| 表头 | 文件为空时才写 | 分段跑多次实验不会写出两份表头 |
| 时间戳 | **`t_mono`（单调，分析用）+ `timestamp`（墙上时钟，人看）** | 只用墙上时钟不安全（NTP 调整会让时间倒流），只用单调时钟没法对「几点跑的」 |
| CPU | **自己算 ΔCPU秒 ÷ Δ墙钟秒 × 100**，不用 `psutil.Process.cpu_percent()` | 那个 API 把阻塞/非阻塞两种语义混在一起，非阻塞还要乘 `cpu_count()`，量纲易错；自己算则定义明确且可单测。**100% = 一个核跑满**，与 D-011 同量纲 |
| CPU 校验 | 忙等 0.5 s/秒 → **49.95%**；0.1 s/秒 → **9.37%**；空闲 → **0.0%** | 量纲正确，精度优于 0.1% |
| psutil 缺失 | 只留空两列并提示一次，不崩 | 少一个包不该让整个实验跑不起来 |

### 决定六：⭐ `tick_ms` 与 `CPU%` 是两个不同量纲，必须同时报

**实测发现**（4 人 + 100 敌机 + 800 子弹）：

| 指标 | 值 | 含义 |
|---|---|---|
| `tick_ms` | 1.396 ms | tick 主体的**墙钟**耗时（**含** `await drain()` 等待与事件循环调度） |
| `cpu_percent` | 1.7% | **真正的 CPU 时间** → 约 **0.87 ms/tick** |

差额（约 0.5 ms/tick）是 I/O 等待与调度。

- **意义**：`tick_ms` 回答「50 ms 帧预算还剩多少、会不会掉帧」；
  `CPU%` 回答「还剩多少算力、能再加多少负载」。只看一个会得出错误结论
- **对旧数据的补充说明**：D-011 的「0.45 ms/tick」同样包含等待，**不能直接当成 CPU 时间用**

### 决定七：其他

- **matplotlib 缓存目录**：在 `import matplotlib` **之前**设 `MPLCONFIGDIR` 指向项目内 `.cache/matplotlib`。
  默认位置（`%LOCALAPPDATA%\matplotlib`）不可写时，matplotlib 会**在当前工作目录建临时目录** ——
  等于往仓库根目录拉屎，且每次重建、导入慢几秒。`.cache/` 已进 `.gitignore`

- **`client/main.py` 的子弹不做插值**：协议里子弹条目**没有唯一 ID**（只有 `owner_id`），
  客户端无法把这一帧的子弹与上一帧对应起来。这是**协议设计的代价**
  （省 2 B/颗 × 200 颗 = 400 B/帧，约占快照 20%），不是实现遗漏

### 代价 / 风险

- 新增 3 个模块文件（`server/entities.py`、`server/metrics.py`、`tools/plot.py`）+ 4 个测试文件
- 测试从 88 → **153 个**

## D-025 tick 拆四段：碰撞与通信分开测、分开画，并补上占位碰撞判定

- **日期**：2026-10-25
- **背景**：D-024 留了一个开放项 —— E9 的 CPU 曲线要不要弯（A 只测通信层 / B 补占位碰撞）。
  **用户拍板选 B**，并追加一条要求：**碰撞耗时与通信耗时必须分开测、分开画**。
  这条要求把实验质量抬了一档：只报一个 `tick_ms` 回答不了
  「**瓶颈在游戏逻辑还是通信层**」，而这正是本课题的核心问题。

### 决定一：补上朴素 O(子弹×敌机) 的占位碰撞判定

- 双重循环遍历所有（子弹, 敌机）对，AABB 判定，半径 8 px
- **只判定不生效**：不改血量、不删实体、不掉道具，只累计 `hits`
- 实现上的两点讲究：先把 `bullet.x/.y` 取到局部变量；**先判 x 再判 y**（多数配对在 x 上就短路）
- **理由**：
  1. `01 §7.1` 那份基准（100 敌机 + 800 子弹 = 4.37 ms/tick、87.3% 单核）算的就是
     这个**算法复杂度**（每 tick 8 万次配对）。不补它，E9 的 CPU 曲线是平的，
     图 6-19 的「50% 舒适线」永远碰不到
     （⚠️ 其中 87.3% 系**量纲错误**，正确值 8.74%，见 **D-027**；
     但「那份基准包含碰撞检测」这一事实不变）
  2. **只判定不生效**保证 E9 的自变量**由构造恒定** —— 不必依赖「删了再补足」来维持数量，
     自变量最干净；伤害结算是第 11 步的游戏内容
  3. 还要返回 `hits`：它是「这个循环真的在算」的证据。
     没有它，一个写错方向、实际空转的循环同样会报出很漂亮的耗时曲线
- **备选方案（否决）**：
  - 保持 A（不补碰撞）→ 图 6-18 好看但结论空：只能说"通信不贵"，说不出"贵在哪"
  - 命中真删实体并补足 → 更像真实游戏，但每 tick 实体都在换，
    且"补足"会把命中效果立刻抹平，收益为零、复杂度更高
  - 用空间划分（网格）加速 → 那是第 11 步之后的**优化对比实验**素材，现在做就没有朴素基线可比了
- **代价**：多一段第 11 步会被替换掉的临时逻辑；常数因子与当年那个一次性原型不同
  （代码没留下来），所以**绝对值不能和 §7.1 逐位对齐**，只对齐**复杂度与趋势**

### 决定二：tick 内部拆成四个可测阶段

```
tick 开始
├─ ① sim_ms        玩家按输入移动 + 实体移动 + 出屏剔除 + 补足数量
├─ ② collision_ms  朴素 O(子弹×敌机) 碰撞判定
├─ ③ ser_ms        pack_snapshot：逐实体 struct.pack
└─ ④ net_ms        逐客户端 write + await drain
tick 结束
```

- 约定：**逻辑 = sim + collision**，**通信 = ser + net**
- 四段各取**平均值**（不是 p95）：**四段严格相加等于 `tick_ms_avg`**
  （五处计时点首尾相接，从 `started` 到 `net_done` 一次不多一次不少），
  所以堆叠图能画成 100%，**不存在"其它"那一类**；p95 之间不可相加，画不了堆叠
- 为此把 `broadcast_snapshot()` 拆成 `build_snapshot()` + `broadcast(payload)` ——
  合成一个方法就没法把"序列化"和"发送"分开量
- 每 tick 多 4 次 `perf_counter()`，约 100 ns，可忽略
- **CSV 新增 5 列**：`sim_ms` / `collision_ms` / `ser_ms` / `net_ms` / `hits`

### 决定三：图 6-17 改多线，新增图 6-20

- **图 6-17**：总耗时 + 四段各一条线 + 50 ms 预算线。关键不是谁高，而是**斜率不同**
- **图 6-20（新增）**：100% 堆叠柱状图，一眼看出**构成占比随实体数怎么变**
- **图表总数 19 → 20**，已同步更新 `03-实验清单.md`（§3 指标定义 / §5 E9 / §6 汇总）

### 决定四：给 tick_loop 加崩溃上报（本次踩坑的直接产物）

- **踩到的坑**：改代码时漏了一行 import，`tick_loop` 在第一个 tick 就抛 `NameError`，
  **整个协程静静死掉**。症状极具迷惑性：

  ```
  机器人：clients_connected: 4、snapshots: 0、errors: 0
  服务端：照常监听、照常打印 "player 1 joined"
  ```

  连接是好的，只是**再也没人广播**。asyncio 只在**任务对象被回收**时打印未取回的异常，
  而 `main()` 一直持有 `tick_task` 引用 —— 所以进程活着时**什么都不显示**。
- **决定**：
  1. `tick_task.add_done_callback(report_tick_crash)` —— 崩了立刻大声报（含 traceback）
  2. 新增 `tests/test_tick_guard.py`：真跑一遍 `tick_loop`，
     名字缺一个就在第一个 tick 失败，不用等"连得上但零快照"才发现
- **代价 / 风险**：无。这条防线对**长时间无人值守的实验**尤其重要 ——
  否则一次 3 分钟的场景会跑完并留下一整份空数据

### 实测（本机 loopback 冒烟，4 个机器人，**非 E9 正式数据**）

| 场景 | 实体 | 总 ms | 逻辑 ms | 碰撞 ms | 通信 ms | 快照 | 下行/客户端 | 单核 | hits/s |
|---|---|---|---|---|---|---|---|---|---|
| 30 敌机 + 200 子弹 | 234 | 1.071 | 0.587 | **0.462** | **0.484** | 1927 B | 38.8 KB/s | 1.4 % | 39 |
| 100 敌机 + 800 子弹 | 904 | 6.105 | 5.148 | **4.775** | **0.957** | 7357 B | 147.4 KB/s | 13.2 % | 514 |

**构成占比（图 6-20 的数据）**：

| 场景 | 碰撞 | 模拟 | 序列化 | 广播 | **通信合计** |
|---|---|---|---|---|---|
| 30/200 | 43.1 % | 11.7 % | 26.9 % | 18.3 % | **45.2 %** |
| 100/800 | 78.2 % | 6.1 % | 12.4 % | 3.3 % | **15.7 %** |

**三条可以直接写进论文的结论**：

1. **通信占比随实体数下降**（45.2 % → 15.7 %）——
   通信层是可扩展的，**瓶颈在游戏逻辑侧**，这正是本课题要证明的事
2. **碰撞耗时随实体数超线性增长**：实体 3.86 倍 → 碰撞 10.3 倍
   （配对数 6,000 → 80,000，13.3 倍），符合 O(子弹×敌机) 的预期
3. ⭐ **广播发送耗时与包大小几乎无关**：`net_ms` 0.196 → 0.200 ms（**基本持平**），
   而同期快照从 1927 B 涨到 7357 B（3.8 倍）。
   原因是内核发送缓冲区没饱和时 `drain()` 立即返回，
   所以**广播成本 ≈ O(客户端数)，与快照大小无关** ——
   这是个反直觉但有数据支撑的结论，答辩时是个亮点

### 答辩可能被问

- **为什么碰撞只判定不生效？** → 答：E9 的自变量是「同屏实体数」。
  只算不改，实体数量就**由构造保证**恒定，不需要靠"删掉再补足"来维持，
  自变量最干净；伤害结算属于第 11 步的游戏内容。
  同时仍然统计命中数，用来证明这个循环真的在计算而不是空转。
- **为什么要把 tick 拆成四段？** → 答：一个总耗时回答不了"瓶颈在哪"。
  拆开后可以直接看出：实体数增长 3.86 倍时，碰撞耗时涨 10.3 倍、
  通信耗时只涨 2 倍，且**通信占比从 45% 降到 16%**。
  这组数据同时支撑"通信协议设计是高效的"和"设计上限由游戏逻辑的算法复杂度决定"。
- **为什么四段相加正好等于总耗时？** → 答：五个计时点首尾相接、一次不多一次不少，
  所以这是构造上的恒等式，堆叠图不需要"其它"项；
  每个阶段取均值而非 p95 也是为此（p95 之间不可相加）。

## D-026 E9 档位定为 9 档；实验结果支持 D-011 的实体上限约束

- **日期**：2026-10-25
- **前置**：D-024（占位实体）、D-025（补碰撞 + 四段拆解）

### 决定一：E9 从 6 档扩到 **9 档**

- 原计划（`03 §8`）：敌机 10/20/30/50/80/100，子弹 50/100/200/400/600/800
- **追加 3 档**：150/1200、200/1600、250/2000
- **理由**：预实验实测 100/800 时单核只占约 11 %，
  **碰不到 D-011 的 50 % 舒适线** —— 曲线不弯，图 6-19 就证明不了「上限从哪来」，
  而 `D-011` 的「敌机 ≤ 30、子弹 ≤ 300」正是基于那条线定的
- **代价**：总时长从约 40 分钟增到 55.8 分钟；无其他代价
- **可逆性**：档位表固化在 `tools/run_e9.py` 的 `DEFAULT_LEVELS`，改一行即可

### 决定二：用运行器固化实验条件

- 新增 `tools/run_e9.py`：9 档 × 2 轮，每轮**重启服务端**，自动校验与落盘
- **理由**：手敲 18 遍命令，第 7 遍和第 13 遍的参数可能悄悄不一致
  （漏一个 `--seed`、忘了 `--ramp`），而这种不一致**不会报错**，只会让数据不可比。
  把参数固化成代码，实验条件就成了可审查、可回归测试的一部分
- **每轮重启服务端**还带来一个好处：`t_mono` 从 0 重新计时，
  `tools/plot.py` 靠这一点给每轮单独丢热身（见 D-025）

### 实测结果（18/18 轮达标，55.8 分钟）

| 档位 | 实体 | tick ms | 碰撞 ms | 通信 ms | **通信占比** | 快照 B | 下行 KB/s | 单核 % |
|---|---|---|---|---|---|---|---|---|
| 10/50 | 64 | 0.366 | 0.047 | 0.267 | **73.0 %** | 547 | 10.9 | 0.0 |
| **30/200** | **234** | **1.016** | 0.446 | 0.433 | 42.7 % | 1 927 | 37.9 | **2.0** |
| 100/800 | 904 | 5.738 | 4.493 | 0.842 | 14.7 % | 7 357 | 143.9 | 10.5 |
| 150/1200 | 1354 | 11.658 | 9.879 | 1.209 | 10.4 % | 11 007 | 215.2 | 23.2 |
| 200/1600 | 1804 | 19.934 | 17.602 | 1.588 | 8.0 % | 14 657 | 286.5 | 39.2 |
| 250/2000 | 2254 | 30.797 | 27.825 | 2.057 | **6.7 %** | 18 307 | 357.8 | **61.0** |

**三条核心结论**：

1. **通信占比随实体数单调下降：73.0 % → 6.7 %** ——
   通信层可扩展，**瓶颈在游戏逻辑侧的算法复杂度**（本项目要证明的核心论点）
2. ⭐ **广播耗时与报文大小几乎无关**：快照涨 **33.5 倍**（547 → 18 307 B），
   广播耗时只从 0.150 → 0.182 ms。内核发送缓冲区未饱和时 `await drain()` 立即返回，
   广播成本主要是「每客户端一次 write 调用」的固定开销，**≈ O(客户端数)**
3. **单核占用跨过 50 % 舒适线**：200/1600 = 39.2 %、250/2000 = **61.0 %**，
   插值拐点约 **215/1720**

**对 D-011 的支持**：设计目标规模 30/200 实测 **tick 1.016 ms、单核 2.0 %**，
距 50 ms 预算有 **49 倍余量**。D-011 的「敌机 ≤ 30、子弹 ≤ 300」**得到实测支持**。

**数据质量**：

- **多轮一致性**：tick 两轮偏差全部 ≤ **1.8 %**（两档为 0.0 %）→ 可作正式数据
- **交叉验证**：`tick_ms × 20 Hz` 与实测单核占用在高负载下吻合 98~99 %——
  两套**完全独立**的机制（进程内 `perf_counter` vs psutil 读进程累计 CPU 时间）互证
- **逐字节核对**：9 档快照大小全部吻合 `57 + 9E + 8B`，偏差 0 B
- **环境**：实验期间整机 CPU 1.4~16.1 %，机器基本空闲
- ⚠️ **如实记录的一处干扰**：第 1 轮最后约 20 秒在同机跑了单元测试（3.5 s 满载一核），
  该轮 tick 偏差仅 0.9 %，未造成可观测影响 —— 但**跑批期间不应在同机执行重负载任务**，
  运行器已记录每轮前后整机 CPU 供事后审查

### 代价 / 风险

- 18 轮 × 3 分钟需**无人值守约 1 小时**，期间机器不宜做其他重活
- 仍是本机 loopback（D-016）；但本实验的因变量是**服务端处理开销**，不受 RTT 影响
- 与 `01 §7.1` 旧基准（一次性原型）**只对齐复杂度与趋势，不可逐位对比**：
  同规模 100/800 本次 5.738 ms vs 旧基准 4.37 ms，同一量级
- 碰撞仍是占位实现（只判定不生效），第 11 步替换后绝对耗时会变，**但通信部分不受影响**

### 答辩可能被问

- **为什么 E9 要跑到 250 敌机 + 2000 子弹，不是只要 30/300 吗？** →
  答：设计约束本身需要实测依据。原计划 6 档最高只到 100/800，单核仅占 11 %，
  曲线不弯就证明不了"上限从哪来"。追加档位后单核占用跨过 50 % 舒适线，
  才能回答"为什么同屏敌机只能 30 个"。D-011 也明确说过实验**有意突破**设计上限。
- **你的 CPU 数据和 tick 耗时对得上吗？** → 答：高负载下二者吻合 98~99 %。
  它们由完全独立的机制测得（进程内高精度计时 vs 操作系统进程 CPU 时间），
  互相印证 —— 这也是数据可信度的证据。
- **为什么通信占比会随实体数下降？** → 答：游戏逻辑是 O(子弹×敌机) 的超线性增长，
  通信是近似线性的，占比被逻辑侧稀释。这说明**通信层可扩展，瓶颈在算法复杂度**。

## D-027 ⚠️ 更正：早期基准表的 CPU 量纲错误（10 倍），E9 正式数据取代该基准

- **日期**：2026-10-26
- **性质**：**数据更正**，不是决策推翻。D-011 的约束值（敌机 ≤ 30、子弹 ≤ 300）**保留**，
  但它引用的量化依据作废。

### 发现过程

E9 正式实验跑完后对照旧基准，发现同一规模下差了一个数量级：

| 规模 | `01 §7.1` 旧表 CPU | E9 实测（100/800） |
|---|---|---|
| 100/800 | 87.3 % | **10.5 %** |

### 验算结论：CPU 列是按 **200 Hz** 算的

旧表 CPU 列精确等于 `ms/tick × 200 Hz`，而本协议 tick 率是 **20 Hz**：

| 敌/弹 | ms/tick | 旧表 CPU | `ms×20`（20 Hz 正确值） | `ms×200` | 比值 |
|---|---|---|---|---|---|
| 30/100 | 0.22 | 4.4 % | 0.44 % | 4.4 % | 10.0× |
| 30/200 | 0.45 | 8.9 % | **0.90 %** | 9.0 % | 9.9× |
| 50/400 | 1.21 | 24.1 % | 2.42 % | 24.2 % | 10.0× |
| 80/600 | 2.72 | 54.4 % | 5.44 % | 54.4 % | 10.0× |
| 100/800 | 4.37 | 87.3 % | **8.74 %** | 87.4 % | 10.0× |

五档全部吻合 `ms×200`，比值恒为 10.0 —— **不是测量噪声，是系统性的量纲错误**。

### 三条被推翻的说法

1. ❌ **「16 人 + 100 敌机 + 800 子弹 = 87.3 % ← 单核极限」**
   → 更正为 **8.74 %**。**它从来就不是单核极限**，20 Hz 下连 10 % 都没到。
2. ❌ **「同屏敌机上限 30，原因：超过则 tick 耗时逼近 50 ms 预算」**
   → 原型最大规模的 4.37 ms 只占 50 ms 预算的 **8.7 %**，谈不上"逼近"。
3. ❌ **D-004「实测证明硬件撑得住（8.9 % 单核）」**
   → 更正为 **0.90 %**。结论（做得动）不变，但数字要改。

### 更正后的权威数据：**E9 正式实验**（2026-10-25，9 档 × 2 轮）

| 规模 | tick ms | 单核 % | 占 50 ms 预算 |
|---|---|---|---|
| **30/200**（设计目标） | **1.016** | **2.0 %** | 2.0 % |
| 100/800 | 5.738 | 10.5 % | 11.5 % |
| 250/2000 | 30.797 | **61.0 %**（跨过 50 % 舒适线） | 61.6 % |

拐点约在 **215 敌机 / 1720 子弹**。详见 `docs/experiments/E9-实体数影响.md`。

### 为什么之前没发现

- 旧表来自**项目初期的一次性原型**（代码未保留），只留了一张结果表，没有原始数据可复核
- 表里的 `ms/tick` 列是**对的**（与 E9 同量级：4.37 vs 5.738 ms），
  所以只扫一眼"耗时"不会觉得有问题 —— **错的是由它换算出来的 CPU 列**
- 真正暴露它的是 E9：**同一规模下差 10 倍**，而 E9 的 CPU 列
  是用累计 CPU 时间增量算的，且经过"人为 50 % 负载 → 读出 49.95 %"的独立校验

### 处理方式

1. 旧表**保留**（历史记录不删），但加醒目的更正块，**双列对照**（原值 / 更正值）
2. `01 §7.1`、`03 §5`、`05-论文素材`、`server/metrics.py`、`notes/07`、`notes/08`、
   `PROGRESS`、`CAREER` 中所有引用该列的地方同步更正
3. **D-011 的约束值不变**，但理由 1 标注作废，答辩话术明确"不要引用旧数字"
4. 在 `05-论文素材` 的"可信度图例"里把这张表钉死为 ⬜（推算/不可用）

### 教训（**这一条本身可以写进论文**）

> **任何跨来源对比数据前，先验算量纲自洽性。**
> 本例中 `ms/tick × tick率` 必须与 CPU 占用在同一量级 ——
> 只要做一次这样的量纲检查，10 倍错误当场就会暴露。
> 而这个错误之所以能存活两周，是因为它写在"已实测"的标题下，
> 且唯一的自洽性检查（与 tick 耗时对不上）没有被执行。
>
> 更正后的做法：**每个 CPU 数字都能由 `ms/tick × 20` 反推校验**，
> E9 数据正是这样交叉验证的（高负载下 `tick_ms × 20 Hz` 与实测单核占用吻合 98~99 %）。

## D-028 E1 用三变体可比设计；编码计时用嵌套 `encode_ms`；JSON 在最大规模下不可用

- **日期**：2026-10-26
- **前置**：D-019（二进制 vs JSON 的取舍）、D-025（四段计时）、D-027（旧基准量纲更正）

### 决定一：`encoder` 从两变体扩到**三变体**

| 变体 | 是什么 | 回答什么 |
|---|---|---|
| `binary` | 协议标准编码，逐条目 `struct.pack` | 基线 |
| `binary_fast` | **同一个协议、产物逐字节相同**，整帧只调一次 `struct.pack` | **实现方式**的差异 |
| `json` | 短键名 JSON，编解码双向实现 | **编码形式**的差异 |

- **理由**：只比两变体，JSON 慢多少都能被质疑成"你的二进制写得快"或"你的 JSON 写得烂"。
  加第三个变体后，「协议形式」与「实现方式」成了两个**可分别测量**的量
- **约束**：`binary` 与 `binary_fast` 的产物必须**逐字节相同**（有测试断言），
  否则跑得快可能只是因为**少编码了东西**
- **代价**：多约 30 行实现 + 1/3 实验时间

### 决定二：编码耗时用**嵌套计时 `encode_ms`**，不用 `ser_ms`

- **背景**：`ser_ms` 圈的是整个 `build_snapshot()`，其中包含
  **实体对象的构造**（100 敌机 + 800 子弹 = 900 个 dataclass 实例）。
  实测该共享开销在 100/800 时约 0.55 ms，而真正的编码只有 0.14~0.64 ms。
  **用 `ser_ms` 画图 6-2 会得到三根一样高的柱子**
- **决定**：拆出 `build_entities()`，只把 `encoder.encode()` 包进独立计时器
- **约束**：`encode_ms` **嵌在 `ser` 内、不参与四段相加**（`NESTED_TIMERS`），
  且 `encode_ms ≤ ser_ms` 恒成立 —— 四段相加等于 `tick_ms` 的不变量不受影响

### 决定三：JSON 是一条**完整可用**的协议路径，不只是对照组

- 编解码双向都实现（`pack` 侧 + `unpack_snapshot_json`）
- **公平性写成 6 条可检查约定**（详见 `protocol/encoders.py` 模块注释与 E1 实验记录 §4）：
  字段与实体集合完全一致（**往返测试锁住**）、标准库 `separators`/`ensure_ascii`、
  短键名、不做协议值域校验、计时窗口起止点相同、实现解码
- **理由**：对照组的实现方式直接决定结论可信度

### 实测结果（4 档 × 3 编码 × 2 轮，74.4 分钟，22/24 达标）

| 档位 | binary 快照/编码 | binary_fast | json | json/binary |
|---|---|---|---|---|
| 30/200 | 1927 B / 0.064 ms | 1927 B / 0.069 | **9076 B / 0.249** | 4.71× / 3.90× |
| 100/800 | 7357 B / 0.161 | 7357 B / 0.145 | **34788 B / 0.640** | 4.73× / 3.98× |
| 150/1200 | 11007 B / 0.216 | 11007 B / 0.206 | **52097 B / 1.057** | 4.73× / 4.89× |
| 250/2000 | 18307 B / 0.360 | 18307 B / 0.323 | ❌ **无法发送** | — |

**三条结论**：

1. **二进制体积优势是结构性的：4.7 倍**（三档稳定复现）
2. ⭐ **JSON 在 250/2000 规模下根本发不出去**：载荷 **79 538 / 89 538 B**
   > 协议 64 KiB 帧上限 → 帧层拒绝 → tick 循环崩溃（**两轮可复现**）。
   同规模二进制 18 307 B（上限 28 %）。**这从"性能差异"升级成"可用性差异"**
3. **打包方式不是瓶颈**：`binary_fast` 小规模慢 8 %、大规模快 5~10 %
   （`encode_ms` 轮间偏差仅 0.4~3.4 %，故为信号），
   但编码只占 tick 的 **1.2~6.8 %** → 换打包方式对总耗时影响 **< 0.1 %**。
   **所以第 1 条来自协议形式，不是实现差异**

### 代价 / 风险

- JSON 的**可读性优势**没有量化（本实验只量体积与耗时）；这在论文里作为"取舍"讨论
- 已如实说明"条目改数组形式还能再压约一半"，避免被指稻草人
- 带宽是**应用层字节数**（服务端自计），不含 TCP/IP 头开销 —— 抓包验证是 E7 的任务

### 答辩可能被问

- **你的 JSON 是不是故意写慢了？** → 答：三条证据。① 用标准库 + 短键名 +
  去空格，是"认真写 JSON"的写法；② 加了 `binary_fast` 变体做对照，
  **换打包方式对总耗时影响 < 0.1 %**，说明快慢不是实现问题；
  ③ 公平性有 6 条可检查约定，其中"字段与实体集合完全一致"由**往返测试**锁住。
- **二进制协议的优势到底有多大？** → 答：**体积 4.7 倍、编码耗时 4~5 倍**；
  但**更关键的是可用性** —— JSON 在 250/2000（我们的实验上限规模）下
  载荷 79.5 KB 超出协议 64 KiB 帧上限，**根本发不出去**。
- **那编码是不是性能瓶颈？** → 答：不是。编码只占 tick 的 1.2~6.8 %，
  E9 已证明碰撞判定才是大头（占 60~90 %）。**瓶颈在游戏逻辑侧。**

## D-029 实验期间实体数恒定（`--fixed-entities`）；击杀只计分或补生

- **日期**：2026-10-28
- **前置**：D-025（碰撞只判定不生效，作为测量夹具）、D-008（缩圈关卡为排行榜提供分数来源）、
  D-005（登录 / 排行榜属主线，不砍）

### 背景：一旦「击杀生效」，已跑完的基线就不可比了

E9（9 档 × 2 轮，55.8 分钟）与 E1（4 档 × 3 编码 × 2 轮，74.4 分钟）的全部数据，
都是在**实体数恒定**的条件下测的：4 玩家 + 30 敌机 + 200 子弹，跑完一局数量不变。

而排行榜需要一个真实的分数来源（`best_score` = 击杀敌机换算的分数，见 `04 §4.4`），
这就必须让**击杀真的生效**。矛盾在于：

```
击杀生效 → 敌机数量下降 → 快照变小 → tick 耗时 / 带宽下降
         → 与 E9 / E1 的静态基线不可比 → 要么重跑 130 分钟，要么数据说不清
```

### 决定

**实验期间实体数恒定**，用 `--fixed-entities` 开关控制：

| 项 | 内容 |
|---|---|
| **固定规模** | **4 玩家 + 30 敌机 + 200 子弹**（与 E9 目标档、E2/E8 完全一致） |
| **击杀处理** | 二选一：① **只计分不移除**；② **击杀后在屏幕外立即补生**，保证同屏数量不变 |
| **正式游戏**（步骤 11） | 恢复正常击杀 / 移除语义 |
| **开关** | `--fixed-entities`：**实验开、演示关** |
| **默认值** | **关**（保持「正式游戏」语义）；**但所有实验脚本必须显式传参** |

### 约束

1. **补生必须在屏幕外**（坐标落在可视区域之外再入场），不能凭空出现在玩家眼前
2. **补生不得与现有实体重叠**，否则碰撞判定的分支覆盖会变，测量条件又被改掉
3. **实验脚本里写死这个开关**，不依赖人工记忆 —— `tools/run_e9.py`、E2/E8 的运行脚本
   都要显式传 `--fixed-entities`。**漏传就会悄悄污染基线，这种错误最难查**
4. 开关打开时，`snapshot_bytes` 必须**逐字节可预测**（E9 已建立这个校验：
   与公式零偏差），可用来反向确认开关确实生效

### 备选方案

| 方案 | 为什么不选 |
|---|---|
| A. 击杀直接移除，**重跑 E9/E1 基线** | 130+ 分钟纯重跑，且已写进论文的 10-27 数据要全部作废 |
| B. 允许数量波动，分析时按「当时实体数」归一化 | 破坏「同规模对比」的前提，图 6-17~6-20 的横轴（实体数）会失去意义 |
| C. 敌机打不死（只判定不生效） | 就是现状，会导致**排行榜全是 0**，演示时是个空表 |
| **D. 击杀即补生（选定）** | 分数正常增长 + 实体数恒定 + 这也是真实游戏的做法 |

### 代价 / 风险

- 补生逻辑本身有一点点 tick 开销（与「移除 + 新增」同量级），**已在实验记录里注明**
- 演示时必须记得**关掉** `--fixed-entities`，否则敌机打不完，观感奇怪
- 关闭开关后的行为（正常击杀）**没有专门的性能数据** —— 它不在实验范围内，属于游戏功能

### 答辩可能被问

- **为什么你演示时敌机打不完？** → 答：实验期固定实体数是为了保证测量可比；
  正式演示会关掉 `--fixed-entities`，恢复正常击杀。
  **这是测量严谨性的要求，不是游戏缺陷。**
- **补生不会影响你的性能数据吗？** → 答：补生与「移除 + 新增」是同一量级的操作，
  且 E2/E8 **全部在固定实体数下测**，条件一致；E9/E1 的基线本来就是静态的，两者不混用。
- **那你的排行榜分数是怎么来的？** → 答：分数由**服务端**在击杀时累加（客户端无上报接口），
  实验模式下「只计分不移除」或「击杀即补生」，两种都能产生真实分数。

## D-030 击杀走**独立代码路径**（`--enable-kills` 默认关）；补生分两种模式

- **日期**：2026-10-31
- **前置**：D-025（碰撞只判定不生效，作为测量夹具）、D-029（实验期实体数恒定）、
  D-005（登录 / 排行榜属主线，需要真实分数来源）

### 背景：让击杀生效，但**不能动基线**

排行榜需要真实分数（`04 §4.4` 的 `best_score`），所以击杀必须真的生效。
但 E9 / E1 / E2 的全部数据都是在「碰撞只判定不生效」下测的，
`collision_ms` 是图 6-17、图 6-20 的数据来源 —— **往那条循环里加伤害结算，
等于偷偷改了历史数据的实验条件**。

### 决定一：两条循环分开，基线那条**一字不改**

| 路径 | 函数 | 何时走 | 行为 |
|---|---|---|---|
| **计数**（基线） | `detect_collisions()` | `--enable-kills` **关**（默认） | 只数命中对数，不动任何实体 |
| **结算** | `World.resolve_kills()` | `--enable-kills` 开 | 扣血 → 死亡 → 计分 → 消耗子弹 |

- **理由**：E9 的 `collision_ms` 靠"同一条代码路径"才有可比性。共用一条循环再按开关分支，
  仍会让循环体变大（多出分支与写操作），常数因子会变
- **代价**：约 25 行相似的循环重复。**用重复换可复现性，值得**
- **可接受的风险**：两条循环的判定条件理论上可能写岔，用测试锁住

### 决定二：`--enable-kills` 默认关

- **默认关的理由**：任何人在跑 E9/E1/E2 时都不会因为"忘了关"而污染基线
- **打开的场景**：游戏演示、产生排行榜分数
- 与 `--fixed-entities` 正交，组合如下：

| `--enable-kills` | `--fixed-entities` | 效果 |
|---|---|---|
| 关（默认） | 关（默认） | 当前基线行为 |
| 关 | 开 | 基线 + 数量守卫（E2/E8 用） |
| 开 | 开 | 击杀计分 + **当场补满**，数量恒定 |
| 开 | 关 | 击杀计分 + 按速率补生 → **正式游戏手感** |

### 决定三：补生的两种模式

- **`fixed_entities` 开**：击杀后**当场**补回目标数（不等下一个 tick）
- **`fixed_entities` 关**：每 tick 最多补 `respawn_per_tick = 2` 个敌机 ——
  否则刚打掉的敌机下一 tick 就满血复活，玩家看不到"打掉了"的反馈
- **子弹不设速率上限**：它是发射物，补慢了弹幕会变稀，属于观感退化而不是难度

### 决定四：分数计到子弹主人，且**必须夹到 uint16**

- 一次击杀 `score_per_kill = 10` 分，归 `bullet.owner_id`
- **`score` 是协议里的 uint16 字段**，越界会让 `struct.pack` 抛错
  → 和 E2 的「257 个玩家」一样**直接搞死 tick 循环**，所以 `_award()` 里 `min(0xFFFF, ...)`
- 敌方子弹 `owner_id == 0`，`resolve_kills()` 直接跳过 —— 否则将来加 AI 后
  会出现"敌人给自己加分"

### ⚠️ 实现时踩到的坑：守卫查错了位置

第一版把 `_verify_entity_counts()` 只放在 `world.step()` 之后。而**击杀发生在它之后**：

```
step() → _respawn() 补满 → 守卫检查（通过 ✓） → resolve_kills() 杀掉几个 → 建快照
                                                                    ↑ 这时少了 3 个敌机
```

实测快照里的敌机数在 **27~30 之间跳** —— 守卫**通过了**，数据却已经不符契约。
而快照字节数是 E9 那套「逐字节等于公式」校验的基础，一浮动全废。

**修法**：① `resolve_kills()` 内部在 `fixed_entities` 时当场补满；
② tick 里在击杀**之后再查一次**守卫。两处都加，并补了回归测试。

> **教训**：不变量检查必须放在**所有可能破坏它的操作之后**。
> 放在操作之前，检查通过只能说明"操作前是好的"。

### 顺带发现：E9 的 `hits` 里混着**没有物理意义的命中**

`detect_collisions()` 把**敌方子弹 × 敌机**也算作命中（约 922 次 / 20 秒），
但敌方子弹朝下飞、敌机也朝下飞，两者在 y=0 出生点重叠才是主因 ——
真实的玩家子弹命中只有个位数。

- **对 E9 的影响**：无。`hits` 在 E9 里的作用只是「证明这个循环真的在算」，
  不是物理命中率（`entities.py` 的 docstring 已这么写）
- **对论文的影响**：**不能把 E9 的 `hits/s` 说成"命中率"**，只能说"判定对数"
- **要不要修**：不修。改了会让 E9 的 `collision_ms` 与 `hits` 全部作废

### 代价 / 风险

- 两条循环重复约 25 行，靠测试锁一致性
- 击杀模式的 `collision_ms` **不能**与基线的比（多了写操作），实验记录里要注明
- 玩家子弹目前只沿一条竖线飞（`BULLET_PLAYER_L1` 没有扩散），
  所以**命中率取决于玩家是否横移** —— 实测 20 秒：玩家不动 1 杀、横移 33 杀。
  扩散弹 / 多级火力属于步骤 11 的游戏内容

### 答辩可能被问

- **为什么击杀要单独写一份循环？** → 答：E9/E1/E2 的 `collision_ms` 全部来自那条只计数的循环，
  往里加写操作会改变常数因子，历史数据就不可复现了。**用 25 行重复换基线可比。**
- **分数会不会溢出？** → 答：`score` 是 uint16，`_award()` 夹到 65535。
  越界会让 `struct.pack` 抛错并搞死 tick 循环，和 E2 的 257 玩家是同一类风险。
- **为什么打不着敌机？** → 答：占位阶段玩家子弹只沿一条竖线（没有扩散），
  **横移时命中率明显更高**（实测 20 秒：不动 1 杀 vs 横移 33 杀）；扩散弹属步骤 11。
- **E9 的 hits 是命中率吗？** → 答：**不是**，是"判定对数"，含敌方子弹与敌机的出生点巧合。
  它的作用只是证明循环真的在算。

## D-031 步骤 10 用**纯 Django**（不上 DRF）；Redis 走 RESP2 + 熔断 + 写透缓存

- **日期**：2026-11-01
- **前置**：D-005（长短连接分层，登录/排行榜属主线）、D-001（PyMySQL）、D-002（Django 5.2 LTS）

### 决定一：不打 Django REST Framework，手写 3 个视图

`04-API接口设计.md` 原定用 DRF（"省代码"）。实际改成纯 Django：

| 理由 | 说明 |
|---|---|
| **只有 3 个接口** | 注册 / 登录 / 排行榜，没有一个需要序列化器的嵌套、视图集、自动路由 |
| **零新依赖** | `JsonResponse` 是 Django 自带；DRF 装不上时整层直接卡死（本项目环境多次遇到依赖下载失败） |
| **更透明** | 每个接口做了什么一眼看完，答辩时不用解释框架 |

**代价**：参数校验手写（DRF 的 serializer 能省掉这部分），已用测试覆盖边界。

### 决定二：`INSTALLED_APPS` / `MIDDLEWARE` 砍到最小

这是**纯 JSON API，不出网页**，所以：

- 不要 `admin`（要模板 / 静态文件 / messages 一整串）
- 不要 `sessions` / `messages`（用自建 `auth_token` 表认证，与"非浏览器客户端"匹配）
- **必须去掉 `CsrfViewMiddleware`** —— 客户端不是浏览器、拿不到 CSRF token，
  留着会把所有 POST 变成 403（最容易踩的一脚）

用户表用 Django 内置 `auth_user`（PBKDF2 + salt 由框架保证，不存明文）。

### ⚠️ 决定三：Redis 三个坑（全部实测踩到，逐个修）

本机 Redis 是 **5.0.14.1**（Windows 版），而 `redis-py` 是 **8.1.0**，版本差造成三个不兼容：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `unknown command 'HELLO'` | redis-py 8.x 默认 **RESP3**，握手发 `HELLO 3`；Redis 5.0 不支持 | 显式 `protocol=2` |
| 2 | 排行榜接口**卡 8.5 秒** | redis-py 8.x 对连接错误**默认指数退避重试**，把 `socket_connect_timeout=0.3` 掩盖了 | `Retry(NoBackoff(), 0)` + 0.25 s 超时 + **5 秒熔断** |
| 3 | 写缓存**全部静默失败** | `ZADD ... GT` 的 `GT` 是 **Redis 6.2** 才加的，5.0 上直接 `syntax error` | 用 **Lua 脚本**做原子的"只在更高分时更新" |

> 第 3 条特别值得记：`04 §4.4` 的设计原文就按 `ZADD GT` 写，
> **文档没错，是环境版本不满足**。Lua 版语义相同（原子比较后写入），
> 且比"先 `ZSCORE` 再 `ZADD`"更安全（没有读改写竞态）。

**熔断效果实测**（Redis 停掉时查榜）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 第 1 次请求 | **8.5 s 超时** | 306 ms（一次连接尝试 + MySQL 兜底） |
| 后续请求 | 每次都超时 | **44 ms**（熔断期直接跳过 Redis） |
| Redis 恢复后 | — | 熔断 5 秒后自动回到 `source=redis` |

### 决定四：写透缓存（先 MySQL，再 Redis）

排行榜**读**走 Redis ZSET、**写**若只落 MySQL，就会出现"榜永远不动但不报错"的
静默错误（实测：新用户打完分查不到）。

所以 `accounts/scoring.py::record_result()` **两边都写**，顺序固定：

```
先写 MySQL（真相来源）→ 成功 → 再更新 Redis（读路径）
```

Redis 写失败**只记日志，不影响入库** —— 后果只是"下一次读变慢"，不是丢分。

### 决定五：Redis 返回的成员要**验存在性**

**实测踩到**：Redis 是进程外状态，不随 Django 测试库回滚。
开发库灌过的 ZSET 与测试库 user_id 对不上，排行榜直接返回
`{"username": "?", "games": 0}` 的**幽灵条目**。

修法：`_leaderboard_from_redis()` 过滤掉在 `auth_user` 里查不到的 `user_id`；
若整页都是陈旧成员，返回 `None` 退回 MySQL 重建。

### 决定六：Django 测试必须**隔离真实 Redis**

用 `override_settings` 把 `REDIS` 指向必然连不上的端口（`127.0.0.1:1`），
让测试只走 MySQL 路径、结果确定。

**Redis 读路径由 `tools/check_api.py` 单独验证**（打真实 HTTP，24 条断言，
含"写进去之后能从 Redis 读到"的闭环）。

### 代价 / 风险

- 参数校验手写，比 DRF 多一些样板
- **Redis 5.0 是旧版**（Windows 移植版），将来要用 `ZADD GT` / 事务 / Stream 得升级
- 排行榜的"总数"用 `ZCARD`，含陈旧成员时可能略微偏大（条目已过滤、总数没过滤），
  下一次 MySQL 重建后自愈
- `django_user` 需要 `test_myproject` 的权限才能跑 `manage.py test`（已授权）

### 答辩可能被问

- **为什么不用 DRF？** → 答：只有 3 个接口，没有一个用得上序列化器的能力；
  零新依赖意味着任何环境都能跑起来，**校验边界用 21 个 Django 测试覆盖**。
- **Redis 挂了排行榜还能用吗？** → 答：能，**实测只慢 306 ms**（第 1 次），
  之后熔断期内 44 ms。MySQL 是真相来源，Redis 只是读路径。
- **为什么用 Lua 而不是 `ZADD GT`？** → 答：`GT` 要 Redis 6.2，本机是 5.0。
  Lua 语义相同且**原子**，比读改写更安全。
- **排行榜数据会不会造假？** → 答：客户端**没有任何写分接口**，
  分数由 TCP 服务端结算时算好直接入库（`04 §3.1` 取消 `/api/scores` 就是这个原因）。
- **密码怎么存的？** → 答：Django `auth_user` 的 PBKDF2 + salt，
  且有测试断言"库里不出现明文、`check_password` 能验回"。
