## D-001 数据库驱动用 PyMySQL，而不是 mysqlclient

- **日期**：2026-10-10
- **决定**：Django 连接 MySQL 使用 `PyMySQL`，配合 `pymysql.install_as_MySQLdb()`
- **理由**：
  1. **Windows 友好** —— `mysqlclient` 是 C 扩展，Windows 上安装需要编译环境（Visual C++ Build Tools），经常装不上；PyMySQL 是纯 Python，`pip install` 即可
  2. 本机是 Windows 开发环境，优先保证「装得上、跑得通」
- **备选方案**：`mysqlclient`（性能更好，但 Windows 安装门槛高）
- **代价 / 风险**：
  - PyMySQL 是纯 Python 实现，批量操作性能约为 mysqlclient 的 1/2 ~ 1/5
  - 需要额外安装 `cryptography`（MySQL 8 的 `caching_sha2_password` 认证需要）
- **落地方式**：项目包 `__init__.py` 中

  ```python
  import pymysql
  pymysql.install_as_MySQLdb()
  ```

- **答辩可能被问**：为什么不用官方推荐的 mysqlclient？
  → 答：Windows 环境下 C 扩展编译门槛高，PyMySQL 保证可移植性；性能差距在当前并发量级下可以忽略。

## D-002 降 Django 到 5.2 LTS，而不是升级 MySQL 到 8.4

- **日期**：2026-10-10
- **背景**：venv 中安装的 Django 6.1.2 连接 MySQL 8.0.41 时直接抛错：

  ```
  django.db.utils.NotSupportedError: MySQL 8.4 or later is required (found 8.0.41).
  ```

  经查 Django 官方 ticket [#36624](https://code.djangoproject.com/ticket/36624)：**Django 6.1 起将 MySQL 最低版本提高到 8.4**。这是框架源码里的硬性检查，没有任何配置项可以绕过。

- **决定**：把 venv 中的 Django 降到 **5.2 LTS**（实际安装 5.2.18）
- **理由**：
  1. **动作最小** —— 只更换 venv 中的一个包；升级 MySQL 需要下载 MSI、运行图形安装器、重启服务，并承担数据迁移风险
  2. Django 5.2 是 **LTS 版本**，维护到 2028 年，稳定性有保障
  3. Django 5.2 支持 MySQL 8.0.11+，与本机 8.0.41 匹配
  4. 毕设周期内不需要 Django 6.x 的新特性
- **备选方案**：升级 MySQL 到 8.4 LTS
- **代价 / 约束**：
  - ⚠️ **在升级 MySQL 之前，不能把 Django 升到 6.x**
  - 系统 Python 里另有一个 Django 5.0.3，与 venv 隔离；**运行项目必须使用 venv 的解释器**
- **验证结果**：降级后实测通过

  ```
  ('8.0.41', 'myproject', 'django_user@localhost', 'utf8mb4_unicode_ci')
  Django version : 5.2.18
  ```

- **答辩可能被问**：为什么不用最新版 Django？
  → 答：框架版本应在满足需求的前提下选择稳定版；5.2 是 LTS，且与本机数据库版本兼容，避免了升级数据库带来的额外风险。

## D-003 渲染采用几何多边形飞船，不使用位图素材

- **日期**：2026-10-10
- **决定**：玩家角色用 `pygame.draw.polygon` 绘制几何多边形（箭头/三角），机头指向行进方向
- **理由**：
  1. **零素材** —— 不需要找图、不存在版权问题
  2. **风格天然统一** —— 素材风格不统一是「廉价感」的头号来源
  3. **永不失真** —— 矢量绘制任意分辨率都锐利（对比：现有 `enemy0.png` 20×15 被拉到 30×30 已变形）
  4. **染色 / 发光 / 拖尾都容易加**
  5. 有朝向，符合「飞机大战」的直觉
- **备选方案**：位图精灵（`hero.png` 可染色复用，但仅 40×50，放大发虚且难统一风格）
- **代价 / 风险**：视觉上限低于精细美术资源（但本项目重点不是美术）
- **可逆性**：**完全可逆** —— 渲染层不影响通信系统
- **答辩可能被问**：为什么不用图片素材？→ 答：实时游戏的重点是通信；几何渲染保证风格统一、零素材依赖，且不影响任何网络层设计。

## D-004 游戏形态定为「竖版飞机大战 + 关卡 + BOSS」

- **日期**：2026-10-10（**取代同日早先的「极简多人」版本**）
- **决定**：游戏做**竖版飞机大战（弹幕射击）**：
  - **1~4 人合作**，**2 关 × 5 波**，**1 个三阶段 BOSS**
  - **3 种敌机**（直线俯冲 / 横向移动 / 追踪玩家）、**3 种弹幕**（直线散射 / 扇形 / 追踪弹）
  - **5 级火力**（伤害 + 射速 + 形态三重递进）、**拾取道具**升级
  - **几何绘制，零素材**，**720 × 960 竖版**窗口
- **演进过程（诚实记录）**：完整双摇杆 → 极简多人 → 抢靶 → **飞机大战**
- **理由**：
  1. **弹幕游戏是实时同步负载最重的类型之一** —— 200+ 颗子弹的高频生成/移动/销毁，是真正的同步难题，
     比「几个方块移动」有料得多（快照从 ~200 B 涨到 ~1974 B，带宽差 5 倍）
  2. **实测证明硬件撑得住**：4 人 + 30 敌机 + 200 子弹 = **0.45 ms/tick = 8.9% 单核**
  3. **天然有死亡条件**（被敌机/弹幕击中掉血），解决了抢靶方案「游戏永不结束」的漏洞
  4. **可复用现有代码约 80%** —— 玩家、敌机、子弹、碰撞的结构都已存在
  5. **动机**：学员明确表示想做飞机大战。**5 个月的项目，动力比省时间重要**
- **备选方案**：
  - 「极简多人」（只有方块移动）→ 同步负载太轻，实验数据单薄
  - 「抢靶方案」→ 无死亡条件，游戏不会结束（已否决）
- **代价 / 风险**：
  - ⚠️ 游戏内容代码从约 160 行升至约 **540 行**，多约 **13~17 小时**
  - ⚠️ 时间预算从约 218 h 升至约 **222 h**（超预算约 10%）
  - **兜底**：优先级 **④（游戏内容）排在最后，超时第一个砍**，论文不受影响
- **答辩可能被问**：为什么做弹幕游戏而不是更简单的？
  → 答：弹幕游戏的同步实体数量最多（200+ 子弹），是最能暴露实时同步问题的场景；
  实测证明单机性能足够（仅占 8.9% 单核），不存在做不动的风险。

## D-005 加入 HTTP 短连接层，与 TCP 长连接分层

- **日期**：2026-10-10
- **决定**：保留 Django，作为**主线的一部分**（非可选）：
  - **TCP 长连接**：实时同步（玩家位置、房间状态）
  - **HTTP 短连接（Django）**：登录、排行榜、玩家战绩
  - **MySQL**：用户与分数持久化
  - **Redis**：排行榜缓存
- **理由**：
  1. 题目是「数据通信**系统**」，分层设计比单一 TCP 服务器更完整
  2. 「按数据类型选择通信方式」是有质量的论文论点
  3. 环境（Django 5.2.18 / MySQL 8.0.41 / Redis）已就绪，边际成本可控
  4. TCP 连接用 HTTP 登录得到的 **token 认证**，两层自然衔接
- **备选方案**：纯 TCP 项目（省约 30 小时，但论文少一个论点）
- **代价 / 风险**：
  - ⚠️ **时间预算上升约 30 小时**（原估算 218 h → 约 248 h，而预算是 200 h）
  - ⚠️ **接口需要有调用方** —— 客户端要实现 HTTP 调用，且**不能在游戏主循环里阻塞**（见 D-007）
  - ⚠️ **排行榜缺少数据来源**（见 D-004）：当前玩法没有分数，需用玩家战绩类指标替代，或给玩法补一个极简得分机制
- **答辩可能被问**：为什么要两套通信方式？→ 答：实时数据要求低延迟高频次，适合长连接自定义协议；账号与战绩是低频请求-响应，HTTP 更简单可靠。按数据类型分层可降低系统整体复杂度。

## D-006 同步模型：服务端权威，客户端只上报输入

- **日期**：2026-10-10
- **决定**：客户端**只上报输入**（按键位掩码），坐标由服务端计算并广播。
- **理由**：
  1. **防篡改** —— 客户端无法直接伪造坐标
  2. 状态一致性由单一权威裁定，避免多端分歧
  3. 局域网 RTT < 5 ms，远小于一个 50 ms 的 tick，**不做客户端预测也不会感觉滞后**
- **备选方案**：
  - 客户端权威上报坐标（实现更简单，但可被任意篡改）
  - 服务端权威 + 客户端预测回滚（手感最好，但实现与调试成本高，列为进阶项 F12）
- **代价 / 风险**：
  - 客户端必须做**插值**，才能把 20 Hz 快照渲染成 60 fps 平滑动画
  - 服务端承担全部游戏逻辑计算（本项目规模下无压力）

## D-007 客户端网络 IO 采用非阻塞 socket + 每帧轮询

- **日期**：2026-10-10
- **决定**：客户端 socket 设为非阻塞，在 pygame 主循环中**每帧检查一次**可读性。
- **理由**：
  1. **绝不能阻塞渲染主循环** —— 阻塞式 `recv()` 会让游戏在网络卡顿时直接冻死
  2. 单线程、无锁、无并发 bug，逻辑简单可预测
  3. 便于调试（所有事情都发生在主循环里，没有线程交错）
- **备选方案**：独立接收线程 + 队列（编程模型更熟悉，但引入线程同步与退出处理问题）
- **代价 / 风险**：
  - 需要自己处理**部分写**（`send` 未发送完）与发送缓冲队列
  - 每帧轮询引入最多 1 帧（约 16 ms）接收延迟 —— 局域网场景下可忽略
- **答辩可能被问**：为什么不用多线程？→ 答：避免线程同步复杂度；游戏主循环本身就是天然的轮询驱动，非阻塞 IO 与它天然契合。

## D-009 游戏内容：射击 + 关卡 + BOSS（取代 D-008 的缩圈方案）

- **日期**：2026-10-10
- **决定**：
  - **玩家**：左右移动 + **自动向上射击**，3 点 HP，受击后 1.5 s 无敌帧
  - **火力**：**5 级**，伤害 + 射速 + 形态三重递进（单发 → 双发 → 三发扇形）
  - **道具**：击杀 15% 掉落，拾取升级；满级后转分数；**被击中降 1 级**
  - **敌机 3 种**：直线俯冲 / 横向移动 / 追踪玩家
  - **弹幕 3 种**：直线散射 / 扇形 / 追踪弹
  - **关卡**：2 关 × 5 波（50 + 80 架），波次「清完或超时 25 秒」推进
  - **BOSS**：1 个，3 阶段，血量 = **1250 × 进入时人数**
  - **失败条件**：玩家阵亡 10 秒后自动复活（火力重置为 1）；**全员同时阵亡才结束本局**
- **理由**：
  1. **一次解决三个问题**：排行榜有数据（分数）、关卡进度有名目、游戏有结束条件
  2. **同步负载大幅提升** —— 从「几个方块」变成 200+ 子弹，快照 1974 B（**39.5 KB/s**），
     序列化对比实验的差异从「不明显」变成「5.6 倍」
  3. **引入真实的同步难题** —— 高频瞬时实体的生成/销毁，是实时网络同步的经典问题
  4. **服务端权威有更多体现** —— 命中判定、伤害计算、火力等级、计分全在服务端
- **备选方案**：
  - 缩圈方案（D-008，已否决）
  - 「子弹 + 静态靶子」抢靶方案 → 无死亡条件，且同步实体种类少
- **代价 / 风险**：
  - ⚠️ 游戏代码从约 160 行升至约 **540 行**（+13~17 h）
  - ⚠️ BOSS 血量系数 1250 假设玩家平均火力 Lv4，**需实机调整**
- **答辩可能被问**：为什么要做 BOSS？
  → 答：BOSS 是一个**多阶段状态机**的同步对象（血量 + 阶段），
  与普通敌机、子弹、道具的同步策略不同，能覆盖更多同步场景。

## D-010 三阶段解耦：占位对象 → 完整游戏

- **日期**：2026-10-10
- **背景**：优先级 ④（游戏内容）排在最后（见 D-013），
  但阶段 ①~③（通信 / 抓包 / 性能）**必须先有可同步的对象**才能验证。
- **决定**：把**网络层与游戏层解耦**，分三阶段演进：

  | 阶段 | 同步对象 | 目的 |
  |---|---|---|
  | 阶段 1~3（第 1~13 周） | **极简占位**：几个方块在场地内移动 | 独立验证通信系统 |
  | 阶段 4（第 14~17 周） | 逐步替换为敌机、子弹、道具 | 增加负载与复杂度 |
  | 最终 | 完整飞机大战（含 BOSS） | 演示效果 |

- **理由**：
  1. **通信系统可独立验证** —— 用最简单的对象证明协议、粘包、同步、并发都是对的
  2. **占位方块是最好的协议测试工具** —— 排查问题时排除游戏逻辑干扰
  3. **风险前移** —— 最难的部分先做完，游戏内容可随时削减
- **关键约束**：占位阶段的**实体结构、同步机制、渲染管线与最终版本一致**，只是实体类型少。
  **替换游戏内容时通信层不用改。**
- **答辩可能被问**：占位阶段是不是白做了？
  → 答：不是。它证明了通信系统独立于游戏内容可用，这正是「数据通信系统」作为交付物的核心论点。

## D-011 性能硬约束：同屏实体上限

- **日期**：2026-10-10
- **背景**：实跑基准测试（Ryzen 7 7735H / 31.2 GB）：

  ```
  players enemies bullets   |  ms/tick | snapshot | CPU@20Hz
  --------------------------------------------------------------------
        4      30     200   |    0.45  |    1655 B |   8.9 %   ← 设计目标
        8      50     400   |    1.21  |    3231 B |  24.1 %
       16     100     800   |    4.37  |    6453 B |  87.3 %   ← 单核极限
  ```

- **决定**：
  - **同屏敌机上限 = 30**
  - **同屏子弹上限 = 300**
  - **刷怪前必须检查当前敌机数**，超上限则延后本波剩余敌机的刷新
- **理由**：
  1. tick 预算为 50 ms（20 Hz）；超过上限会让单帧耗时逼近预算，**导致掉帧**
  2. **这是硬件决定的，不是设计偏好** —— 因此它必须现在定，而不是"后面调"
  3. 该保险机制**不会死锁** —— 敌机被击杀后释放名额，刷新继续，只是节奏变慢
- **代价 / 风险**：
  - ⚠️ 关卡编排（每波敌机数）受此约束，不能"一口气刷 60 个敌人"
  - 实验 E2（并发测试）会主动突破此约束以寻找性能拐点 —— **这是有意的**
- **答辩可能被问**：为什么定 30 而不是 50？
  → 答：实测得出。50 个敌机时单核占用已达 24%，再叠加子弹增长会逼近预算；
  30 个时仅占 8.9%，留出 5 倍余量应对峰值。

## D-012 协议坐标值域：出屏即剔除

- **日期**：2026-10-10
- **背景**：基准测试时发现的**真实 Bug**：

  ```
  struct.error: 'H' format requires 0 <= number <= 65535
  ```

  子弹飞出屏幕后坐标为**负数**，而协议坐标用 `uint16`（只能表示 0~65535），**编码直接崩溃**。

- **决定**：**出屏即剔除** —— 坐标越界的实体**不写入快照**，客户端据此删除该实体。
- **理由**（对比另外两个方案）：

  | 方案 | 评价 |
  |---|---|
  | **A. 出屏即剔除** | ✅ **采用**：省带宽 + 客户端逻辑更简单 |
  | B. 改用 `int16` | 支持负坐标，但浪费一半值域 |
  | C. 序列化时截断 | ❌ 数据错误 |

- **衍生设计原则**：**快照是全量真相**。
  客户端每收到一帧快照，就**完全以快照为准**重建本地实体表 —— 快照里没有的实体一律删除。
  **因此无需额外的「删除实体」消息。**
- **答辩可能被问**：协议设计时怎么考虑数据值域？
  → 答：坐标用 `uint16` 是无符号的，而实体越界后会产生负值。
  这提醒我们协议字段的值域必须与业务数据的实际范围对齐；本项目的解法是「不同步越界实体」，
  既避开了值域问题，又顺带省了带宽。

## D-013 优先级顺序与时间预算

- **日期**：2026-10-10
- **决定**：明确优先级为

  ```
  ① 通信跑通  →  ② 抓包实验  →  ③ 性能测试  →  ④ 游戏内容
  ```

- **理由**：
  1. **这个顺序保证：任何一周停下来，手上都有完整可交付、可写论文的成果**
  2. 做到 ③ 时，**论文第 3 / 4 / 6 章素材齐全，毕设已经成立**
  3. ④ 是「锦上添花」，**时间不够时第一个砍它，论文不受影响**
- **时间账**：
  | 项 | 值 |
  |---|---|
  | 可用预算 | 20 周 × 10 h = **200 h** |
  | 估算需求 | 约 **222 h** |
  | 差额 | 超支约 **10%**，**靠砍 ④ 兜底** |
- **止损点**：

  | 检查点 | 如果没做到 | 处理 |
  |---|---|---|
  | 第 9 周 | 通信没跑通 | 🔴 **红线**，停下查原因 |
  | 第 13 周 | 性能测试没数据 | 🔴 **红线**，没有第 6 章毕设会很虚 |
  | 第 17 周 | 游戏内容没做完 | 🟡 **正常**，砍 BOSS 或砍到 1 关 |

- **答辩可能被问**：如果重做一次，你会怎么安排？
  → 答：同样的顺序。先保证「数据通信系统」这个核心交付物成立，再考虑游戏内容的丰富度。

## D-014 asyncio 服务端中不能使用阻塞式数据库驱动

- **日期**：2026-10-10
- **背景**：TCP 服务端在一局结束时要写 MySQL（成绩）和 Redis（排行榜）。
  但服务端是 **asyncio 单线程事件循环**，而 `pymysql` 是**阻塞式**驱动 ——
  一次数据库写入会**阻塞整个事件循环**，导致同一时刻所有客户端掉帧。
- **决定**：
  1. **MySQL 写入放到线程池** —— `await asyncio.to_thread(...)`（Python 3.9+），不要把阻塞调用直接放进协程
  2. **Redis 用异步客户端** —— `redis.asyncio`（`redis` 包已自带，无需额外依赖）
  3. **写入失败必须重试 + 落盘兜底** —— 成绩不能因为数据库抖动而丢失
  4. 数据库操作**只在结算时发生**，不在 20 Hz 的游戏循环里
- **理由**：
  1. 「事件循环里不能有阻塞调用」是 asyncio 的核心纪律，违反会拖垮全部并发连接
  2. 结算是一局一次的低频操作，放线程池的额外开销可忽略
  3. 成绩是毕设里唯一的持久化数据，**丢了就白打了**
- **备选方案**：
  - 改用异步 MySQL 驱动（`aiomysql`）→ 更纯粹，但多一个依赖、生态较小
  - 用独立进程处理数据库写入（消息队列）→ 过度设计
- **代价 / 风险**：
  - `asyncio.to_thread` 会占用线程池线程，高并发结算时需要留意线程池大小
  - **必须在早期就做对** —— 后期发现事件循环被阻塞，排查成本很高
- **答辩可能被问**：为什么数据库写入要放线程池？
  → 答：asyncio 是单线程事件循环，任何阻塞调用都会卡住**所有**连接。
  `pymysql` 是同步驱动，必须 `to_thread` 隔离；这也是「事件驱动模型下如何与阻塞式组件共存」的典型问题。

## D-015 第 1 步用阻塞式单客户端回声程序起步，不直接上 asyncio

- **日期**：2026-10-19
- **决定**：阶段 1 的第 1 步只写两个最小脚本：
  - `server/echo_server.py`：阻塞式 `accept` / `recv` / `sendall`，一次只服务一个客户端，**不加消息边界**
  - `client/echo_client.py`：命令行发送一行、打印回显与 RTT

  长度前缀留到第 2 步，asyncio 留到第 5 步。
- **理由**：
  1. **让 socket 的基本语义可见**：`accept` 等连接、`recv` 返回“当前能读到的字节”而不是“一条消息”、`sendall` 负责把数据发完
  2. **先看见阻塞模型的缺陷**（一次只能服务一个客户端、一个慢客户端会卡住所有人），第 5 步再引入 asyncio，才知道它解决了什么问题
  3. 逻辑约 30 行，变量少，出错时容易定位，适合作为第一步建立信心
- **备选方案**：
  - 直接用 asyncio 写回声服务器 → 这确实是最终架构，但 `await reader.read()` 把“字节流无边界”藏了起来，容易误以为“一次 read 就是一条消息”
  - 用 `SocketServer` / Twisted 等框架 → 封装太厚，不适合作为理解底层的第一步
- **代价 / 风险**：
  - 这段代码**不是最终服务端**，第 5 步会被 asyncio 版本取代；但 `recv` / `sendall` / `accept` 的概念与排错经验完全复用
  - **单客户端是刻意保留的限制，不是 Bug**
- **答辩可能被问**：为什么不用 asyncio 一步到位？
  → 答：先理解阻塞 IO 的行为和瓶颈，才能说清 asyncio 解决了什么问题；最终服务端确实用 asyncio，但那是第 5 步的重构目标。

## D-016 网络实验必须使用独立网络栈，不能依赖“本机连自己的局域网 IP”

- **日期**：2026-10-19
- **背景**：`01-系统架构.md §11.2` 要求阶段 1 实测：客户端连**本机局域网 IP**（而不是 `127.0.0.1`）能否拿到真实 RTT 与抖动。第 1 步实测结果：
  - `ping 127.0.0.1` 与 `ping 10.140.71.127` 均 **< 1 ms**
  - 回声 RTT **0.03~0.14 ms**
  - 向 `10.140.71.127` 传 16 MB：**1145.8 MB/s**，WLAN 网卡收发增量仅 **0.001 / 0.012 MB**
- **结论**：**Windows 把发往本机地址的流量短路到回环，根本没有经过网卡**。`§11.2` 的兜底条件（0.1 ms 量级）已触发。
- **决定**：
  1. **本机多进程**继续用于：协议、粘包、并发、房间逻辑、抓包字段核对
  2. **RTT / 抖动 / 丢包 / 网络损伤类实验**，改用**虚拟机桥接网络**或**第二台设备**
  3. 具体选型（VirtualBox / VMware / Hyper-V / 借设备）待定，但**第 13 周性能测试前必须就绪**
- **理由**：
  1. 1145.8 MB/s 是内存拷贝速度，不是 WiFi 速度；网卡计数器不增长，说明流量没出协议栈
  2. 在回环上做“网络实验”，RTT 恒定在 0.1 ms 且无抖动，**数据不可信，论文不能用**
  3. 虚拟机有独立网络栈，可在 guest 内用 `tc netem` 注入延迟 / 抖动 / 丢包，实验可重复
- **备选方案**：
  - 只在本机 `127.0.0.1` 上做实验 → 数据没有网络意义（否决）
  - 用 `clumsy` 等工具在主机上注入延迟 → 对回环流量的作用不可靠，且难以写进方法论
  - 第二台物理设备 / 树莓派 → 最真实，但成本高；作为升级选项保留
- **代价 / 风险**：
  - 增加环境搭建时间（预计 2~4 h）
  - 虚拟机桥接的 RTT 也可能只有 0.x ms，需要**主动用 netem 注入**可观测的延迟 / 抖动；这本身要写进实验设计
- **答辩可能被问**：为什么不能直接在本机用局域网 IP 测？
  → 答：实测 16 MB 传输达到 1145.8 MB/s 且网卡计数器几乎不动，证明 Windows 把本机地址短路成了回环。这种“网络”没有 RTT 和抖动，不能用于网络性能结论；必须用独立网络栈。

## D-017 第 2 步用 4 字节大端长度前缀划清消息边界

- **日期**：2026-10-19
- **决定**：
  - 本步帧格式：`uint32 大端长度 + payload`，长度**只算 payload**，不含 4 B 头
  - 接收端用 `recv_exact()` 循环读满；`recv_frame()` 先读 4 B 长度，再读 N B
  - 单帧载荷上限 `MAX_PAYLOAD = 64 KiB`；超限抛 `ProtocolError` 并断开连接
  - 第 4 步把 4 B 长度扩展成 **12 B 帧头**（magic / version / type / seq / length），
    “先读长度、再读载荷”的核心不变
- **理由**：
  1. **二进制安全**：长度前缀对任意字节都成立；分隔符（`\n`）遇到载荷里的 `\n` 必须转义
  2. **大端 = 网络字节序**：`struct` 的 `!I` 明确表达跨平台一致
  3. **把“可能只收到一部分”的循环收敛到一个函数**：业务代码只看到完整消息，不必重复写 while
  4. **64 KiB 上限**：防止对端声明 4 GB 长度把内存吃光；本项目快照约 2 KB，留了 30 倍余量
- **备选方案**：
  - 分隔符（`\n` / `\0`）→ 二进制载荷要转义，体积和复杂度都上升（否决）
  - 定长包 → 载荷可变时浪费带宽（否决）
  - 每次 `recv(65536)` 后自己切 → 还是要处理半包 / 粘包，且缓冲区逻辑散落各处
- **代价 / 风险**：
  - 每帧多 4 B；1 B 的输入包头部是载荷的 4 倍（第 4 步变 12 B 后是 12 倍，见 `02 §4.1`）
  - `recv_exact()` 是**阻塞版本**；第 6 步客户端改非阻塞后，要换成“缓冲区 + 状态机”的 FrameParser
- **答辩可能被问**：长度字段为什么用 4 字节，不用 2 字节？
  → 答：2 字节上限 65535 B，当前快照够用，但扩展余量小；4 字节是通用做法，只多 2 B，
  并且后面加 seq / type 时帧头本身就会超过 4 字节。

## D-018 帧边界测试用标准库 unittest + FakeSocket，不依赖真实网络

- **日期**：2026-10-19
- **决定**：
  1. 用标准库 `unittest` 写 `tests/test_framing.py`，**不引入 pytest**
  2. 用 `FakeSocket` 精确编排每次 `recv(n)` 返回的字节；另保留 1 个 `socket.socketpair()` 真实 socket 用例
  3. 测试只覆盖 `framing.py` 的纯逻辑；真实端到端联调留到第 5~6 步
- **理由**：
  1. 半包 / 粘包在真实 TCP 上由内核决定，**无法稳定复现**；FakeSocket 可以精确制造“每次只给 1 字节”“两条帧粘在一起”“读到一半断开”
  2. 纯逻辑测试**毫秒级、可重复、失败定位直接**（15 个用例 0.002 s）
  3. 标准库零安装，符合“先跑通再引入工具”的节奏
- **备选方案**：
  - pytest → 写法更简洁，但当前规模用不上；以后需要 fixture / 参数化再换
  - 直接开真实服务器做集成测试 → 受端口、时序、内核缓冲区影响，容易不稳定；留到端到端阶段
  - 只用 socketpair 模拟 → 仍然无法精确控制每次 recv 的拆分
- **代价 / 风险**：
  - FakeSocket 不是真实 socket，可能漏掉 OS 层行为（EINTR、非阻塞 EAGAIN）；由真实 socketpair 用例和后续联调兜底
  - 第 4 步扩成 12 字节帧头后，测试里的帧头偏移要同步更新
- **答辩可能被问**：为什么不用真实网络测？
  → 答：单元测试要能稳定复现边界情况。真实 TCP 的拆分方式不可控，同一个用例可能时过时不过；
  用 FakeSocket 把“每次 recv 返回多少字节”变成确定输入，才能真正证明拆包逻辑正确，端到端另有联调。
