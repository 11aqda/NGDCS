## 3. 三个变体的定义（这是本实验的设计核心）

| 变体 | 是什么 | 用来回答 |
|---|---|---|
| `binary` | 协议标准编码：逐条目 `struct.pack` 再拼接 | 基线 |
| `binary_fast` | **同一个协议、产物逐字节相同**，但整帧只调一次 `struct.pack`（格式串按实体数缓存 `Struct`） | **实现方式**能带来多少差异 |
| `json` | 短键名 JSON，另一套编码（编解码双向都实现） | **编码形式**能带来多少差异 |

**为什么必须有 `binary_fast`**：没有它，JSON 慢多少都可以被质疑成
"你的二进制写得快"或"你的 JSON 写得烂"。有了它，「协议形式」和「实现方式」
就成了两个可以分别测量的量。

## 4. ⚠️ 公平性：可检查的硬约束（答辩会被问，这里逐条钉死）

对照组的实现方式直接决定结论可信度，所以把「公平」落成**可执行、可复核**的约定：

| # | 约束 | 怎么保证 |
|---|---|---|
| 1 | **字段与实体集合完全一致** | 同一份 `Snapshot` 进三种编码器，装的是同一批数据。**往返测试锁住**：`JsonEncoder.encode` → `unpack_snapshot_json` 的结果与 `BinaryEncoder.encode` → `unpack_snapshot` 的结果**完全相等**（`tests/test_encoders.py::JsonRoundTripTest`，覆盖 8 种实体组合） |
| 2 | **`encode_ms` 涵盖各自的完整编码过程** | JSON 侧**包含建 `list[dict]` + `json.dumps` + `encode("utf-8")` 全过程**；二进制侧**包含逐字段读取属性 + `struct.pack` 全过程**。三者计时窗口的**起止点完全相同**（`server/main.py::build_snapshot` 里同一个 `perf_counter()` 包住 `encoder.encode()`） |
| 3 | **用标准库、不做人为劣化** | `json.dumps(payload, separators=(",", ":"), ensure_ascii=False).encode("utf-8")` —— 去空格、关 ASCII 转义，都是"认真写 JSON"该做的 |
| 4 | **键名刻意取短** | `t`/`p`/`i`/`x`… 而不是 `tick`/`players`/`id`/`x` —— 拿字段名拼全的 JSON 来比是稻草人 |
| 5 | **不给 JSON 加协议值域校验** | JSON 没有固定位宽，本来就不需要；强加二进制协议的约束反而对它不公 |
| 6 | **JSON 是完整可用的协议路径** | 解码也实现了（`unpack_snapshot_json`），不是"只管发不管收"的一次性序列化函数 |

> **还能再压的余地（如实说明，避免被指稻草人）**：把 JSON 条目从对象改成数组
> （`[1,100,200,0,3]` 而不是 `{"i":1,"x":100,...}`），体积约再降一半。
> 但那已经不是"用 JSON"而是"用 JSON 语法手写二进制"（失去自描述性），
> 本实验不实现 —— 这个量级差已在 §7 里说明。

## 5. 关键结果

### 5.1 ⭐ 最重要的一条：JSON 在最大规模下**根本发不出去**

`E1-e250-b2000-json` 的两轮**全部失败**，同一原因、可复现：

```
[server] !! tick loop 已崩溃，不再广播快照：
ProtocolError: 载荷超限：79538 B > 65536 B      ← r1
ProtocolError: 载荷超限：89538 B > 65536 B      ← r2
```

- 协议在帧层有 `MAX_PAYLOAD = 64 KiB` 的上限（`protocol/framing.py`）
- **JSON 在 250/2000 规模下产生 79.5~89.5 KB 的载荷，超出上限 → 帧层拒绝发送 → tick 循环崩溃**
- 同规模下二进制只有 **18 307 B**（上限的 28 %），毫无压力

> **这不只是"体积大 4.7 倍"，而是"在目标规模下不可用"。**
> 而且两轮的载荷大小不同（79 538 / 89 538 B），说明它**已经贴在悬崖边上** ——
> 实体数稍有波动就掉下去。

**越线点估算**：按实测的三点（234 实体 → 9076 B、904 → 34 788 B、1354 → 52 097 B）
线性拟合约 **38.4 B/实体**，越过 65 536 B 大约在 **1700 实体**（≈ 190 敌机 / 1500 子弹）。

### 5.2 体积对比（两轮均值）

| 档位 | 实体 | `binary` | `binary_fast` | `json` | **json / binary** |
|---|---|---|---|---|---|
| 30/200 | 234 | **1927 B** | **1927 B** | **9076 B** | **4.71×** |
| 100/800 | 904 | **7357 B** | **7357 B** | **34 788 B** | **4.73×** |
| 150/1200 | 1354 | **11 007 B** | **11 007 B** | **52 097 B** | **4.73×** |
| 250/2000 | 2254 | **18 307 B** | **18 307 B** | ❌ 超出帧上限 | — |

- `binary` 与 `binary_fast` **逐字节相同**（这正是设计意图，有测试断言）
- 二进制侧**逐字节吻合**协议公式 `13 + 4×11 + 9E + 8B`，偏差 **0 B**
- JSON 比例**稳定在 4.7×**（三档 4.71 / 4.73 / 4.73）—— 说明这不是偶然，是结构性的

### 5.3 ⭐ 编码耗时：`binary` ≈ `binary_fast`，JSON 慢 4~5 倍

`encode_ms` 的两轮轮间偏差只有 **0.4 % ~ 3.4 %**，所以几 % 的差异是信号不是噪声。

| 档位 | `binary` | `binary_fast` | 差异 | `json` | json / binary |
|---|---|---|---|---|---|
| 30/200 | 0.0639 | 0.0692 | **+8.3 %**（fast 略慢） | 0.2493 | **3.90×** |
| 100/800 | 0.1608 | 0.1450 | −9.8 % | 0.6396 | **3.98×** |
| 150/1200 | 0.2164 | 0.2058 | −4.9 % | 1.0569 | **4.89×** |
| 250/2000 | 0.3600 | 0.3233 | −10.2 % | — | — |

**怎么读这张表**：

1. **`binary_fast` 在小规模反而略慢（+8.3 %），在大规模快 5~10 %。**
   原因：小规模时"查缓存 + 拼格式串 + 摊平参数"的固定开销占了上风；
   大规模时省掉 1700 多次 `Python→C` 跨界调用才开始回本。

2. **但这点差异在总耗时里可以忽略** —— 编码只占 tick 的：

   | 档位 | `binary` 编码 / 总耗时 | `binary_fast` | `json` |
   |---|---|---|---|
   | 30/200 | 6.4 % | 6.8 % | **21.2 %** |
   | 100/800 | 2.7 % | 2.5 % | **10.4 %** |
   | 150/1200 | 1.8 % | 1.8 % | **8.5 %** |
   | 250/2000 | 1.2 % | 1.1 % | — |

   → **打包方式换来换去，总 tick 耗时的变化 < 0.1 %。**

3. **结论（按拍板的口径写）**：
   > **打包方式不是瓶颈；二进制的优势是结构性的** ——
   > 不建 dict、不自描述字段名，因而体积小 4.7 倍、编码快 4~5 倍，
   > 而且在大规模下仍然发得出去。
   >
   > 换句话说：**JSON 慢不是因为"我们把它写慢了"，而是它的结构性开销** ——
   > 每个实体都要建一个 dict 对象、每个字段都要重复一遍键名。

### 5.4 下游影响：带宽与 tick 总耗时

| 档位 | 快照 B | 下行 KB/s（每客户端） | tick ms | 单核 % |
|---|---|---|---|---|
| | binary / **json** | binary / **json** | binary / **json** | binary / **json** |
| 30/200 | 1927 / **9076** | 37.9 / **177.6** | 0.994 / **1.173** | 2.2 / **2.5** |
| 100/800 | 7357 / **34 788** | 144.0 / **680.2** | 5.891 / **6.154** | 13.2 / **11.1** |
| 150/1200 | 11 007 / **52 097** | 215.4 / **1018.5** | 11.787 / **12.469** | 23.6 / **24.7** |

- **带宽差 4.7 倍**是直接后果：150/1200 时 JSON 每客户端要 **1.0 MB/s**
- **tick 总耗时只差 5~18 %** —— 因为 E9 已经证明碰撞判定才是大头（占 tick 的 60~90 %），
  编码只是小头。**这正好印证了"瓶颈在游戏逻辑侧"**
- CPU 那几个数在低负载档位受调度计时粒度量化，**以 `tick_ms` 为准**（与 E9 同口径）

## 6. 多轮一致性（`03 §7` 要求）

| 指标 | 结果 |
|---|---|
| `tick_ms` 两轮偏差 | **0.3 % ~ 1.7 %**（12 个场景全部） |
| `encode_ms` 两轮偏差 | **0.4 % ~ 3.4 %** |
| CPU 偏差 | 低负载档位（<5 %）受计时粒度限制，**以 `tick_ms` 为准**；中高负载 0.4 %~7.1 % |

**结论：数据可作正式使用。**

## 7. 数据质量、异常与已知局限

### 7.1 ⚠️ 实验期间发现并修复的一个数据完整性 Bug

**现象**：`server_metrics.csv` 的表头是 22 列，而 E1 写出的数据行是 **23 列** ——
从 `encode_ms` 往后**整列错位**（读出来的 `snapshot_bytes` 只有 48 B、`encode_ms` 是空的）。

**根因**：`_open_for_append()` 只在「文件不存在或为空」时写表头。
文件里已有 3312 行 E9 数据（旧表头 22 列），所以新增的 `encode_ms` 列
**从没被写进表头**；而 `csv.DictWriter` 是按 `fieldnames` 顺序写值的，
于是数据行多一个值、表头少一个名字 —— **不报错、不崩溃，只是数据全错**。

**处理**：
1. 新增 `tools/migrate_metrics.py`：按**列名**（不是位置）把旧行迁移到新字段表，
   缺的新列补空值；已在真实数据上执行（3312 行 E9 补空 `encode_ms`，备份为 `.bak`）
2. `_open_for_append` 改为**表头不匹配就抛 `MetricsSchemaError` 并指出修法** ——
   宁可在开跑前失败，也不要跑完 75 分钟拿到一份错位数据
3. 表头/写入字段一致性由测试锁住（`tests/test_metrics.py`）

> **教训**：append-only 的 CSV + schema 演进是必然会撞上的组合。
> 这次的错误**没有任何报错**，只有靠人眼比对列数才发现 ——
> 如果不查，E1 的整批数据都会是错的，而且图还能照画。

### 7.2 其他局限

| 局限 | 说明 |
|---|---|
| **本机 loopback** | RTT ≈ 0 ms（D-016）。本实验的因变量是**服务端编码开销与体积**，不受 RTT 影响 |
| **带宽是"应用层字节数"** | 由服务端自计，不是抓包实测值（差一个 TCP/IP 头开销）。抓包验证是 E7 的任务 |
| **无道具** | 三种编码的条目集合都不含道具，与 `01 §7.4` 含 5 道具的设计估算口径不同 |
| **JSON 未测 250/2000** | 因为**发不出去**（§5.1）—— 这是结论不是缺失 |
| 与旧文档的 5.6 倍不可比 | 那是含 5 道具的纸面估算（1974 B / 11000 B），本次是实测 4.7 倍 |

## 8. 结论

1. **二进制协议在体积上是结构性的优势：4.7 倍**（三档稳定复现），
   且二进制侧逐字节吻合协议公式
2. ⭐ **JSON 在 250/2000 规模下无法发送**（载荷 79.5~89.5 KB > 64 KiB 帧上限，
   两轮可复现）。**这从"性能差异"升级成了"可用性差异"**
3. **`binary` 与 `binary_fast` 的差异可以忽略**（±10 %，且只占 tick 的 1~7 %）——
   **打包方式不是瓶颈**，说明第 1 条的结论是**协议形式**带来的，
   不是"我们把某一方写快了/写慢了"
4. **编码开销随实体数增长而占比下降**（JSON 从 21.2 % 降到 8.5 %），
   与 E9 的结论一致：**真正的瓶颈在游戏逻辑侧（碰撞判定）**
