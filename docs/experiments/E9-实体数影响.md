### 3.2 三条核心结论

**① 通信占比随实体数单调下降：73.0 % → 6.7 %**

这是本实验最重要的结果。直觉上"实体越多、要传的字节越多、通信越贵"，
但实测**占比**一路下降 —— 因为游戏逻辑是 O(子弹×敌机) 的超线性增长，
而通信是近似线性的，占比被逻辑侧稀释。

**通信层是可扩展的，瓶颈在游戏逻辑侧的算法复杂度。**
这正是「数据通信系统」这个题目要证明的事。

**② 广播发送耗时与报文大小几乎无关：0.137 ~ 0.182 ms**

快照从 547 B 涨到 18 307 B（**33.5 倍**），而广播耗时只从 0.150 涨到 0.182 ms。
原因是内核发送缓冲区未饱和时 `await drain()` 立即返回，
所以广播成本主要是「每个客户端一次 write 调用」的固定开销 ——
**≈ O(客户端数)，与报文大小无关**。（缓冲区一旦饱和就会退化，那正是 E4/E5 要测的。）

**③ 单核占用跨过 50 % 舒适线，拐点位于 200/1600 ~ 250/2000 之间**

| 档位 | 单核占用 |
|---|---|
| 200/1600 | 39.2 % |
| **（插值 ≈50 %）** | **约 215/1720** |
| 250/2000 | 61.0 % |

而 D-011 的硬约束是「同屏敌机 ≤ 30、子弹 ≤ 300」——
对应 30/200 档，单核仅 **2.0 %**，余量充足。**设计约束得到实测支持。**

### 3.3 交叉验证：`tick_ms × 20 Hz` 应当等于单核占用

两个指标由**完全独立**的机制测得（前者是进程内 `perf_counter` 量 tick 主体的墙钟时间，
后者是 psutil 读进程累计 CPU 时间），二者应当自洽。实测：

| 档位 | tick×20 | 实测单核 | 吻合度 |
|---|---|---|---|
| 30/200 | 2.03 % | 2.0 % | ✅ |
| 100/800 | 11.5 % | 10.5 % | 91 % |
| 150/1200 | 23.3 % | 23.2 % | ✅ |
| 200/1600 | 39.9 % | 39.2 % | 98 % |
| 250/2000 | 61.6 % | 61.0 % | 99 % |

高负载下两者几乎完全一致 —— 说明此时 tick 主体**几乎全是 CPU 时间**（碰撞主导，
`drain()` 不阻塞）。低负载（≤ 10/50）时 CPU 读数被调度计时粒度量化，以 `tick_ms` 为准。

### 3.4 带宽线性度

下单行模型（4 玩家、无道具）：

```
快照载荷 = 13 + 4×11 + 9×敌机 + 8×子弹 = 57 + 9E + 8B   （字节）
```

**9 档全部逐字节吻合**（偏差 0 B）：

| 档位 | 公式 | 实测 |
|---|---|---|
| 10/50 | 547 | **547** |
| 30/200 | 1 927 | **1 927** |
| 250/2000 | 18 307 | **18 307** |

下行带宽 = 快照 ÷ 时间 × 20 Hz，9 档同样线性（10.9 → 357.8 KB/s）。

## 5. 数据质量与异常

### 5.1 采集完整性

- **18/18 轮全部达标**：每轮 4/4 连接、机器人 `errors = 0`、无服务端崩溃标记、指标行数 184
- 每轮快照数 14 397 ~ 14 400（理论值 4 × 20 Hz × 180 s = **14 400**）—— 吻合
- 服务端日志中无 `tick loop 已崩溃` 标记

### 5.2 环境干净度

每轮前后采样的整机 CPU：**1.4 % ~ 16.1 %**（16 逻辑核）。
实验为单进程 asyncio 服务端 + 4 个机器人，占用一个核以内，
其余负载来自系统本身，**机器基本空闲**，测量条件良好。

### 5.3 ⚠️ 必须如实记录的一处干扰

**第 1 轮 `E9-e10-b50-r1` 的最后约 20 秒，我在同一台机器上跑了单元测试套件**
（218 个用例，约 3.5 秒满载一个核）。

- 影响面：该轮 180 秒窗口的最后约 11 %，且**热身已剔除前 10 秒**
- 判定：该轮与 r2 的 **tick 偏差 0.9 %**、CPU 偏差 14.5 %（但该档 CPU 均值仅 0.0 %，
  本就受计时粒度限制），**未造成可观测的偏差**，数据保留
- 教训：跑批期间**不应**在同一台机器上执行任何重负载任务。
  运行器已记录每轮前后的整机 CPU 供事后审查（`manifest.json`）

### 5.4 已知局限

| 局限 | 说明 |
|---|---|
| **本机 loopback** | RTT ~0 ms，测不到真实网络指标（D-016）。本实验的因变量是**服务端处理开销**，不受此影响；但 E4/E5 的延迟/丢包实验必须在 VMnet1 + netem 上做 |
| **低负载 CPU 读数** | ≤ 50/400 档的逐秒 CPU 被调度计时粒度量化；已改用累计值算整轮，但均值仍偏保守（更低） |
| **与 `01 §7.1` 旧基准不可逐位对齐** | 旧数据来自一次性原型（代码未保留），只对齐复杂度与趋势。同规模（100/800）本次 **5.738 ms** vs 旧基准 **4.37 ms**，同一量级 |
| **没有真实游戏逻辑** | 碰撞为占位实现（只判定不生效），敌机无 AI；第 11 步替换后绝对耗时会变，但**通信部分不受影响** |

## 7. 结论与对设计的影响

1. **D-011 的硬约束（敌机 ≤ 30、子弹 ≤ 300）得到实测支持**：
   设计目标规模 30/200 下单核仅占 2.0 %，有 49 倍余量应对峰值。
2. **拐点在 200/1600 ~ 250/2000 之间**：这给出了"超过多少实体就该降级"的量化边界，
   可作为后续关卡编排（第 11 步）的上限参考。
3. **通信层不是瓶颈**：即使 18 KB/帧、358 KB/s/客户端，通信也只占 6.7 % 的 tick 时间。
   若要继续提升容量，应优化碰撞检测的算法复杂度（空间划分），而不是协议本身。
4. **协议设计的一个代价值得讨论**：子弹条目没有唯一 ID（省 400 B/帧、约占快照 20 %），
   代价是客户端无法对子弹做实体插值。
