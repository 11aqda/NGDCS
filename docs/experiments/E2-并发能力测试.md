## 3. 三个结论

### ① 250 连接内，tick 仍只用 5.7 ms —— 距 50 ms 预算还有一个数量级

最重的一档（250 连接）`tick 均耗时 5.743 ms`、`p95 约 6.2 ms`，**只占 20 Hz 预算的 12%**。
单核占用 **24.9%**，内存 44.5 MB（每连接约 0.08 MB）。

也就是说：**从资源角度看，服务端还能再上一个量级** —— 但先撞到了协议上限（见结论 ②）。

### ② ⭐ 真正的上限来自**协议字段宽度**，不是 CPU 或带宽

300 档两轮**全部崩溃**，服务端日志给出确定原因：

```
[server] !! tick loop 已崩溃，不再广播快照：ProtocolError: 玩家 数量超出上限：257 > 255
  File "server/main.py", line 244, in build_snapshot
    payload = self.encoder.encode(self.tick, players, enemies, bullets)
  File "protocol/snapshot.py", line 141, in pack_snapshot
    _check_count(len(players), 0xFF, "玩家")
protocol.framing.ProtocolError: 玩家 数量超出上限：257 > 255
```

快照头里 `player_count` 是 **uint8**（1 字节），上限 255。
**第 257 个玩家连上时，序列化抛错，tick 循环死掉。**

> **这比"跑到 300 撑不住了"有价值得多**：它说明系统在 250 连接时资源还很宽裕
> （CPU 24.9%、tick 5.7 ms），是**协议设计**先划出了天花板。
> 也解释了为什么 250 档能过、300 档必崩 —— 分界线就是 255。

**这不是缺陷，是设计约束**，与「同屏敌机 ≤ 30」性质相同：
本协议面向局域网小规模对战，1 字节容量（255 人）远超实际需求。

### ③ 增长**全在通信侧**，碰撞几乎纹丝不动

| | 10 连接 | 250 连接 | 倍数 |
|---|---|---|---|
| 碰撞 | 0.464 ms | 0.450 ms | **0.97×（持平）** |
| 通信 | 0.588 ms | 4.984 ms | **8.5×** |

**这是 D-029「固定实体数」直接带来的可读性**：实体数不变，所以逻辑侧恒定，
增长全部归因于广播。如果实体数随玩法变动，这条结论就说不出来了。

同时注意快照从 1993 B 涨到 4523 B —— **因为快照里包含所有玩家**，
每多一个玩家，**每个客户端**收到的快照都多 11 B。所以总带宽是 `N × (1883 + 11N)`，
增长略快于线性（250 连接时 90.4 KB/s per 客户端，总出向约 22 MB/s）。

## 4. 方法学：这一轮抓到两个**会让数据说假话**的坑

### 4.1 崩溃之后，指标反而"变好看"

300 档报出来的 `tick 均 2.5 ms`、`CPU 7.6%`，**比 250 档的 5.7 ms / 24.9% 还低**。
如果只看数字，会误判成"连接越多越轻松"。

原因：tick 循环死后**不再写指标行**，剩下的样本是被截断的短片段。

**所以判失败必须以"崩溃"为准，不能只看数值。** 这也是 `analyze()` 里
把 `server_crashed` 压过一切数值判据的原因（有回归测试）。
出图时该档位也**必须排除** —— 否则曲线末端会出现一段假性下降。

### 4.2 请求 250 个客户端，实际只有 238 个在线

从快照字节数能反推出来：`players = 快照B − 1883) / 11`。

| 请求 | 实际在线 | 缺口 |
|---|---|---|
| 10 | 10 | 0 |
| 20 | 20 | 0 |
| 50 | 48 | 2 |
| 100 | 96 | 4 |
| 200 | 190 | 10 |
| 250 | 238 | **12** |

**原因**：机器人全部跑在**一个 Python 进程**里，受 **GIL** 限制只能用一个核。
250 个 asyncio 客户端挤在一个核上，发送心跳会延迟；
而服务端心跳超时是 **15 s**，超时就被 `reap_timeouts()` 踢掉。

所以"**服务端能撑多少**"与"**机器人能模拟多少**"是两个不同的上限，
本轮实验里后者先到顶。**这是测试端的限制，不是被测系统的限制** —— 写论文时必须讲清楚，
否则会被质疑"你的并发数不实"。

> 改进方向（未做）：机器人按 CPU 核分多进程，或提高心跳超时。
> 本轮选择**如实记录**而不是掩盖，因为缺口本身是可控且可解释的。

## 5. 已知局限

### 5.1 未能测到资源极限

因为协议上限（255）先触发，**E2 没有测到"CPU 或带宽先撑不住"的点**。
10~250 的曲线显示资源仍宽裕（CPU 24.9%、tick 5.7 ms），外推约在 **1000 连接**量级
才会碰到 50 ms 预算 —— 但**协议不支持，无法验证**，所以论文里只说"250 以内仍宽裕"，
不做外推。

### 5.2 100 档两轮 tick 偏差 10.6%

已自动补跑一轮 120 s 采样，三轮为 2.523 / 2.969 / 2.976 ms ——
第 1 轮偏低约 15%，后两轮一致。该档 CPU 读数波动也大（11.2% / 7.4% / 10.7%）。

**判断**：属于该档位（100 连接）在 2~3 s 内集中建连时的瞬时抖动，
三轮取均后 2.823 ms 仍落在 50→200 的单调区间内，不影响趋势结论。
**论文里注明三轮取均，并保留原始三轮数据。**

### 5.3 机器人端瓶颈（见 §4.2）

实际在线数低于请求值，且缺口随规模增大。

### 5.4 回环网络

全部在本机 `127.0.0.1` 上（D-016），**RTT 不含真实网络往返**，
所以 P50 只有约 1 ms。这里的 RTT 反映的是**服务端处理 + 本机回环**，
不是广域网时延 —— 图 6-6 的正确读法是"**服务端处理延迟随连接数的增长**"。

## 6. 答辩可能被问

- **你的服务端能撑多少连接？** → 答：**实测 250 连接稳定**（tick 5.7 ms、CPU 24.9%、内存 44.5 MB），
  再往上（300）触发的是**协议上限 255**（`player_count` 是 uint8），不是资源耗尽。
  所以准确说法是"**协议设计上限 255，250 以内资源充裕**"。
- **为什么不用 uint16 存玩家数？** → 答：局域网对战场景 255 人远超需求，
  用 1 字节更省；这是**有意的设计取舍**，与"敌机 ≤ 30"同类。
  真要提高上限只需改字段宽度 + 重跑本实验。
- **300 档的 tick 反而更低，怎么解释？** → 答：tick 循环已崩溃、停止写指标，
  那是**被截断的样本**。判失败看"是否崩溃"而不是看数值；出图时该档已排除。
- **250 个机器人为什么只有 238 个在线？** → 答：机器人单进程受 GIL 限制，
  高并发下心跳延迟被服务端 15 s 超时踢掉。**这是测试端限制**，
  服务端侧 250 档两轮 tick 偏差仅 0.1%，说明服务端本身很稳。
- **碰撞耗时为什么几乎不变？** → 答：实体数固定（D-029），逻辑侧恒定；
  增长全在通信侧（8.5×）。这正是把"逻辑"与"通信"分开测量的意义。
