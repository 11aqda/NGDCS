### 1.1 ⚠️ 跑实验前必须先改一处代码

原来 `TICK_HZ` 是**写死的常量**，而指标 CSV 是"每 N 个 tick 一行"，`N` 也写死成 20。
直接改 tick 率的话：

| tick 率 | 窗口里的 tick 数 | 一行代表的时间 | 后果 |
|---|---|---|---|
| 10 Hz | 20 | **2.0 秒** | `bytes_out` 被当成 1 秒的流量 → 带宽**虚低一半** |
| 20 Hz | 20 | 1.0 秒 | 正常 |
| 30 Hz | 20 | **0.67 秒** | 带宽**虚高 1.5 倍** |

关键是**它不会报错**：CSV 照样写、图照样画，只是那条直线的斜率是错的。

所以改成 `stats_every_ticks = tick_hz`（窗口恒为 1 秒），并加了
`tests/test_tick_rate.py::test_window_is_always_one_second` 守住这条。
`--tick-hz` 的默认值仍是 20，**没有动 E1/E2/E9 的基线**。

## 2. 实验配置

```powershell
# 服务端（每一档换 --tick-hz）
python -X utf8 -m server.main 9585 --enemies 30 --bullets 200 `
    --scenario E5-h20-r1 --tick-hz 20 --fixed-entities --no-stats

# 机器人（4 个客户端，跑 190 s）
python -X utf8 -m bot.main --clients 4 --duration 190 --seed 99
```

一次跑完 8 轮：`.venv\Scripts\python.exe -X utf8 -m tools.run_e5`（约 26 分钟）

**汇总口径**（`tools/run_e5.py::summarize`）：

- 只取 `client_count == 4` 的行 —— 服务端一启动就写指标，前几秒没客户端，那些行没有快照流量
- 再丢掉该档的前 10 秒预热
- **带宽** = `bytes_out` 的均值（每行恒为 1 秒，所以均值就是 B/s）
- **CPU** = `cpu_seconds` 首尾差 ÷ 墙钟秒 × 100（E9 口径；低负载下逐行 `cpu_percent` 被计时粒度量化）
- **单 tick 耗时** = `tick_ms_avg` 的均值（每行是该窗口内所有 tick 的平均）与 p95

## 3. 关键结果

### 3.1 逐轮与逐档（两轮均值）

| tick 率 | 轮 | 带宽 KB/s | CPU % | tick ms | p95 ms | 帧预算占用 |
|---|---|---|---|---|---|---|
| **10 Hz** | r1 | 75.76 | 0.82 | 1.007 | 1.041 | 1.0 % |
| | r2 | 75.76 | 0.93 | 1.062 | 1.130 | 1.1 % |
| | **均值** | **75.76** | **0.88** | **1.034** | 1.085 | **1.1 %** |
| **15 Hz** | r1 | 113.63 | 1.26 | 1.072 | 1.120 | 1.6 % |
| | r2 | 113.63 | 1.14 | 1.066 | 1.117 | 1.6 % |
| | **均值** | **113.63** | **1.20** | **1.069** | 1.119 | **1.6 %** |
| **20 Hz** | r1 | 151.07 | 2.04 | 1.057 | 1.109 | 2.1 % |
| | r2 | 151.50 | 1.97 | 1.068 | 1.107 | 2.1 % |
| | **均值** | **151.28** | **2.00** | **1.062** | 1.108 | **2.1 %** |
| **30 Hz** | r1 | 226.56 | 3.16 | 1.053 | 1.097 | 3.2 % |
| | r2 | 227.24 | 2.89 | 1.071 | 1.104 | 3.2 % |
| | **均值** | **226.90** | **3.03** | **1.062** | 1.101 | **3.2 %** |

> 「帧预算」= `tick_ms_avg ÷ (1000 / tick_hz)`。10 Hz 的预算本来就是 100 ms，
> 30 Hz 是 33.3 ms —— **逐档比预算才有意义**，不能都拿 50 ms 去比。

### 3.2 三条核心结论

**① 带宽与 tick 率严格线性，且能被解析式精确预测（误差 ≤ 0.14%）**

每档"每 Hz 的带宽"：7.576 / 7.575 / 7.564 / 7.563 KB/s —— 四档之间的差异只有 0.17%，
基本就是测量噪声。这意味着**不需要查表，直接算**：

$$
\text{带宽（KB/s）} = \frac{(S + 12) \times P \times f}{1024}
$$

其中 `S` = 快照载荷字节数（本题 1927）、`12` = 帧头、`P` = 玩家数（4）、`f` = tick 率。

| tick 率 | 实测 KB/s | 解析 KB/s | 误差 |
|---|---|---|---|
| 10 Hz | 75.76 | 75.74 | **+0.02%** |
| 15 Hz | 113.63 | 113.61 | **+0.01%** |
| 20 Hz | 151.28 | 151.48 | **−0.13%** |
| 30 Hz | 226.90 | 227.23 | **−0.14%** |

能对到 0.1% 以内，说明**带宽完全由"全量快照 × 频率 × 人数"决定**，
没有隐藏的额外流量（心跳 1 Hz、输入 20 Hz 相比快照都可忽略）。

**② 单 tick 耗时与频率无关（1.03 ~ 1.07 ms，极差 0.04 ms = 3.3%）**

每个 tick 干的活是一样的：模拟 234 个实体 + 朴素碰撞 + 序列化一次 1927 B 快照。
频率只决定"每秒干几次"，不改变"每次干多久"。**没有出现**"频率越高单次越慢"
（那通常意味着 CPU 降频或缓存竞争），说明这台机器在 30 Hz 以内完全吃得下。

**③ CPU 与频率成正比，但增速略缓于"tick_ms × 频率"的理论值**

| tick 率 | 由 `tick_ms × f` 推算 | 实测 CPU | 差异 |
|---|---|---|---|
| 10 Hz | 1.034 % | 0.88 % | −14.9% |
| 15 Hz | 1.604 % | 1.20 % | −25.2% |
| 20 Hz | 2.124 % | 2.00 % | −5.8% |
| 30 Hz | 3.186 % | 3.03 % | −4.9% |

两个原因，都写在这里免得被当成"数据不对"：

1. **`tick_ms` 是墙钟耗时，不是 CPU 时间**。tick 内部有 `await`（等 socket 可写），
   那段时间不烧 CPU，但算进 `tick_ms`。
2. **低负载下 CPU% 被计时粒度量化**。10/15 Hz 时进程只占 1% 上下一个核，
   psutil 的秒级采样在这个量级上误差很大（`plot.py` 的一致性检查也把 <2% 的档
   标成"读数受计时粒度限制，以 tick 为准"）。

20/30 Hz 差距（5%）小得多，正是因为负载够高、量化误差相对变小 —— 这个趋势本身就自证了解释成立。

## 5. 数据质量与异常

### 5.1 采集完整性

| 项 | 值 |
|---|---|
| 轮次 | **8 / 8 全部成功**（无崩溃、无超时、无 `tick loop` 中断） |
| 每轮指标行 | 满负载行 ≥ 180 行（1 Hz，覆盖 3 分钟采样） |
| 实体数校验 | `--fixed-entities` 全程通过，快照稳定 1927 B（8 轮 `snapshot_bytes` 全是 1927） |
| 丢帧 / 崩溃标记 | 0 |

`--fixed-entities` 的守卫在这里很关键：它保证 4 轮之间的**分子完全相同**，
带宽的差异只可能来自 tick 率 —— 这正是本实验要的因果隔离。

### 5.2 环境干净度

跑之前关掉了游戏服务端（`server.main`）和 Django，只留 MySQL / Redis 服务（空转）。
浏览器（msedge）仍在运行，但它不在绑核的 CPU 0–1 上（服务端独占那两核），
影响主要是 L3 缓存与内存带宽，属于**桌面机做实验的固有噪声**，已在 §5.4 记入局限。

### 5.3 ⚠️ 必须如实记录的一处耦合：**游戏速度会随 tick 率变**

`PLAYER_SPEED_PER_TICK` 是"每 tick 固定像素"，`tests/test_movement.py` 断言
`PLAYER_SPEED_PER_TICK × TICK_HZ == 300`（20 Hz 下 300 px/s）。

所以：

| tick 率 | 玩家实际速度 |
|---|---|
| 30 Hz | 450 px/s |
| 20 Hz | 300 px/s（基准） |
| 15 Hz | 225 px/s |
| 10 Hz | **150 px/s** |

**这是已知耦合，不是 bug**：本实验只测带宽 / CPU / 单 tick 耗时，
三者都与"玩家跑多快"无关，所以结论不受影响。
但它确实说明：**要把 tick 率当产品旋钮用，就得先把所有"每 tick"常量改成"每秒"**。
这件事列入步骤 11（见 D-031 之后的待办）。

### 5.4 图 6-12 的实测结果：**理论预测被推翻**（2026-11-04 补做）

`err_px` 采集做完后，本地补跑了图 6-12（4 档 × 2 轮 × 40 s，`tools/run_e5_errpx.py`）。

**跑之前的预测**：`err ≈ v × (1/f)`，即误差与 tick 率成反比 —— 10 Hz 应是 20 Hz 的 2 倍。

**实测方向相反**：

| tick 率 | 首轮 err 均值 | 复跑 err 均值 | 两轮均值 | P95 | max | 相对 20 Hz 的"反比推算" |
|---|---|---|---|---|---|---|
| 10 Hz | 10.30 | 10.21 | **10.21** | 17.23 | 17.61 | 预期 17.47，偏差 **−41.6%** |
| 15 Hz | 9.17 | 9.20 | 9.20 | 18.07 | 18.53 | 预期 11.65，偏差 −21.0% |
| 20 Hz | 8.73 | 8.69 | 8.69 | 18.70 | 19.38 | 基准 |
| 30 Hz | 7.05 | 7.08 | **7.08** | 19.65 | 20.62 | 预期 5.79，偏差 **+22.3%** |

两轮独立复跑的偏差分别为 −0.9 % / +0.3 % / −0.5 % / +0.5 %，**全部在 1 % 以内** ——
不是测量噪声。

> **复跑时间点**：这两轮是在修完客户端 `alpha` 之后跑的（见 §5.5）。
> 数字与修复前一致，因为 `err_px` 一直由机器人用 `protocol/interp.py` 采集，
> 而那个公式本来就是正确的；修复让**客户端渲染**也换成了同一个公式。

#### 为什么不成立 —— 又是 §5.3 那条耦合

预测式默认速度是"**每秒**多少像素"。但本项目是 `PLAYER_SPEED_PER_TICK`
（**每 tick 固定 15 px**），所以**每 tick 的位移与频率无关**，误差自然不随 `1/f` 变。

再进一层：频率越高，玩家**实际速度**越大（10 Hz → 150 px/s，30 Hz → 450 px/s）。
30 Hz 下 1.6 秒就走完 720 px 的场地，**大部分时间被墙卡住、位移为 0**，
平均误差反而变小。

证据：`err_mean ÷ 15px` 从 10 Hz 的 **0.69** 掉到 30 Hz 的 **0.47**，
正是"处于移动状态的帧变少了"。而 P95 反向上升（17.3 → 19.6），
因为高频下每帧位移仍是 15 px、偶发两帧叠加时跳得更远。

#### 这个结果怎么用

**不要把它写成"频率越低越准"** —— 那会把设计缺陷当成优点。

正确的表述是：**插值误差被"每 tick 固定像素"这个速度模型主导，而不是被网络主导**。
这是 §5.3 那条限制的**第二个后果**（第一个是"游戏速度随频率变"）。

要让 6-12 呈现教科书里"频率越低误差越大"的形状，必须先做一件事：
**把所有 `*_PER_TICK` 常量改成"每秒像素"**，然后重跑本实验。
这件事已列入步骤 11，重跑后本节要整体重写。

### 5.5 客户端 `alpha` 的 bug（已修，并影响本节结论的**可解释性**）

**修之前**：`client/main.py` 用**写死的** `TICK_INTERVAL = 0.05`（20 Hz 的间隔）当插值分母。

| tick 率 | 真实间隔 | 用 0.05 算的后果 |
|---|---|---|
| 30 Hz | 33 ms | alpha 到 33 ms 才 0.67，帧就到了 → 画面**永远追不上**（拖影） |
| 10 Hz | 100 ms | alpha 在 50 ms 就到 1 并钳住 → 后 50 ms **冻住**再跳一下 |
| 抖动时 | 忽大忽小 | 固定分母与真实节奏完全不匹配 |

**这条 bug 与本节的关系**：`err_px` 一直由机器人经 `protocol/interp.py::clamp_alpha`
采集，**用的是正确公式** —— 所以本节的数字描述的是"正确算法"的表现，
不需要重算。但客户端当时渲染的**不是**这个算法，等于"论文里说的和玩家看到的不一致"。

**修法**：客户端改为按**两帧实际到达时刻**算（复用同一个 `clamp_alpha`），
并加了防回归测试（`tests/test_client_ui.py::InterpolationRegressionTest`）。
修复后按同样的条件复跑本节实验，四档偏差 ≤ 1 %（见 §5.4 的对照表），
证明修改没有影响测量口径。

> **方法论要点**：**测量和渲染必须共用同一个插值公式**，
> 否则实验结论和玩家体验就是两回事。这条已经写进代码注释。

### 5.6 已知局限

1. **玩家数固定为 4**。带宽 ∝ 玩家数（§3.2 ① 的解析式里就有 `P`），
   但"玩家数 × tick 率"的**联合**影响没有做交叉实验（那是 E2 的范围）。
2. **全部在本机 loopback**。没有真实链路的带宽上限与丢包，测的是"协议产生多少流量"，
   不是"链路能不能扛"。
3. **6-12 的采样只有 40 s**（主实验是 180 s）。`err_px` 是逐帧样本，
   40 s 已有 1790~5390 个样本，够稳；但和主实验的时长不一致，写论文时要注明。
4. **只有 4 档数量级的 tick 率**，没有测 60 Hz 以上。按 §3.2 ② 的结论外推
   （单 tick 1.06 ms），60 Hz 时预算占用会是 6.4%，仍在安全区，
   但**没测就是没测**，不外推成结论。

## 7. 结论与对设计的影响

**结论一句话**：tick 率是一个**代价严格线性、收益直接可见**的旋钮 ——
带宽按 `7.57 KB/s per Hz`（4 玩家时）线性增长，CPU 同比例增长，
而**单 tick 的计算量完全不变**。

对设计的影响：

1. **默认 20 Hz 是合理的**。4 玩家 30 敌对 200 弹时占用 151 KB/s、2% 单核、2.1% 帧预算 ——
   余量巨大。
2. **要提升流畅度就升频率，代价可预算**。从 20 → 30 Hz：带宽 +50%（151 → 227 KB/s）、
   CPU +50%，换来快照间隔从 50 ms 降到 33 ms。**不需要重新做容量评估**，套解析式即可。
3. **瓶颈不在频率，在实体数**。30 Hz 时单 tick 才吃 3.2% 预算；
   而 E9 已经量出实体数的拐点在 215 敌 / 1720 弹。两者的量级差了两个数量级 ——
   优化优先级应该是**降实体同步成本**（区域裁剪 / 差量快照），而不是降频率。
4. **降频率换带宽是"省得不多、亏得很多"**。20 → 10 Hz 只省 75 KB/s，
   但快照间隔变成 100 ms，插值误差、操作延迟都会明显恶化（这也是 6-12 要量的事）。
