## 2. 实验配置

### 2.1 ⚠️ 为什么没用 netem（以及为什么这不影响结论）

`03-实验清单` 原定在 Ubuntu VM 里用 `tc netem` 注入损伤。实际情况：

- 本机**没有安装 WSL 发行版**（`wsl -l -q` 返回退出码 1）
- 装一个需要下载镜像、可能要重启并修改系统功能

所以改用**用户态 TCP 代理**（`tools/netem_proxy.py`），机器人连代理、代理连服务端，
在代理里按配置延迟数据块。这属于 D-032。

**对"延迟"这一轴，代理与 netem 是严格等价的**：都是把数据推迟 D 再交付，
实测 `--delay-ms 100` 得到往返 219 ms（理论 2×100+1），偏差 18 ms 是操作系统的定时器粒度。

### 2.2 ⚠️⚠️ 最关键的一点：**TCP 上"丢包"的表现是延迟，不是丢帧**

这是本实验最容易讲错、也最容易被问倒的地方：

| 注入方式 | 网络层发生什么 | **应用层**看到什么 |
|---|---|---|
| netem 丢包（IP 层） | 数据段被丢弃 → TCP **重传** | **不会少收快照**，只是**来晚了** |
| 应用层丢帧（`bot --sim-loss`） | 整帧被丢弃 | 真的**少收一帧** |

我们的传输层是 **TCP**，所以正确的实现是前者：
**"丢包率"要模拟成"按概率给该数据块加一个 RTO 量级的额外延迟"**
（Linux TCP 最小 RTO = 200 ms，代理默认用这个值）。

`bot --sim-loss` 保留，但**不作为 E4 主实验** —— 它模拟的是 UDP 式丢帧，
与 TCP 的真实行为不是一回事。

**这个选择直接决定了结果的形状**：丢包的影响集中在**尾部**（P95），而不是均值。

### 2.3 运行方式

```powershell
# 服务端
python -X utf8 -m server.main 9620 --enemies 30 --bullets 200 `
    --fixed-entities --no-metrics --no-stats

# 损伤代理（每一档换参数）
python -X utf8 -m tools.netem_proxy --listen 9720 --upstream 9620 `
    --delay-ms 100 --jitter-ms 0 --loss-pct 5

# 机器人（8 个，走代理）
python -X utf8 -m bot.main --port 9720 --clients 8 --duration 65 --err-px --out ...
```

一次跑完：`.venv\Scripts\python.exe -X utf8 -m tools.run_e4`

### 3.2 五条结论

**① 恒定延迟对插值误差【零影响】**

延迟 0 → 200 ms，`err_px` 均值 8.22 → 8.19、P95 18.71 → 18.80，
**在噪声范围内完全不变**；而 RTT 从 1 ms 涨到 407 ms（说明延迟**确实注入成功**了）。

原因：恒定延迟把所有快照**整体平移**，快照之间的**相对间隔**没变，
插值器看到的输入节奏和本地一样。

> **这是本实验最重要的一条**：延迟和"画面平滑度"是**两件事**。
> 延迟伤害的是**操作手感**（按下到看见反应的时间），
> 插值误差伤害的是**画面连续感**。论文里不能混为一谈。

**② 丢包的影响集中在尾部，不在均值**

丢包 0 → 20 %：均值 8.22 → 9.48（**+15 %**），但 P95 18.71 → 29.94（**+60 %**）。

这与 §2.2 的机制一致：TCP 丢包不会丢帧，只会让数据**来晚**（一个 RTO ≈ 200 ms）。
"来晚"在统计上就是**尾部的几个大值**，均值被大量正常帧摊平。

所以**图 6-8 的主线必须是 P95**。只看均值会得出"丢包影响不大"的错误结论。

**③ 丢包率从 5 % 到 10 % 有一个明显跳变**

| 丢包 | err P95 | 到达间隔 P95 |
|---|---|---|
| 0 % | 18.71 | 62.5 ms |
| 5 % | 18.93 | 64.5 ms |
| **10 %** | **27.66** | **249.0 ms** |
| 20 % | 29.94 | 250.1 ms |

5 % 时几乎无影响，10 % 时 P95 突增 46 %、到达间隔 P95 直接**翻了 4 倍**（64 → 249 ms）。

**机制推断（未直接测量，如实标注）**：这是**头部阻塞**（head-of-line blocking）。
代理按 FIFO 转发，一个块被"重传"卡住 200 ms 时，**后面所有块都排在它后面**；
丢包率低时偶发的 stall 之间彼此不重叠（一个 stall 结束后队列已排空），
丢包率上来之后 stall 开始**首尾相接**，队列再也排不空 ——
于是到达间隔出现连续的 200 ms 空洞。

支持这个推断的证据：`interval_p95` 在 10 % 处从 64 ms 跳到 249 ms（几乎正好是一个 RTO），
且之后不再随丢包率增长（因为队列已经饱和，瓶颈是 stall 本身而不是频率）。

**④ 延迟与丢包【没有交互作用】**

图 6-10 的热力图每一**行都是水平的**：同一丢包率下，延迟 0 → 200 ms 的 P95 变化 ≤ 1 %。
说明两者是**独立的两个维度**，可以分开讨论、分开优化。

**⑤ 抖动是最强的单一因素，且作用平滑**

| 注入 | err 均值 | err P95 |
|---|---|---|
| 无损伤 | 8.22 | 18.71 |
| **+50 ms 抖动** | 9.32（+13 %） | 24.90（+33 %） |
| **+100 ms 抖动** | 10.07（+23 %） | 29.89（+60 %） |
| +200 ms **恒定延迟** | 8.19（**−0.4 %**） | 18.80（**+0.5 %**） |

**200 ms 的恒定延迟几乎无害，100 ms 的抖动却让 P95 涨了 60 %。**

抖动改变的是**相邻快照的间隔**，而插值器的 `alpha` 正是按实际间隔算的 ——
间隔忽大忽小，插值就走偏。这解释了为什么"延迟"和"抖动"在体验上的差别远大于数值上的差别。

18 个条件各跑 1 轮；在**两端 + 转折点**三个点上做了独立复跑（`tools/e4_repeat.py`）：

| 条件 | 指标 | 首轮 | 复跑 | 偏差 |
|---|---|---|---|---|
| l0-d0（基线） | err 均值 | 8.22 | 8.13 | **−1.0 %** |
| | err P95 | 18.71 | 18.55 | **−0.8 %** |

## 5. 数据质量与异常

### 5.1 采集完整性

| 项 | 值 |
|---|---|
| 条件数 | **18**（4 丢包 × 4 延迟 + 2 抖动对照） |
| 成功 | **18 / 18** |
| 每条件样本 | 8 玩家 × 60 s × 20 Hz ≈ **9600 个 `err_px` 样本** |
| 客户端连接 | 每条件 8/8 全部连上 |
| 复跑 | 3 个关键点，偏差 ≤ 1.3 % |

### 5.2 代理与 netem 的等价性（必须说清）

| 维度 | netem | 本代理 | 等价性 |
|---|---|---|---|
| **延迟** | `delay 100ms` | `--delay-ms 100` | **严格等价**（都是推迟 D 交付）。实测 219 ms vs 理论 201 ms |
| **抖动** | `delay 100ms 100ms` | `--jitter-ms 100` | 等价，但**保序**：真实 netem 可能乱序，TCP 会重排；本代理用 FIFO 直接保序 |
| **丢包** | `loss 10%` | `--loss-pct 10` | **近似等价**：都是"该数据晚到 ≈ RTO"，但 netem 是真丢真重传，本代理是直接推迟 |

**为什么"近似"够用**：两者的应用层效果都是"这块数据晚到约一个 RTO"。
差别在于 netem 会真的触发 TCP 拥塞控制（cwnd 减半），本代理不会 ——
所以本代理测到的是**纯延迟效应**，不含拥塞窗口收缩。
这一点会低估真实环境的恶化程度，属于**保守估计**。

### 5.3 已知局限

1. **丢包的 5 % → 10 % 跳变是机制推断，不是直接测量**。
   要确认需要记录代理队列长度，本次没做（见 §3.2 ③ 的证据与标注）。
2. **每条件 1 轮**，只在 3 个点上复跑。曲线形状可信，但单点的绝对精度只有一次采样。
3. **全部在 loopback + 本机代理**。代理自身是用户态转发，会引入约 15~20 ms 的
   定时器开销（已在 `实测 RTT` 列里体现，读者可据此校正）。
4. **8 名玩家**。玩家数增加会让快照变大、单帧占用更多带宽，但**不改变丢包率的影响机制**。
5. **代理不模拟 TCP 拥塞控制**（见 §5.2），因此对真实恶劣网络的恶化程度是**低估**的。
6. **未测"丢包 + 抖动"的组合**，只测了各自单独与"丢包 × 延迟"。

## 7. 结论与对设计的影响

**一句话**：决定插值质量的是**到达时间的方差**，不是**平均延迟**。

对设计的影响（按优先级）：

1. **抗抖动比抗延迟更重要**。如果带宽/算力只够做一件事，应该做
   **抖动缓冲（jitter buffer）或位置外推**，而不是去优化链路延迟。
   本实验给出了量化依据：100 ms 抖动 → P95 +60 %；200 ms 延迟 → P95 +0.5 %。

2. **插值策略应当按"实际到达间隔"算 alpha，而不是按固定 tick 间隔**。
   本项目的客户端目前用的是常量 `TICK_INTERVAL = 0.05`（对应 20 Hz），
   在抖动或不同 tick 率下会算错 —— 这是从 E4/E5 两次实验里**共同指向的一个改进点**，
   已列入步骤 11。

3. **TCP 的代价要写进选型讨论**。本项目选 TCP 是因为实现简单、天然可靠；
   代价是丢包会以"200 ms 级的延迟尖峰"的形式出现（重传），
   这对实时游戏的观感伤害比 UDP 的"丢一帧"更大。
   `02 §3` 的传输层选型讨论应当引用本实验的这组数据。

4. **5 % 丢包是一个可接受的工作点，10 % 开始明显劣化**。
   若将来做自适应码率/发送频率，可以把"丢包率 > 8 %"作为降低 tick 率或
   简化快照的触发条件。
